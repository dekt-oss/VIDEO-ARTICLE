# video-article 대시보드 — 화면·시스템 구성 브리핑 (UI/UX 리뷰 요청용)

작성 시점: 2026-07-27 · 기준 커밋: `ba77971` (main, Vercel 운영 배포 완료)

이 문서는 **외부 리뷰어(GPT)에게 UI/UX 개선 검토를 받기 위한 현황 브리핑**이다.
코드에서 직접 확인한 사실만 적었고, 추정이 섞인 곳은 "미확인"이라고 표시했다.

---

## 0. 리뷰어에게 — 30초 요약

**1인 운영자가 매일 20~30분 안에 "논문 1편 → 숏폼 영상 1편"을 통과시키는 작업 콘솔**이다.
자동화(수집·채점·초안·렌더)는 이미 돌아가고, 사람이 하는 일은 **판단 3번 + 승인 2번**뿐이다.
그래서 이 대시보드의 성패는 예쁨이 아니라 **"지금 내가 무엇을 결정해야 하는가"가 몇 초 안에 보이는지**에 달려 있다.

- 접속: **<대시보드 URL>** (로그인 없음 — 주소를 아는 사람은 누구나 조작 가능. §6-1 참조)
- 화면 수: **22개**(논문 공장 13 + 리포트 공장 9), API 라우트 31개
- 기술: Next.js 14 App Router + 순수 CSS 357줄 (UI 라이브러리 없음), Supabase, 다크 단일 테마
- 특히 봐줬으면 하는 것: **§4-1 홈, §4-3 검수 상세(가장 길고 무거운 화면), §6 마찰 목록**

## 2. 무엇을 하는 도구인가 (사용자·목표)

- **사용자:** 운영자 1명(제작자 본인). 데스크톱 주 사용, 모바일에서도 확인함(모바일 대응 흔적이 CSS에 있음).
- **주기:** 하루 1편. 아침에 후보를 보고 1편 낙점 → 초안 검수 → 지시서 승인 → 렌더 결과 확인 → 유튜브 업로드.
- **명시된 합격 기준**(프로젝트 문서 `CLAUDE.md` 기준):
  - 낙점 → 승인까지 **사람 작업 30분 이내/편**
  - 발행 가능 초안의 **사실 오류 0건** (LLM 자기검증의 빨간 깃발이 실제로 오류를 잡아야 함)
- **공장이 2개 있다:** 🎬 **논문 공장**(루트 경로) / 📈 **리포트 공장**(`/finance` 접두, 금융·증권 리포트 소재).
  두 공장은 화면 구조가 거의 같고 강조색만 다르다(논문=파랑 `#4f8cff`, 리포트=바이올렛 `#a855f7`).

### 파이프라인 (화면 번호와 1:1 대응)

```
① 수집 → ② 채점(5축 LLM) → ③ 최종선별(사람 낙점) → ④ 초안 검수(사람)
   → ⑤ 영상 지시서(사람 승인) → ⑥ 렌더 결과(mp4) → 유튜브 업로드 → 성과 분석
```

화면마다 상단에 이 흐름이 텍스트로 찍히고 현재 단계만 굵게 표시된다(`.flow` 클래스).

## 3. 시스템 구성

```
┌─────────────────────────── 로컬 / GitHub Actions (Python 엔진) ────────────────────────────┐
│ engine/collect.py   수집 (arXiv·OpenAlex·HN·Reddit·언론 RSS)                              │
│ engine/score.py     5축 LLM 채점 → daily_batch 상위 N편                                   │
│ engine/draft.py     Fact Sheet 추출 → 대본 → 자기검증  (큐 폴링)                          │
│ engine/render.py    TTS + 이미지/영상 클립 생성 + ffmpeg 조립 → mp4                       │
│ engine/publish.py   유튜브 업로드(비공개 기본)                                            │
│ engine/analytics.py 쇼츠 성과 수집 → perf_report.py 분석 리포트                           │
│ 워크플로 10개: engine / draft / render / publish / analytics / report* / deploy-edge       │
└──────────────────────────────────────┬────────────────────────────────────────────────────┘
                                       │ 쓰기 (service_role 키 — 엔진 전용)
                                       ▼
                        ┌──────────────────────────────────┐
                        │  Supabase (Postgres + Storage)   │
                        │  마이그레이션 30개 · RLS 적용     │
                        │  Edge Function 4개:              │
                        │   generate-draft / -directive /  │
                        │   generate-report-draft /        │
                        │   translate-titles              │
                        └───────────────┬──────────────────┘
                                        │ 읽기·쓰기 (anon 키, 쿠키 세션)
                                        ▼
                   ┌────────────────────────────────────────────┐
                   │  Next.js 14 App Router  (Vercel)           │
                   │  페이지 = 서버 컴포넌트 SSR(force-dynamic)  │
                   │  조작 = 클라이언트 컴포넌트 → /api/* 33개   │
                   │  긴 작업 = 큐 INSERT 후 상태 폴링           │
                   └────────────────────────────────────────────┘
```

핵심 특성 3가지가 UX를 지배한다:

1. **모든 페이지가 `force-dynamic` SSR.** 캐시가 없어 항상 최신이지만, 이동할 때마다 Supabase 왕복이 있다.
   (체감 지연 수치는 **미측정**.)
2. **긴 작업은 전부 비동기 큐 + 폴링.** 초안 생성(약 1분), 지시서 생성, 렌더는 버튼을 누르면 큐에 행이 들어가고
   화면은 `useGeneration` 훅으로 상태를 폴링한다 → 스피너 + 단계 라벨 + 경과 초를 보여준다.
   렌더는 GitHub Actions 워커가 집어가므로 **수 분~수십 분** 걸린다.
3. **엔진은 수동 실행이 기본이다.** 무인 크론이 아니라 사람이 로컬 명령이나 Actions 버튼으로 돌린다.
   그래서 화면에 "데이터가 없으면 이 명령을 실행하세요"라는 안내가 여러 곳에 하드코딩돼 있다
   (예: `python -m engine.collect`).

## 4. 화면 구성

### 4-0. 공통 셸

- **상단 sticky 바 하나**가 전부다(사이드바·햄버거 없음). 구성: `[🎬 논문 | 📈 리포트]` 공장 스위처 + 메뉴 탭.
- 메뉴는 그룹 단위. 항목이 1개인 그룹은 탭으로 바로 노출, 2개 이상은 `<details>` 드롭다운으로 접는다.
  - 논문 공장 그룹: `홈 · 오늘의 후보` / **검수 · 제작**(④⑤⑥) / **보관함**(아카이브·휴지통) / **데이터**(①②·측정·쇼츠 성과·성과 리포트)
  - 리포트 공장 그룹: `📈 오늘의 리포트 후보` / 검수 · 제작 / 보관함 / 데이터
- 본문 폭 **max-width 920px**, 중앙 정렬. 즉 데스크톱 와이드에서도 한 컬럼이다.
- 피드백 3종: **토스트**(우하단), **확인 모달**(파괴적 동작), **스켈레톤/스피너**(생성 중).
- 코드 주석에 남은 명시적 사용자 요구: *"옆으로 쭉 나열되는 건 불편"* → 좁은 화면에서 탭은 가로 스크롤이 아니라 **줄바꿈**,
  드롭다운은 720px 이하에서 **인라인 확장**. *"두 공장을 헷갈리지 않게"* → 강조색 전역 치환.

### 4-2. 홈 `/` — ③ 최종 선별

세로 순서:

1. 제목 `③ 최종 선별 (오늘의 후보)` + 우측에 배치 날짜(확인 완료면 `✓`)
2. 파이프라인 한 줄 (`① 수집 → ② 채점 → ③ 최종선별 → ④ 초안`)
3. **요약 타일 5개** — 미확인 배치일 / 초안 대기(낙점됨) / 렌더 진행중 / 렌더 완료 / 발행. 각각 해당 화면으로 링크.
4. 확인 바 — "미확인 N일 · 오래된 미확인 일자부터 표시" + `이 날짜 확인 완료` 버튼
5. 날짜 네비 — `← 이전 배치` / 드롭다운 + `이동` / `최신 →`
6. 컨트롤 — 정렬 `재미순·중요순·황금순`(황금=재미×중요, 기본값) / 결정 필터 `전체·미정·낙점·후보·탈락` / `NEW만` / 편수
7. 후보 카드 N개 — `NEW` 뱃지, 한글 제목(원제는 작게 아래), 게재처·ID, 한 줄 요약,
   점수 3개(재미/중요/황금), 빨간 깃발 경고, 액션 `낙점 · 후보 · 탈락 · 원문↗`

동작 특징: **진입 시 "가장 오래된 미확인 배치일"을 자동으로 띄운다**(밀린 날짜부터 처리하게 만드는 설계).
낙점하면 카드가 사라지지 않고 테두리 색만 바뀐다(탈락은 반투명 50%).

### 4-3. 검수 상세 `/review/[paperId]` — 가장 길고 무거운 화면

**한 화면에 ④ 초안 검수와 ⑤ 영상 지시서가 세로로 다 들어있다.** 세로 순서:

1. 논문 제목(한글) + `← 목록`
2. 논문 요약 / 발행용 제목(`PublishTitles`) / 숏폼 캡션(`PublishCaption`) — 복사 버튼들
3. 초안이 없으면: 안내문 + 스켈레톤 + `초안 생성 요청` 버튼 (약 1분 폴링)
4. 초안이 있으면:
   - 승인됨 배너(초록) — "이제 아래 지시서에서 승인하면 렌더가 시작됩니다 (↓)"
   - **자기검증 배너** — 초록(`✓ 모든 문장이 Fact Sheet로 뒷받침됨`) 또는 노랑(`⚠️ 근거 없는 문장 N개 씬`)
   - **빨간 깃발 빠른 이동 링크** (`#1 #4 #7` 형태 앵커)
   - **Fact Sheet** — 발견 / 방법 / 수치 / 한계 / 주장 강도
   - **전체 영상 흐름(스토리보드)** — 로그라인 + 비트 목록 + 전환
   - **장면별 미디어 프롬프트** — 씬 카드 N개. 각 카드: 씬 번호·제목·길이·근거 fact id,
     나레이션(한/영), `✓ 뒷받침: …` 초록 줄, ① 이미지 프롬프트 + 복사, ② 영상 프롬프트 + 복사,
     `⚠️ 근거 없음: …` 빨간 줄. `✏️ 장면 편집` 토글로 전부 textarea 로 바뀐다.
   - **대본 (인라인 편집)** — 큰 textarea. 미저장 시 노란 점(`dirty-dot`).
   - **세부 수정 요청** — "어떤 방향으로 다듬을지" 자유 입력 → `이 요청으로 다듬기`(방향 있는 재생성)
   - **하단 sticky 액션 바** — `초안 재생성`(확인 모달, danger) / `승인`(확인 모달)
5. 이어서 **⑤ 만화 영상 지시서** 블록(`DirectiveClient`) — 영상 버전, 헤더, 컷 N개(효과 칩·모션 프롬프트·
   영상 클립 여부), `저장` / `재생성` / 언어 선택 / `승인`(→ 렌더 시작) / `⑥ 렌더 결과 →`

즉 **한 페이지에서 사람이 내리는 결정이 4종류**(장면 편집 저장 / 대본 승인 / 지시서 저장 / 지시서 승인)이고,
각각 다른 위치에 버튼이 있다. 스크롤 길이는 씬 수·컷 수에 비례한다(대략 10~15 스크린 추정 — **정확한 측정은 안 했다**).

### 4-4. 렌더 결과 `/render` — ⑥

- 컨트롤: 상태 필터 / `최신순·오래된순` / `★ 보관만` / 편수·건수 / `지금 렌더` / `휴지통`
- **2단 그룹**: 날짜 헤더 → 논문별 `<details>`(기본 접힘). 논문 줄에 `완료 2/3`, `$0.412` 비용, 언어·버전 뱃지.
- 펼치면: 📋 유튜브 업로드용 제목·설명 복사 버튼, mp4 미리보기, `▶️ 유튜브 업로드`,

## 6. 알려진 마찰 · 리뷰 때 참고할 사실

아래는 **코드에서 실제로 확인한 것**이다(추측 아님). 우선순위는 매기지 않았다 — 그 판단을 리뷰에서 받고 싶다.

### 6-1. 로그인이 없고 RLS가 전면 개방이다 ⚠️ 가장 큰 사실
- 로그인 페이지·미들웨어가 **없다**(`web/middleware.ts` 없음, 인증 관련 컴포넌트 없음).
  `globals.css` 에 `.login-box` 스타일만 유령처럼 남아 있다.
- 초기 마이그레이션(`0002_rls.sql`)은 `app_allowed_emails` 이메일 허용목록으로 막았지만,
  `0007_public_access.sql` 이후 정책이 **`for all to anon using (true) with check (true)`** 로 교체됐다.
  즉 주소를 아는 누구나 읽고 쓰고 삭제할 수 있다.
- UX 관점 질문: 1인 도구에 로그인을 붙이는 비용 vs 지금의 노출. 붙인다면 어느 화면부터인가.

### 6-2. 피드백 방식이 화면마다 다르다
- 대부분은 토스트(`useToast`)를 쓰는데, **홈의 후보 카드(`CandidateList`)만 `alert("저장 실패. 다시 시도하세요.")`** 를 쓴다.
- 성공 시 갱신 방식도 갈린다: 검수 화면은 `router.refresh()`, **렌더 목록은 `window.location.reload()`**
  (0.7초 후 전체 새로고침 — 스크롤 위치·펼친 `<details>` 상태가 날아간다).

### 6-3. 검수 상세 화면이 하나에 다 들어있다
- ④ 초안 검수와 ⑤ 지시서가 같은 페이지에 세로로 이어진다. 저장 지점이 4개(장면 편집 저장 / 대본 승인 / 지시서 저장 / 지시서 승인),
  각각 위치가 달라 "지금 눌러야 하는 것"이 화면 밖에 있을 수 있다.
- sticky 액션 바가 하나 있는데 이건 **④ 초안용**이다. ⑤ 지시서의 승인 버튼은 문서 흐름 안에 있다.
- 미저장 편집 표시는 노란 점(`dirty-dot`) 하나뿐이다. 페이지를 떠날 때 경고는 **없다**.

### 6-4. 대기 시간 안내가 단계별로 다르다
- 초안 생성: 스피너 + 단계 라벨 + 경과 초 + 스켈레톤 (약 1분, 안내 문구 있음)
- 렌더: GitHub Actions 워커가 처리 → **수 분~수십 분**. 화면에는 진행 상태 pill 만 있고 예상 시간 안내가 없다.
  사용자가 새로고침해서 확인해야 한다(자동 폴링 여부는 잡 상태에 따라 다름).

### 6-5. 공장이 2개라 화면·컴포넌트가 쌍으로 복제돼 있다
- `RenderList` ↔ `ReportRenderList`, `ReviewClient` ↔ `ReportReviewClient`, `CandidateList` ↔ `ReportCandidateList`,
  `ScoredTable` ↔ `ReportScoredTable`, `queries.ts` ↔ `reportQueries.ts`.
- 구분은 강조색 + 상단 스위처뿐이다. 한쪽만 개선되면 두 공장의 UX가 어긋난다.

### 6-6. 상태를 색으로만 구분하는 곳이 있다
- 낙점 = 테두리 강조색 / 탈락 = 투명도 50%. 텍스트 라벨이 카드에 남지 않는다(버튼 활성 상태로만 표시).
- 접근성 점검(대비비·키보드 내비게이션·스크린리더)은 **한 번도 하지 않았다.**
  `aria-label`·`role="tablist"`는 여러 곳에 있지만 검증된 적 없다.

### 6-7. 정보 밀도가 화면마다 크게 다르다
- 홈·검수는 카드형(여유 있음), `/scored`·`/papers`·`/analytics`는 숫자 테이블(밀도 높음).
- 920px 한 컬럼 제약 안에서 테이블은 좁고, 카드는 넓은 화면에서 공간이 남는다.

### 6-8. 빈 상태 안내가 개발자 명령어다
- "아직 배치가 없습니다. 엔진을 실행하세요: `python -m engine.collect` → `python -m engine.score`"
- 운영자 본인이 곧 개발자이므로 실용적이지만, 화면 톤은 콘솔에 가깝다.

## 7. 리뷰 시 지켜야 하는 제약

1. **1인 운영 도구다.** 협업·권한·알림 기능은 필요 없다. 팀 대시보드처럼 확장하는 제안은 범위 밖이다.
2. **의존성 추가는 신중히.** 지금 UI 라이브러리가 0개다(차트만 recharts). 제안이 라이브러리를 요구하면
   **그것이 없으면 안 되는 이유**를 함께 적어주면 좋겠다.
3. **Next.js 14 App Router 구조 유지.** 페이지는 서버 컴포넌트 SSR, 조작은 `/api/*` 라우트 핸들러.
4. **한국어 UI 유지.** 파이프라인 번호(①~⑥)는 문서·엔진·화면에서 공통으로 쓰는 어휘라 바꾸면 파급이 크다.
5. **다크 테마는 현재 유일한 테마다.** 라이트 모드 추가 여부는 열린 질문이다(운영자 선호 **미확인**).
6. 화면에 표시되는 사실(수치·Fact Sheet·근거)은 **환각 방지 불변식**의 산출물이다. 요약·축약을 제안할 때
   "근거 표시(빨간 깃발 / ✓ 뒷받침)를 덜 보이게 만드는" 방향은 이 도구의 핵심 안전장치를 깎는 것이다.

## 8. 리뷰에서 받고 싶은 답 (질문 리스트)

1. **홈(`/`)의 첫 3초.** 요약 타일 5개 + 배치일 네비 + 컨트롤 3줄이 후보 카드보다 위에 있다.
   "오늘 무엇을 결정해야 하는가"에 도달하기까지 군더더기가 있는가? 타일 5개는 많은가?
2. **검수 상세를 쪼개야 하는가.** ④ 초안과 ⑤ 지시서를 탭/단계(stepper)로 분리하는 것이 나은가,
   지금처럼 한 페이지 세로 흐름이 나은가? 저장 지점 4개를 어떻게 하나의 "진행" 축으로 묶을 수 있는가?
3. **30분 목표를 깎는 구간.** 위 화면 서술만 보고, 사람 시간을 가장 많이 먹을 것 같은 지점 3곳을 지목해달라.
4. **긴 비동기 작업(렌더 수십 분)의 표현.** 화면을 떠나도 되는 작업임을 어떻게 알려야 하는가?
   진행률·예상 시간·완료 알림 중 무엇이 1인 운영에서 실효가 있는가?
5. **두 공장(논문/리포트) 구분.** 강조색 + 상단 스위처만으로 충분한가? 색맹 대응 포함해서.
6. **정보 밀도 통일.** 카드형(홈·검수)과 테이블형(채점·성과)이 섞여 있다. 920px 한 컬럼 제약을 유지할 때
   테이블 화면을 어떻게 다뤄야 하는가? 폭 제약 자체를 화면별로 풀어야 하는가?
7. **없어도 되는 것.** 지금 화면 22개 중 통합하거나 없앨 수 있는 것이 있는가?
8. **접근성 최소선.** 한 번도 점검하지 않았다. 1인 도구에서 먼저 지켜야 할 항목 3~5개만 골라달라.
9. **6-2의 불일치**(alert vs toast, reload vs refresh)처럼, 지금 코드에 남은 비일관성 중
   사용자 체감이 가장 큰 것은 무엇인가?
