## 0. 결론 (두괄식)

GPT 명세의 **방향은 수용한다** — 논문 복잡도가 길이를 정하고, 제작비는 별도 예산이 정하며, 근거는
나레이션·오버레이·시각비교로 분산하고, 훅은 강하되 Claim 에 묶는다.

그러나 **코드와 대조하니 명세의 진단 5건이 실제와 달랐고, 그중 2건은 명세가 세운 전제를 무너뜨린다.**

1. **비용 통제가 운영 경로에 걸려 있지 않다.** 명세 §10 은 "이미 이중 캡이 있다"를 전제로 그 위에 모드별
   예산을 얹는다. 실제로 대시보드는 Edge Function 으로 지시서를 만드는데 그 트윈에는
   `preflight_video_budget` 이 **없다**. 지금 프로덕션은 4클립·16초·약 $0.80 을 그대로 내보낸다.
   → **엣지 preflight 이식이 이번 변경의 최우선 항목이다.** 이걸 안 하면 나머지 비용 규칙은 전부 장식이다.
2. **"근거를 화면으로 증명"의 렌더 경로가 0이다.** 명세 §11-5 는 `overlay_plan` 이 "완전히 구현되지 않았다"
   고만 적었지만, 실제로는 **기존 `text_overlay:<문구>` 이펙트조차 렌더에서 버려진다**. Phase 2 는
   "필드 추가"가 아니라 **오버레이 렌더 레이어 신설**이다.

**단일 변수 원칙:** 이번 변경의 실험 변수는 "근거 계약 + 가변 길이" 다. 화풍·훅 유형 enum·BGM·자막 규격은
건드리지 않는다. 훅·리텐션 P1~P5 는 이미 v2 로 `DIRECTIVE_SYSTEM_BASE` 에 있으므로 **재작성하지 않고
`hook_candidates` 게이트만 그 위에 얹는다**(기존 `bold_hook_gate_violation` 재사용).

### D-E4 — 명세 §14-3 에서 이탈한 이유 (구현 중 확정)

원 명세는 `approval_blocked` 면 무조건 승인을 막으라고 한다. 그런데 이 저장소에는 **정반대 전례**가
있다 — 커밋 `6a28761` "리포트 컴플라이언스 하드 차단 제거"에서 운영자가 직접 *"검토 결과(규칙 스캔·
LLM 심사·자기검증)는 참고용으로 계속 보여주되, 승인·영상화 흐름을 자동으로 막지 않는다"* 고 요청했다.
자기검증 LLM 이 오판하면 정상 지시서도 승인이 막히는데, 그 비용이 놓친 오류의 비용보다 크다는 판단이다.
확인 결과 이번에도 같은 방침이다.

그래서 차단 사유를 성격으로 갈랐다. 이건 "모델 자기보고 불신" 원칙을 한 걸음 더 민 것이기도 하다 —
코드가 확정한 사실은 사람을 막을 자격이 있지만, LLM 의 판단은 그렇지 않다.

| 성격 | 사유 | 처리 |
|---|---|---|
| 코드가 데이터로 확정 | 80초 초과 / 시리즈 분할 필요 / 영상 초수·금액 예산 초과 / 원장에 없는 `claim_id` / 필수 Claim 누락 / 핵심 Claim 미포함 | **차단(409)** |
| 자기검증 LLM 의 판단 | 범위 확대 / 인과 과장 / 숫자 불일치 / 수식어 삭제 / 편집적 추론 | **경고만** |

`tests/test_selfcheck_v2.py::test_only_deterministic_reasons_can_block` 이 이 경계를 고정한다.
막다른 길을 만들지 않으려고 `directive-approve` 에 `force: true` 우회를 남겼다.

D-E1 귀결:
- 금액 캡은 초수에서 **파생**한다(`sec × VEO_COST_PER_SEC_USD`). 두 값을 따로 적으면 드리프트한다.
- 모드가 없는 레거시 지시서는 기존 8초/$0.40 으로 폴백한다.
- 기존 `preflight_video_budget` 은 **마지막 백스톱으로 남긴다**(불변식 퇴행 방지).
- 편당 총예산 점검: extended 최악 = 고유 에셋 8장 × $0.039 + 영상 $0.80 = **$1.112 < `RENDER_BUDGET_CAP_USD` $1.2**.
  캡 상향 불필요. 이미지 Batch(기본값)면 $0.956 로 더 여유.

## 5. 프롬프트 변경

### 5-1. 길이 결정 (명세 §13-1)

`DIRECTIVE_SYSTEM_BASE` 의 `전체 길이는 약 {TARGET_TOTAL_SEC}초를 기준으로…` 줄을 **교체**한다.
전체 길이를 먼저 고정하지 말고 primary_claim → 필수 Evidence Unit → `content_mode` → 그 범위의 최단값 순으로
정한다. 80초를 넘겨야 하면 한 편을 늘리지 말고 `series_split` 을 제안한다.

### 5-2. 근거·집중도 — `config.EVIDENCE_RULES_SHARED`

근거·숫자·방법·한계 공통 규칙은 **config 상수 1개**로 두고 `SCRIPT_SYSTEM` 과 `DIRECTIVE_SYSTEM_BASE` 가
같은 문자열을 참조한다. `영상제작_프롬프트_통합명세.md` §4-3 이 지적한 규칙 중복이 4벌(파이썬 2 + TS 2)로
번지는 걸 막는 유일한 장치다. 기존 중복 줄을 **추가가 아니라 교체**한다.

### 5-3. 비용 (명세 §13-4)

`_VIDEO_CLIP_GUIDANCE` 의 `"그 개수를 꽉 채워 배정하라 — 남기지 마라"` 를 **삭제**하고
`motion_value=low 인 컷에는 I2V 를 배정하지 마라` / `I2V 최대 개수를 의무적으로 채우지 마라` 로 바꾼다.

### 5-4. 프롬프트 예산

`DIRECTIVE_SYSTEM_BASE` 는 이미 약 100줄이다. 명세 §13-1~13-5 를 그대로 붙이면 40줄이 더 붙어 지금 작동
중인 훅·리텐션 규칙이 희석된다. **순증 20~25줄**을 목표로: §13-1 7단계 → 4줄 압축, 공통 규칙은
`EVIDENCE_RULES_SHARED` 로 기존 줄 교체, 모드 골격은 **선택된 모드 것 하나만** 주입(4개 전부 나열 금지).

`max_tokens` 은 대본·지시서 둘 다 6144 → **8192**. 신규 필드로 출력이 약 900토큰 늘어 잘리면 JSON 파싱 실패
→ 재시도 1회 → 하드 에러(파이프라인 정지)라 소프트 저하가 아니다.

## 8. 열린 질문

1. **모드별 성과 판정 기준.** 명세 §18 은 모드별로 성과를 따로 비교하라고만 한다. `youtube_analytics` 에
   `content_mode` 를 남길지, 남긴다면 몇 편부터 판정할지는 표본이 쌓인 뒤 결정한다.
2. **`series_split` 의 운영 형태.** 코드는 "분할 권고"까지만 낸다. 2편으로 실제 쪼개는 UI·데이터 모델
   (같은 논문에 지시서 2개)은 이번 범위 밖이다.
3. **`evidence_grade=A` 도달 경로.** A 는 원문 PDF·HTML 본문을 읽은 경우만인데 현재 수집은 초록만 저장한다.
   본문 수집은 별도 결정 사항이며, 그때까지 A 는 사실상 나오지 않는다(설계상 안전측).
4. **`loop_safe` 판정 신뢰도**(기존 열린 질문 유지) — 신규 `motion_value` 도 LLM 판정이라 같은 리스크가 있다.
   기본값 `low` 가 안전측이라 최악의 경우도 "영상 대신 스틸"에 그친다.
