## 0. 결론 (두괄식)

**하루한리포트는 "리포트를 요약하는 채널"이 아니라 "리포트 속 핵심 투자 논리 하나를 근거·반론까지 이해시키는 채널"로 전환한다.**

> 채널 한 줄 정의: **증권사·산업·기업 리포트에서 주가와 산업을 움직일 핵심 논리 하나를 찾아, 근거와 반론까지 짧고 이해하기 쉽게 설명한다.**

전환의 5축:
1. **시각 = 설명판형 데이터 에디토리얼.** 화면 주역은 코드 렌더 설명판·차트·대형 숫자·근거 보드. 실사 이미지는 맥락 보조(15~25%). 웹툰/만화는 기본 경로 폐기.
2. **입력 = 리포트 원문.** 요약의 재요약 금지. source_mode 등급제 + report_analysis 선행.
3. **대본 = 질문 1개·주장 1개.** depth_core / core_thesis / nugget≥2 / counter·watchpoint 계약.
4. **길이 = 45~75초 가변** (기본 55~65초). 길이 = 질문에 답하는 최소 시간.
5. **검증 = 새 포맷 8편 중앙값** vs 기존. 북극성 = stayed_to_watch 단일.

**최대 위험 가정 (착수 전 실측 필수):** "리포트 원문을 확보할 수 있다." Phase 0에서 원문 확보율을 실측하고, 결과가 나쁘면(§16 P0-1) Phase 1 착수를 보류한다.

## 4. 설명판 시스템 (fin_boards)

설명판 = 차트·텍스트·출처·모션을 한 화면으로 조합하는 상위 레이어. 구현 = **레이아웃 템플릿(제목/차트영역/출처/so_what 슬롯) + 모션 단계 정의.** 별도 렌더 시스템 신설 금지 — 기존 조립 파이프라인의 컷 렌더 확장. 모듈 명칭·배치는 런타임 탐색 후 확정.

### 4-1. MVP 4종 (+엔딩 템플릿 1)

| 보드 | 내용 | 규칙 |
|---|---|---|
| `HOOK_BOARD` | 영상이 답할 질문/모순 1문장 | 시각 요소 ≤2 · 0.3초 내 나레이션 시작 · 로고 애니 금지 · **차트 모션이 주도** |
| `NUMBER_BOARD` | 핵심 숫자 1 + 비교 기준 ≤2 | `so_what` 한 줄 필수 (숫자 전시 금지) |
| `CHART_BOARD` | fin_charts 삽입 | 완성본 일괄 노출 금지 — 단계 등장, 나레이션 동기화 |
| `EVIDENCE_BOARD` | 리포트·공시·기사 필요 구간만 크롭 | 출처명·발행일·페이지/표번호 표시 · 전체 페이지 노출 금지 · 하이라이트 1~2개 |
| `WATCHPOINT_BOARD` | 이후 확인할 지표·일정 1~2개 | NUMBER_BOARD 변형 고정 엔딩 템플릿. 투자의견 대신 확인 기준을 남긴다 |

P2 이월: `MECHANISM_BOARD`(노드 그래프 — MVP는 나레이션+NUMBER_BOARD 연쇄로 대체) / `COMPARISON_BOARD`(race_bar와 함께) / `RISK_BOARD`(MVP는 C안 S7 패턴 = number_count(warn)+면책 카드로 대체).

### 4-2. 화면 정보량 상한

핵심 주장 1 / 핵심 숫자 1 / 보조 숫자 ≤2 / 본문 ≤2줄 / 범례 ≤3 / 출처 1줄 / 강조색 ≤2종. **자막은 설명판 문장을 복제하지 않는다** — 차트가 숫자를 보여주면 자막은 의미를 말한다.

### 4-3. 세이프존

**세로 배치는 §20-3 밴드 그리드가 유일 기준**(가장 구체적·최신). 요약: 핵심 헤드라인·숫자는 CORE 밴드(y 501~1180) / x 90~930 / 출처·면책 바는 SOURCE 밴드(y 1401~1500) / y>1500은 정보 배치 금지 / KO·EN 길이 차 고려한 자동 줄바꿈·축소. (자막 스타일 세부는 규격서 v2 §0~1 우선.)

## 5. 훅과 첫 프레임

### 5-1. 훅 아키타입 (MVP 5종)

| hook_type | 소재 | 예시 |
|---|---|---|
| `NUMBER_SHOCK` | 목표가·성장률·점유율 | "목표주가가 30% 올랐습니다. 그런데 이유는 매출이 아닙니다." |
| `CONTRADICTION` | 실적-주가 괴리 | "실적은 좋아졌는데 주가는 왜 떨어졌을까요?" |
| `WINNER_SHIFT` | 정책·공급망 수혜 이전 | "이 규제의 실제 수혜자는 미국 기업이 아닐 수 있습니다." |
| `MECHANISM_REVEAL` | 부품·작동 원리 | "막히는 건 로봇 완제품이 아니라 이 부품입니다." |
| `BEFORE_AFTER` | 정책·추정치 전후 | 규제/추정 변경 전후 비교 |

`MAP_FLOW`는 enum에 정의만, 구현 P2 (지도 코드 렌더 무거움 — 그 전까지 지도 소재는 EVIDENCE 크롭·실사 지도로 대체).

### 5-2. 첫 프레임 규칙

- 허용: MVP 보드 4종. **단 어떤 보드든 첫 1~2초 안에 fin_charts 모션(폭주·카운트업 등)이 화면을 주도해야 한다.** 정적 텍스트가 주인공인 화면 금지 — stayed 36.8%는 썸스톱 실패이며, 스와이프 판단 시점에 "움직이는 숫자"가 있어야 한다.
- 금지: 기업 빌딩 전경 / 분위기용 전광판 / 파스텔 지도 / 놀라는 웹툰 캐릭터 / 1초+ 로고 인트로 / 무관 추상 AI 영상.
- 훅 약속: 이유 설명 / 수혜·피해 구조 / 숫자의 함정 / 통념과 다른 점 / 확인 조건 — 중 1개를 명확히 약속하고 본문이 이행 (§7-5 검사).

### 5-3. 재미 장치의 지위

은유·위트는 "예외"가 아니라 **훅·전환 설계의 선택 요소** (LS v2 골드스탠다드 계승). 단 C안 컴플라이언스 하위(수치 주장 없는 context 분리 기록). MVP에선 생성 자산 없이 차트 모션·카피로 구현.

### 5-4. 만화·일러스트 예외 (최대 1컷)

## 6. 원문 분석 파이프라인 (본 전환의 심장)

### 6-1. 문제 정의

제목·요약·짧은 메모 입력 → 주장-근거 분리, 차트·각주·가정·리스크 소실, 기사 요약과 무차별, 제목 대비 얕은 본문. **대본 생성 전에 원문 분석 산출물을 반드시 생성한다.**

### 6-2. source_mode 등급

```jsonc
{ "source_mode": "FULL_REPORT | PARTIAL_REPORT | SUMMARY_ONLY",
  "source_quality": { "has_full_text": true, "has_page_refs": true,
    "has_tables_or_charts": true, "has_risk_section": true, "has_method_or_assumptions": true } }
```

- `FULL_REPORT`: 원문 전체 접근 → 정식 해석 영상 승인 가능.
- `PARTIAL_REPORT`: 핵심 본문·차트 존재, 일부 누락 → 조건부 승인 (누락 범위 UI 표시).
- `SUMMARY_ONLY`: 제목·초록·기사 재인용만 → **정식 해석 영상 승인 차단.** 별도 `REPORT_HEADLINE` 경량 포맷으로만 제작 가능(P0-1 실측 결과에 따라 정책 확정 §19). 원문 해석으로 오인될 표현 금지.

### 6-3. report_analysis — MVP 스키마

```jsonc
{
  "report_analysis": {
    "source_mode": "FULL_REPORT",
    "document_id": "<hash>",
    "metadata": { "title": "", "publisher": "", "author": "", "published_at": "",
      "company_or_sector": "", "report_type": "COMPANY | INDUSTRY | EVENT | EARNINGS | TARGET_REVISION" },
    "executive_thesis": "<리포트 핵심 주장 1~2문장>",
    "thesis_chain": [
      { "claim_id": "C1", "claim": "", "because": "<원인/메커니즘>",
        "implication": "<실적·밸류 의미>", "fact_refs": ["F1","F3"] } ],
    "facts": [
      { "fact_id": "F1", "text": "", "value": null, "unit": null,
        "source_page": 0, "source_section": "", "table_or_figure": "",
        "source_type": "TEXT | TABLE | CHART | FOOTNOTE",
        "confidence": "HIGH | MEDIUM | LOW" } ],
    "risks": [ { "text": "", "fact_refs": [] } ],
```

P2 이월: `chart_inventory` / `assumptions` / `candidate_angles` (각도 선정은 MVP에서 directive 생성 LLM이 겸무).

### 6-4. 분석 규칙

- 리포트의 결론 vs 모델의 해석 분리 / 수치의 기간·단위 보존 / 추정 vs 확정 구분 / YoY·QoQ·컨센서스比 혼용 금지.
- 차트에서 읽은 근사치: "근사치" 표시 + **핵심 근거(claim 유일 fact_ref)·훅 수치·화면 대형 숫자 사용 금지** (보조 맥락만).
- 페이지·표 근거 없는 주장 = `confidence=LOW` + 핵심 근거 사용 금지.
- 충돌 수치는 자동 선택 금지 → 충돌 상태로 승인 UI 노출.
- 원문에 없는 수혜주·피해주 확장 금지.

### 6-5. 비용·캐시

문서 해시 기준 report_analysis 캐시 / 한·영 동일 분석 사용 / 분석 승인 전 이미지·영상 생성 금지 / 차트 언어별 렌더 시 데이터·좌표 공유 + 텍스트 레이어만 분기.

## 7. 콘텐츠 깊이 계약

### 7-1. depth_core

```jsonc
{ "depth_core": {
    "question": "<훅이 만든 단 하나의 질문 — 한 문장으로 답할 만큼 구체적>",
    "why_viewer_cares": "",
    "answer_path": [ { "beat_id": "B1",
      "role": "CHANGE | WHY_NOW | MECHANISM | WINNER_LOSER | RISK | WATCHPOINT",
      "claim_id": "C1" } ],
    "answered_at_cut": 0 } }
```

"이 회사 전망은?" 류 광범위 질문 금지 / 모든 본문 컷은 answer_path 비트에 매핑 / **핵심 답은 마지막 15초 이전 완결** (면책에 묻히지 않게).

### 7-2. core_thesis

```jsonc
{ "core_thesis": { "statement": "", "source_relation": "REPORT_CLAIM | MODEL_SYNTHESIS",
    "claim_refs": ["C1"], "confidence": "HIGH | MEDIUM | LOW" } }
```

`MODEL_SYNTHESIS`(모델이 근거를 조합해 도출)인 경우 리포트의 직접 주장처럼 표현 금지 — 귀속 컴플라이언스의 스키마화.

### 7-3. insight_nuggets (≥2)

```jsonc
{ "insight_nuggets": [ { "text": "", "kind": "NUMBER | MECHANISM | UNEXPECTED_LINK",
    "fact_refs": ["F1"], "supports_beat": "B2", "so_what": "", "cut_index": 0 } ] }
```

판정 3축 (각 **pass/fail** — 점수 척도 금지): ① 제목만 보고 알 수 없는가 ② 인과·메커니즘이 있는가 ③ core_thesis에 기여하는가. 3축 전부 pass만 유효. 잡학·제목 재진술 = fail.

### 7-4. counter_case / watchpoint

```jsonc
{ "counter_case": { "statement": "<핵심 해석이 틀릴 조건>", "fact_refs": [], "severity": "LOW|MEDIUM|HIGH" },
  "watchpoint": { "metric_or_event": "", "why_it_matters": "", "source_relation": "REPORT | MODEL_SYNTHESIS" } }
```

반론 억지 삽입 금지. 단 **리포트가 명시한 핵심 리스크는 누락 금지.** watchpoint는 모든 영상 필수 (고정 엔딩).

### 7-5. hook_promise_check

검사: 훅 질문 = depth_core.question 동일 / 본문이 직접 답함 / 답이 모호한 전망 문장 아님 / 훅보다 약한 사실 나열 아님 / 마지막에 확인 지표 존재. **fail = 경고 배지로 시작** — 5편 운영 후 오탐률 <20% 확인 시 차단 승격.

## 17. 성과 측정

- **북극성 = stayed_to_watch 단일.** 보조: 길이 보정 평균 시청 시간 / 평균 조회율 / 깊이 QA 통과율(≥80%). 정성(댓글 "이해됐다")은 기록만. 조회수 = 후행 기록.
- 판정: 새 포맷 **8편 전체 중앙값** vs 기존 중앙값. 성공 = stayed +8%p AND 길이 보정 시청 시간 +25%.
- 유형별 분석 = 태깅·관찰만 (셀 판정 금지). 태그: `report_type / source_mode / hook_type / duration_band / board_mix / context_visual_style / generated_visual_count / core_question_type / published_at`.
- 길이대별 참고값(내부 운영용): 45~55초 조회율 60%+ / 56~65초 55%+ / 66~75초 50%+.
- 측정: PA0 가동 시 자동, 미가동 시 Studio 수동 주 1회.
- 베이스라인 후 A/B 순서 (한 번에 하나): ① 훅 유형 ② 길이 밴드 ③ 설명판 비율 ④ 결론 구조 ⑤ 코드 훅 vs 생성영상 훅(코드 훅 성과 확인 후에만 비용 실험).

## 20. 샘플 실증 피드백 렌더 규칙 (v3.2 · 동결 · 렌더러 하드 계약)

2026.07.30 LS일렉트릭 샘플 2회 검수 결과를 렌더 하드 규칙으로 승격한다. 참조 구현: `render2.py` (단 §20-3 레이아웃 그리드는 참조 구현보다 본 절이 우선 — 샘플은 하단 여백·배경 위치가 미달이었다).

### 20-1. version_type 배치 (포지셔닝)

```
version_type: "comic" | "image_sequence" | "animation" | "explainer"(신규)
```
- `explainer` = 본 문서의 설명판형. **기존 리포트 경로를 대체하지 않고 병렬 추가** — 리포트 공장의 버전 선택지 중 하나. 지시서 생성 시 리포트 채널 기본값 = `explainer`, 기존 경로는 비교군·폴백으로 보존.
- 논문 채널 버전 enum은 불변.

### 20-2. 배경 규칙 — "맨 배경 금지"

- **텍스트 중심 씬(REVEAL·BROKER_VIEW 등 차트 면적 < 화면 40%)은 단색 배경 금지.** 해당 소재의 실사 맥락 이미지를 딤 처리(밝기 0.40~0.50 + 네이비 오버레이 α 165~185)해 배경으로 깐다.
- 배경 이미지는 **씬 간 재사용** — 편당 이미지 캡 ≤2 안에서 배경·삽입 겸용 (신규 생성 아님).
- 차트·게이지 씬은 가독성 우선 — 그리드 단색 배경 유지 (배경 이미지 금지).
- 배경 위 텍스트는 전부 스트로크(2~4px) 필수.

### 20-3. 세로 레이아웃 그리드 (신설 · 전 씬 강제)

**문제:** 샘플에서 요소가 세로로 흩어지고, 출처·면책 바와 배경 이미지 피사체가 최하단에 배치돼 유튜브 UI(하단 버튼·설명·프로필)와 겹칠 위험 + 화면이 허전해 보였다.

**해결: 모든 씬은 아래 고정 밴드를 따른다 (1080×1920 기준).**

| 밴드 | y 범위 | 용도 | 규칙 |
|---|---|---|---|
| DEAD_TOP | 0 ~ 215 | 여백 | 어떤 요소도 배치 금지 |
| META | 216 ~ 330 | 킥커(좌) · 시리즈 배지(우) | 작은 텍스트만 |
| TITLE | 331 ~ 500 | 보드 제목 (최대 2줄) | |
| **CORE** | **501 ~ 1180** | **차트·대형 숫자·게이지·리빌 타이포 = 화면의 주인공** | 이 밴드를 **최소 70% 이상 채운다**(빈 공간 방치 금지). 시각적 무게중심은 y ≈ 840 |
| SOWHAT | 1181 ~ 1290 | so_what 한 줄 · 보조 캡션 | |
| CAPTION | 1291 ~ 1400 | 나레이션 자막 (앵커 y ≈ 1300) | 최대 2줄 |
| SOURCE | 1401 ~ 1500 | **출처 + 면책 고정 바** | 반투명 바. **화면 최하단 배치 금지 — 반드시 이 밴드로 상향** |
| DEAD_BOTTOM | 1501 ~ 1920 | 유튜브/틱톡 UI 점유 구역 | **어떤 정보도 배치 금지.** 배경 이미지 연장·그라디언트만 허용 |

- 가로: 콘텐츠 x **90 ~ 930**. 930 초과 금지(쇼츠 우측 버튼 스택).
- **밀도 원칙:** 밴드 사이 임의 공백 삽입 금지. CORE가 비면 요소를 키우거나(폰트·차트 스케일 업) 배경 이미지로 채운다 — 세로로 흩뿌려 여백을 만들지 않는다. 목표는 "중앙에 밀도 있게 모인 꽉 찬 화면".
- 면책 카드(엔딩)는 SOURCE 밴드 위(≈ y 1180~1400)에 배치하고, 그 컷에서는 자막을 CORE 하단으로 올린다.

### 20-4. 배경 이미지 프레이밍 (신설)

- 배경 이미지의 **피사체 무게중심을 y ≈ 840(CORE 중앙)에 맞춘다.** 하단 배치 금지 — DEAD_BOTTOM에 피사체가 놓이면 UI에 가려지고 화면이 비어 보인다.
- 구현: 이미지를 화면에 맞춰 커버 크롭할 때 **크롭 앵커를 중앙~상단 40% 지점**으로 잡는다(단순 center-crop 시 피사체가 내려앉는 사례 실측).
- 생성 프롬프트도 이에 맞춰 조정: 여백 확보 지시를 "upper third"가 아니라 **"피사체는 프레임 중앙, 상·하단에 오버레이용 어두운 여백"**으로 (부록 A 갱신 반영).
- DEAD_BOTTOM 구간은 배경을 아래로 갈수록 어둡게 감쇠(그라디언트)시켜 UI와 자연스럽게 섞는다.

### 20-5. 자막 하이라이트 — 2어절 윈도우

- **하이라이트 단위 = 발화 중 어절 + 직전 어절, 총 2어절(또는 2단어).** 1개 단위는 전환이 너무 빨라 시선이 따라가지 못한다(실측 결함).
- 판정: 현재 활성 인덱스 `i`에 대해 `{i-1, i}`를 하이라이트. 청크 첫 어절이면 `{i, i+1}`(선행 표시)로 대체해 항상 2개를 유지.
- 하이라이트 잔류: 어절 종료 후 `+0.12s` 유지 후 흰색 복귀.
- 키워드 고정 하이라이트(청크 내 특정 단어 상시 옐로) **금지** — 활성 어절과 이중 표시되어 혼란 유발. 규격서 v2의 "핵심어 1개 하이라이트"는 이 활성 윈도우 규칙으로 충족한다.

### 20-6. 발화 페이스

- 체감 페이스 목표 = 기존 TTS(+20%) 대비 **1.2배.** 구현은 후처리 배속이 아니라 **TTS rate 상향(+40% 부근)으로 원천 적용** 후 실측 보정 — 워드 타임스탬프·컷 길이가 실발화 기준으로 산출되어야 자막 싱크가 유지된다. (샘플은 프로토타입 한정 전역 1.2x 후처리 — **프로덕션 금지.** C안 setpts 금지 원칙과 정합.)
- rate 상향 후 자막 청크는 규격서 v2 §1.2 Fallback 트리로 재보정(빠른 발화 → 어절 수 축소). 2어절 하이라이트 윈도우와 함께 가독 실측 필요.

### 20-7. 렌더 QA 추가 검사 (§14에 append)

- **밴드 위반**: DEAD_TOP·DEAD_BOTTOM에 텍스트/차트 픽셀 존재 → fail (알파 마스크로 판정).
- **x 930 초과** 요소 존재 → fail.
- **CORE 밀도**: CORE 밴드의 비배경 픽셀 비율 < 30% → warn(허전한 화면 감지).
- **출처 바 위치**: SOURCE 밴드(1401~1500) 밖이면 fail.

## 21. 구현 킬 스위치 (v3.3 신설 · 최우선 · 기계 판정)

**신설 사유:** 2026.07.30 기존 파이프라인 실출력(MS/Azure 편, 편당 $0.556) 검수에서 다음이 실측됐다 — ① AI 생성 이미지가 가짜 대시보드·가짜 수치(27.5%, 63.5% 등 근거 없는 픽셀)를 화면에 표시 ② 4:5 자산을 9:16에 페이스트해 화면의 30~40%가 검은 레터박스 ③ 나레이션 수치("43%")가 화면에 부재, 추상 화살표로 대체 ④ 밴드 그리드 미적용 ⑤ $0이어야 할 차트를 유료 생성.

**진단:** 산문 규칙("코드 렌더 중심", "장식 금지")은 구현체를 구속하지 못한다. 아래 규칙은 **전부 이진 판정이며, 위반 시 렌더 차단(fail)**이다. 경고 아님.

### K1. 숫자 픽셀 출처 규칙 (최상위)

> **화면에 표시되는 모든 숫자·수치·차트·그래프·축·범례는 코드 렌더로만 생성한다. 생성 이미지·생성 영상 자산이 숫자나 차트를 포함하면 즉시 fail.**

- 판정: `asset_type ∈ {generated_image, generated_video}` 인 컷의 `on_screen_text`에 숫자 포함 → fail. 생성 자산에는 프롬프트 단계에서 `no text, no numbers, no charts, no graphs, no dashboards, no UI` 네거티브 강제(부록 A 확장).
- 승인 UI에 생성 자산 썸네일 표시 + "이 이미지에 숫자·차트가 보이면 반려" 체크박스 필수.
- 근거: 가짜 수치는 시청자에게 리포트 데이터로 읽힌다. 품질 문제가 아니라 **컴플라이언스 사고**다. C안 fact_ref 철학(LLM 수치 재복사 금지)의 시각 버전.

### K2. 생성 자산 금지 컷 유형

`HOOK / NUMBER_BOARD / CHART_BOARD / EVIDENCE_BOARD / WATCHPOINT_BOARD` = **생성 자산 사용 절대 금지**(코드 렌더 전용). 생성 이미지는 `CONTEXT_IMAGE` 역할 컷의 **배경**으로만 허용하며, 그 위 정보는 전부 코드 레이어여야 한다. (하루한편 B1 명세의 COMPARE/SCALE/EVIDENCE 하드 차단 게이트와 동일 원리 — 리포트 경로에 이식.)

### K3. 프레임 충전 규칙 (레터박스 금지)

- 모든 자산은 **9:16 커버 크롭**으로 조립한다. 페이스트/레터박스/필러바 **금지**.
- 판정: 최종 프레임의 상·하단 각 200px 밴드에서 **단색 검정(휘도 < 8) 픽셀 비율 > 90%** → fail.
- 자산 원본이 9:16이 아니면 §20-4 크롭 앵커(중앙~상단 40%)로 커버 크롭. 크롭 후 피사체 소실 시 해당 자산 폐기·재생성.

### K4. 나레이션-화면 수치 일치

- 나레이션이 특정 수치를 발화하는 컷은 **그 수치가 화면에 코드 렌더로 존재**해야 한다.
- 판정: `narration`에서 숫자 추출 → 해당 컷 `on_screen_text` 또는 차트 데이터에 동일 값 부재 → fail.
- 목적: "43%를 말하는데 화면엔 화살표만" 같은 정보 공백 차단.

### K5. 비용 상한 하드 캡

- **편당 생성비 상한 $0.25** (실사 맥락 이미지 ≤2장 + LLM). 초과 시 렌더 중단·사용자 보고.
- Veo/영상 생성은 **기본 OFF.** 코드 훅의 stayed_to_watch 성과 확인 후 A/B로만 켠다(§17).
- `generation_attempts` 원장에 컷별 `asset_type`·단가·누적액 기록. 승인 UI에 예상 비용 사전 표시.
- 참고 실측: 코드 렌더 100% 샘플의 시각 직접비 = **$0** (LS일렉트릭 39초). 차트를 생성으로 만드는 것은 **비용을 늘리면서 정확도를 잃는** 순손실이다.

### K6. 버전 라우팅 검증

- 렌더 산출물 메타에 `version_type` 기록 + 승인 UI 표시. `explainer` 경로 산출물에 시리즈 타이틀이 **"하루 리포트 하나"**가 아니면 fail (구 템플릿 혼입 탐지).
- Phase 5 개선판 1편은 반드시 `version_type="explainer"`로 렌더됐음을 메타로 확인한 뒤 발행.

### K7. Phase 0 추가 태스크 (P0-5)

## 22. 시각 구현 계약 — 실행 가능 규범 (v3.4 신설 · 렌더러 필수 의존)

**신설 사유:** 2026.07.30 구현체 실출력 검수에서, 명세를 산문으로 전달한 결과 다음이 실측됐다 — ① 지정 폰트 미로딩 → 모노스페이스 폴백으로 렌더(미학 전면 붕괴) ② 절대좌표 밴드가 다른 해상도에서 무효화 → 상단 편중·하단 공백 ③ 자막을 `"…"`로 절단(정보 소실) ④ 제목과 인용 박스가 동일 문장 반복 ⑤ 차트에 축·기준선·단위·so_what 부재, 막대가 거대 사각형 ⑥ 우측 프레임 블리드.

**진단:** 시각 품질은 산문으로 전달되지 않는다. 좌표·폰트·검증은 **코드로 넘겨야** 한다.

### 22-1. 규범 모듈

`visual_contract.py`를 저장소에 포함하고, explainer 렌더러는 **반드시 이 모듈을 import해 사용**한다. 좌표·폰트·검증 로직의 자체 재구현 금지. 본 절과 산문 절(§20 등)이 충돌하면 **모듈 코드가 우선**한다.

제공 API:
- `BANDS` / `y_of(band, pos)` / `x_bounds()` — **비율 기반** 밴드 그리드 (해상도 독립. §20-3의 절대 픽셀 표기는 1080×1920 참고값으로 격하)
- `load_font(role, size)` / `preflight_fonts()` — 폰트 계약
- `fit_text()` / `wrap_by_width()` / `assert_no_duplicate_text()` — 텍스트 규칙
- `highlight_indices()` / `chunk_words()` — 자막 2어절 윈도우
- `CHART_MIN` / `validate_chart_spec()` — 차트 최소 요건
- `validate_frame()` — 프레임 QA (fail/warn 반환)
- `smoke_test()` — 착수 전 1회 통과 필수

### 22-2. K8 — 폰트 폴백 금지 (하드)

- 지정 폰트 파일 부재 시 **렌더를 중단**한다. 기본 폰트·시스템 폰트로 대체 렌더 금지.
- 파이프라인 시작 시 `preflight_fonts()` 호출 의무. 실패 시 잡을 시작조차 하지 않는다.
- 폰트 자산은 저장소 또는 배포 이미지에 동봉(`EXPLAINER_FONT_DIR`). "로컬에선 되는데 서버에선 폴백" 방지.
- 숫자 폰트 라이선스 미확정 시(§19 열린항목 4) 대체 폰트를 **명시적으로 지정**하고 기록 — 침묵 폴백 금지.

### 22-3. K9 — 말줄임 금지 (하드)

- 화면 텍스트에 `…` / `...` / 문자열 슬라이싱 절단 **금지**. 초과 시 `fit_text()`로 폰트를 줄이고 줄바꿈한다.
- 최소 크기에서도 2줄에 안 들어가면 **렌더가 아니라 대본을 고친다**(예외 발생 → 지시서 반려). 자막 최소 크기 권장 44px(가독 하한) — 그 아래로 줄여 맞추지 말 것.

### 22-4. K10 — 화면 텍스트 중복 금지 (하드)

- 같은 프레임의 제목 / 본문 / 인용 박스 / 자막이 동일하거나 포함 관계인 문장을 반복하면 fail (`assert_no_duplicate_text`).
- 원칙 재확인: **차트가 숫자를 보이면 자막은 의미를 말한다.** 같은 말을 두 번 쓰지 않는다.

### 22-5. K11 — 차트 최소 요건 (하드)

모든 `CHART_BOARD`는 다음을 갖춘다: 기준선/축 · 계열별 값 라벨 · 단위 표기 · so_what 한 줄 · 출처(+페이지). 계열 ≤3, 막대 폭 ≤ 화면폭 22%(거대 사각형 금지), 앰버 강조는 1개 계열만. `validate_chart_spec()` 통과 필수.

### 22-6. 렌더 QA 배선

`report_render.process_job`은 컷 프레임 샘플(최소: 각 씬 중간 프레임)에 `validate_frame()`을 실행하고, `fail`이 하나라도 있으면 **잡을 실패 처리**한다. `warn`은 승인 UI 배지로 노출. 결과는 `report_render_jobs.qa`에 저장.

### 22-7. 착수 순서 (Phase 3 선행 조건)

1. 폰트 자산 배치 → `preflight_fonts()` 통과
2. `visual_contract.smoke_test()` 통과
3. 보드 4종을 **모듈 API만 사용해** 구현 → 각 보드 정지 프레임에 `validate_frame()` fail 0 확인
4. 그 다음에야 모션·TTS 동기화 진행

> 참조 구현 `render2.py`는 미학 방향의 예시이며, **좌표·검증의 규범은 `visual_contract.py`**다. 둘이 다르면 후자를 따른다.
