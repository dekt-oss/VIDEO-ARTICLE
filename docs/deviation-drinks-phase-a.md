## 검토 보완 A — 제작안의 근거 전달

- **사실 항목 / 비사실 항목** — 카드: 설명·비교·체크리스트 = 사실, 표지·출처 = 비사실. 영상: 장면마다 `content_kind`(fact 기본 / transition = 도입·전환·마무리).
- **형식별 필수 주장** — 기획(brief)에 `required_claims: {video: [...], carousel: [...]}`. 제안한 형식마다 비어 있으면 근거 버전 승인을 막는다(`required_claims_missing`). 근거 버전과 함께 승인되어 고정되므로 제작안 단계에서 필수 주장을 빼는 우회가 없다. 두 형식에 같은 목록을 강요하지 않는다(화면은 핵심 주장 전체로 미리 채우고 형식별로 줄일 수 있다).
- **검사 위치** — `drinks_plan_coverage`. 저장은 허용하고 결과를 돌려준다(작성 중). **검토 요청·승인**은 RPC 와 제작안 트리거가 모두 막는다(`plan_coverage`). 모르는 주장 id 는 `plan_claim_unknown`, 핵심이 아닌 주장은 `plan_claim_not_core`, 다른 소재의 근거 버전은 `ownership`.
- **경계** — 주장이 연결됐다는 것은 "근거 범위 안에서 말한다"는 표시일 뿐이다. 문장이 주장과 맞는지는 사람이 검토한다(화면에 그대로 적었다). 제작안 승인 때 근거 필수 조건(유효 기한·사용 조건 등)도 다시 잰다.

## 검토 보완 B — 출처 정보 정정·재확인

- **구조 선택** — 스냅샷(원문 + 등록 당시 정보)은 그대로 불변. 그 위에 추가만 되는 `drink_snapshot_attestations` 를 쌓는다. 종류: `rights_confirmed`(사용 조건 확인) · `recheck`(원문 재확인, 변경 없음) · `correction`(제목·발행처·발행일 등 정정, 사유 필수) · `rights_revoked`(사용 불가·미확인으로, 사유 필수). 종류마다 바꿀 수 있는 칸을 DB 가 제한한다(정정으로 권리를 바꾸지 못한다).
  - 버린 대안: 스냅샷 행 수정(원문 불변·승인 근거 추적이 깨진다), 정정마다 새 스냅샷(같은 원문이 여러 버전으로 보여 "본문 변경"과 섞인다).
- **유효 정보** — `drinks_snapshot_meta` = 스냅샷 값 위에 기록을 시간순으로 덮은 값. 근거 필수 조건은 이 유효 사용 조건으로 판정한다. 근거 승인 때 `readiness.source_state` 에 그 시점의 사용 조건·마지막 기록 id 를 남긴다.
- **재등록** — 같은 URL·같은 본문을 다시 넣으면 스냅샷은 재사용하고, 입력이 유효 정보와 다른 칸을 `metadata_diff` 로 돌려준다. 자동 적용하지 않고 화면이 "정정·확인 기록으로 남기세요"라고 안내한다.
- **영향** — 모든 기록은 그 시점의 영향 범위(이 출처를 쓰는 소재, 그 출처를 근거로 쓰는 철회 안 된 승인, 그 승인을 쓰는 제작안)를 함께 저장하고 돌려준다. 권리 철회는 `revoke_affected=true` 이면 핵심 근거로 쓴 승인을 같은 트랜잭션에서 철회하고 제작안을 차단한다. 철회하지 않아도 이후 편성·제작안 승인은 유효 사용 조건으로 다시 검사해 막힌다. **과거 승인 본문은 바뀌지 않는다.**

## 검토 보완 C — 조회 잘림과 누락

## 추가 검토 재현 결함 2건 (2026-10-22)

### 결함 1 — 비사실 항목으로 필수 주장 전달 검사 통과

- **이전:** 필수 주장 충족을 모든 항목의 `claim_ids` 합으로 셌다 → 표지·출처만 있는 카드(표지에 필수 주장), 전환 장면만 있는 영상이 `coverage.ok=true` 로 검토 요청·승인까지 통과.
- **이후:** 필수 주장 "전달"은 **사실 항목**(카드 설명·비교·체크리스트, 영상 `content_kind=fact`)에 연결된 주장으로만 센다. 비사실 항목의 주장은 `reference_only`(참고 연결)로 따로 보여주고 전달로 치지 않는다. SQL `drinks_plan_coverage`(RPC·트리거 공용)와 TS `planCoverage`(화면) 규칙이 같고 PGlite 테스트가 일치를 대조한다. 저장은 미완성 초안으로 허용, 검토 요청·승인은 막는다. 문장과 근거의 의미 일치는 계속 사람이 본다.

### 결함 2 — 권리 철회 뒤에도 "지금 사용 가능"으로 남음

- **이전:** `revoke_affected=false` 면 기록만 남고 소재는 `selected`, 근거·제작안은 `approved`·미차단, 화면도 승인 상태만 보고 사용 가능으로 표시.
- **이후 — 승인 기록과 현재 사용 가능을 나눈다:**
  - **판정 뷰** `drink_review_validity`(읽기 전용, security_invoker): 승인 버전마다 지금의 차단 사유(`current_blockers`)·사용 가능(`currently_valid`). 정정 기록과 유효 기한이 반영되고 저장하지 않으므로 과거 승인 스냅샷을 덮어쓰지 않는다. 화면(선별·편성함·작업함·제작·기획·제작안 탭)과 서버 판정(`drinks_approval_valid`)이 같은 `drinks_review_blockers` 를 쓴다.
  - **정정 기록 뒤 실제로 깨진 승인**(기록 전엔 통과, 기록 뒤 차단)만 고른다. 체크박스와 무관하게 그 승인을 쓴 제작안을 `evidence_invalid` 로 차단하고 소재 상태를 맞춘다(`drinks_settle_topic`). '함께 철회'를 고르면 승인 자체도 철회(`evidence_revoked`). 승인 본문·해시·승인 당시 `source_state`·제작안 승인 기록은 그대로다.
  - **상태 맞춤:** 편성에 쓴 버전이 지금 무효 → 더 최근 유효 승인이 있으면 편성 가능, 없으면 조사 중. 편성 가능인데 승인이 무효 → 조사 중. 재확인으로 최근 승인이 다시 유효해지면 조사 중 → 편성 가능. 차단된 제작안은 **자동 부활하지 않는다** — 새 제작안 버전으로 다시 검토.
  - 다른 사용 가능한 근거가 남은 승인·제작안은 건드리지 않는다. 공유 출처는 소재마다 영향 판정, 이력은 각 소재에 남는다.
  - 기간 만료처럼 사건 없이 생기는 무효는 저장된 차단이 아니라 판정 뷰·서버 재검사로 막힌다(화면은 "근거 재확인", 제작 화면은 조치 필요). 자동 일괄 차단은 주기 실행이 필요해 A단계 범위 밖이다.
