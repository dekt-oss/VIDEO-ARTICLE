> **상태: 초안(코덱스 리뷰 반영판). 사장님 검토 전. 구현 시작 전.**

## 0. 한 줄 결론과 v1 에서 바뀐 것

**방향은 유지한다 — 홈 = 오늘 할 일 하나 · 소재 = 고르는 곳 하나 · 작업공간 = 소재 하나의 형식별 레인.**
v1 은 화면 통합과 **실행 계약 변경**을 섞어 썼다. "승인이 곧 결재", "승인 뒤 자동 제작", "버튼은 셋"은 지금 코드와 다르고 안전장치를 건너뛴 설명이었다. v2 는:

1. **실행·결재 경계를 지금 그대로 둔다**(기본안). 내용 승인 → 결재 열기 → 구매 요청 → 검수 → 게시 승인 → 예약은 각각 사람이 누르는 서버 전이이고, 화면은 그 순서를 **한 자리에서 차례로 안내**한다. "한 번 확인으로 통합 실행"은 별도 범위(§12 결정 1)로 뺀다.
2. 진단 중 코드와 다르던 넷을 정정했다(§2-3).
3. 다음 행동 결정을 **네 계층**으로 다시 짰다(§7). 차단 조건이 승인·제작 버튼보다 먼저다.
4. 설명형 필수 검수(후보 판정·선택 사유·과정 검수·품질 검수·산출물 검수)를 모두 복원했다(§6-3).
5. 밈은 **카드 기반·소재 기반 두 경로가 이미 있다**는 사실 위에서 연결 계약을 명세했다(§9-3). 데이터 소유자 일괄 변경은 기본안에서 뺐다.
6. 상태표를 DB 어휘 전부로 채웠다(§8). 알 수 없는 상태는 "확인 필요"로 가고 초안 생성으로 떨어지지 않는다.
7. 단계를 P0~P3 으로 다시 나누고, 옛 주소 넘기기는 **목적지가 완성된 뒤**로 미뤘다(§11).

## 2. 현행 사실 — 코드 기준

### 2-1. 화면과 데이터 (유지되는 진단)

- 메뉴는 6묶음·14화면(`web/lib/nav.ts` `GROUPS_DRINKS`): 선별(`/drinks`) · 수집 ▾(소재 발견 `/discover`·커뮤니티 동향·밈 보드 `/memes`·수집 문서·수집원·실행 기록) · 작업함 `/review` · 제작 `/production` · 발행·성과 ▾ · 설정.
- **후보는 `/drinks/discover` 에만 보이고 첫 메뉴 `/drinks` 는 소재(topic) 목록이다.** 후보 조회는 `DISCOVERY_LIMIT = 300` 으로 잘리고(`web/lib/drinks/discoveryQueries.ts`), 후보별 근거 수 집계는 상위 50건(`EVIDENCE_MAX_CANDIDATES = 50`, `web/lib/drinks/formatRecommend.ts`)만 요청한다. 그 밖의 후보는 근거 수가 "모름"이지 "0건"이 아니다.
- 모든 쓰기는 `POST /api/drinks` → `runDrinksAction` 허용 목록(`web/lib/drinks/actions.ts`) → `drinks_*` RPC 하나다. 상태 검사는 전부 DB 가 한다.
- 워커 깨우기(`web/app/api/drinks/route.ts`): `pick_topic`(이어 만들기가 새로 큐에 들어갈 때)·`request_develop` → 개발 워커, `request_render`·`explainer_request_plan`·`explainer_request_assemble` → 제작 워커, `meme_draft_action(approve)` → 밈 워커, `ig_card_use_refine(queued)` → Apify 워커. **`approve_content` 와 `explainer_request_buy` 는 어떤 워커도 깨우지 않는다.** 토큰(`GITHUB_DISPATCH_TOKEN`)이 없으면 큐에만 남는다.
- 운영 DB 스냅샷(2026-11-04, 미검증·완료 기준 아님): 후보 suggested 530 · dismissed 68 · promoted 3, 소재 selected 3 · researching 1, 밈 카드 0(관찰 계정 10, 트렌드 수집 ok 3·빈 결과 6), 음원 412, 게시됨 1.

## 3. 목표 동작 — 유지하는 뼈대

```
[홈 /drinks]            오늘 할 일 한 장(§7-4 우선순위) + 타일 + 이번 주 형식별 진행표
      │
[소재 /drinks/topics]   후보·내 소재·밈 카드를 한 화면에서 ── [이걸로 + 형식] ──▶ 큐 등록(개발 워커가 근거→대본 초안)
      │
[작업공간 /drinks/work/<topicId>]   결정 바 하나 + 형식별 레인
      설명형: 내용 승인 → 결재 열기 → 구매 요청 → 후보 판정·선택 → 조립 → 과정·품질·산출물 검수 → 발행안 → 게시 승인 → 예약
      카드:   내용 승인 → 제작 시작 → 산출물 검수 → 발행안(음원 필수) → 게시 승인 → 예약
      밈:     글 초안 → 승인 → 렌더 → (게시 대기) 발행안 → 게시 승인 → 예약  /  (박자 밈) 앱에서 부착·게시 → URL 기록
      │
[발행·성과]             예약 큐·계정 / 성과·전략
```

- **주요 진입점은 셋이다 — 소재 선택·내용 승인·게시 승인.** 형식별 필수 검수와 수동 작업은 작업공간 안에서 순차 안내한다. "버튼은 셋뿐"이 아니다.
- 사람이 누르는 모든 전이는 **지금 서버 RPC 그대로**다. 화면은 순서와 이유를 보여 주고, 막는 것은 DB 다.
- 모든 형식이 웹 안에서 자동 예약·게시되지 않는다. 박자 밈은 수동 레인이다.

### 4-1. 기본안(이번 범위): 현행 경계 유지 + 순차 안내

### 4-2. 별도 범위(미결정, §12 결정 1): 한 번 확인으로 통합 실행

"[승인] 한 번으로 결재 열기 + 구매 요청 + 워커 깨우기"를 하려면 **새 서버 계약**이 필요하다. 이번 UI 개편에 넣지 않는다. 넣는다면 다음을 먼저 정해야 한다:
승인 대상 버전(근거·제작안·지시서 해시) · 금액 상한과 허용 종류 · 허용 작업 목록 · 재시도 규칙 · 중복 클릭·동시 요청 방지 · 중간 실패(결재는 열렸는데 큐 등록 실패 등) 복구 · 감사 기록(누가 어떤 말로 승인했나).

### 4-3. 차단과 경고 — 서버 규칙을 그대로 따른다

| 조건 | 서버 | 화면 |
|---|---|---|
| 근거 철회·사용 조건 만료(`drink_review_validity`·`drink_output_validity`) | 승인·제작·게시 **차단**(`output_not_usable`·`blocked_at`) | **차단** 표시 + 복구 경로(새 근거 버전) |
| 승인 지문 불일치(`digest_mismatch`·`digest_changed`·`meme_digest_changed`) | **차단** | 차단 + "새로 불러와 다시 승인" |
| 카드 릴스 음원 없음 | submit 때 `audio_required` **차단** | 발행안 폼에서 필수 표시, 없으면 [승인 요청] 비활성 |
| 설명형·산 장면 밈 캡션에 'AI 생성 영상' 없음 | submit·게시 **차단**(`ai_label_missing`) | 차단 |
| 예약 시각 창 밖(KST 07:00~23:30, 0071) | submit·schedule **차단**(`outside_publish_window`) | 폼 경고 + 서버 차단 |
| 예약 2시간 초과 | schedule `too_late` 차단, claim 때 paused | 차단 + 새 시각 안내 |
| Apify 월 상한·실행 상한 임박 | 요청 때 `apify_budget_exhausted` 차단 | **정보성 경고**(임박) → 차단(소진) |
| 결재 잔액 < 다음 구매 예상 | `budget_exceeded` 차단(구매 때) | 정보성 경고(사전) |
| 밈 근거 철회(정보 밈) | 0071 `drinks_pub_meme_block` 차단 | 차단 |

"정보성 경고"는 아직 서버가 막지 않지만 곧 막힐 것을 미리 알리는 것이고, "차단"은 서버가 거부하는 것이다. 화면이 차단을 경고로 낮추지 않는다.

## 6. 화면 명세

### 6-1. 홈 `/drinks` — "오늘"

1. **다음 작업 카드 하나**: §7-4 우선순위로 고른 작업. 소재 제목·형식 칩·막힌 이유 한 줄·버튼 하나(작업공간의 해당 패널로).
   - 같은 문제가 홈을 영구 점유하지 않게: 카드에 **[확인했음 — 나중에]**(그 작업을 N시간 뒤로 미룸, 화면 상태만·실행 차단 해제 아님)와 **[다른 작업 보기]**. "확인된 문제"는 다음 작업 선정에서 뒤로 가고, **새로 생긴 문제**는 다시 맨 앞에 온다.
2. **타일 3**: [고를 후보 N(표시 범위/전체)] → 소재 · [승인·검수 기다리는 것 N] → 작업함 filter=approve · [게시·확인 필요 N] → 작업함 filter=publish.
3. **이번 주 진행표**: 형식 3줄(목표 §7 결정 3: 설명형 1~2 · 카드 5 · 밈 3). 칸: 고름 / 승인 / 제작 / 게시(웹) / 수동 게시(밈). 목표 미달 형식은 "소재 고르기" 링크.
4. **수집 건강 + 막힘**: 지금 `loadRunHealth` 그대로 + 토큰 만료 임박·결재 소진·크론 꺼짐·고아 가잡기(0071 `drinks_spend_orphan_holds`) 수.
5. 빈 상태: 후보 0·소재 0·전부 완료 각각 문구.

### 6-2. 소재 `/drinks/topics` — "고르는 곳"

- **탭:** 후보(기본) / 내 소재 / 밈 카드 / 보류·제외. 형식 칩(전체·설명형·카드·밈)·주종·기간 필터는 **서버 쿼리 조건**이다(화면 안 300건만 거르는 것이 아니다).
- **머리 숫자:** 전체 N · 표시 M(페이지) · 지금 고를 수 있음 K. 조회 실패 / 부분 조회(일부 페이지 실패) / 수집 미실행 / 정상 0건을 글로 가른다.
- **페이지네이션:** 서버 `range` 페이징(기존 `chunked.ts` 규약). 근거 수 집계는 **보이는 페이지의 후보만** 요청하고(`drinks_candidate_evidence_counts`), 집계 전·집계 실패는 "모름"으로 표시한다(0건과 다르다).
- **후보 카드:** 질문 · 추천 형식 칩 + 이유(`formatRecommend`, "모름"은 모름으로) · 근거 수(모름/0/N) · 신호 · 중복 경고(`duplicate_topic_ids`) · **고를 수 있는가**: 가능 / 막힘(예산 없음·중복·이미 승격됨·점수 미달) 사유.
- **[이걸로 ▾]:** 모달 — 형식(추천값 기본, 바꾸면 이유 한 줄 선택) · 주차 · 예산(없으면 [예산 열기] 링크) → `pick_topic`. 결과를 넷으로 가른다: **큐 등록 + 워커 깨움** / **큐 등록(토큰 없음 — 다음 크론)** / **이미 있음(기존 작업공간으로)** / **실패(사유)**. 성공하면 그 소재 작업공간 링크. 중복 클릭은 요청 중 버튼 잠금 + 서버의 `existing` 응답으로 막는다.
- **밈 카드 탭:** `drink_ig_board_cards`. 상단에 지금 `/memes` 의 상태 안내(정상 관측일·관찰 계정 0개·토큰) 그대로. 카드 버튼 **[쓰자 ▾]**: 정밀화 여부를 고른다 — [쓰자(정밀화 포함, Apify $0.02)] = `ig_card_use_refine`(현행), [쓰자(정밀화 없이)] = `ig_card_decide(use)`. **소재 연결은 §9-3 결정 전까지 하지 않는다**; 카드 밈 제작은 지금처럼 밈 제작안(카드 소유)으로 가고, 작업함·작업공간이 카드 밈을 함께 보여 준다(§9-1).
- **내 소재 탭:** 진행 중 소재 + 카드 밈 제작안(작업 단위, §9-1)을 형식 칩·단계 칩·다음 행동과 함께. 클릭 → 작업공간.
- 손으로 넣기(`RegisterForm`·`add_discovery`·`ig_manual_card`·`ig_add_link`)는 탭 위 접힌 영역.

### 6-3. 작업공간 `/drinks/work/[topicId]` — "만들기"

**공통 뼈대**
- **결정 바(sticky)** 가 전역 주 행동을 **하나만** 소유한다(§7). 왼쪽: 형식 칩·단계 칩·차단/경고. 오른쪽: 주 버튼 + ▾ 메뉴(보류·되돌리기·이력).
- **레인 본문**: 형식마다 단계 섹션이 위에서 아래로. 각 섹션은 현재 단계면 펼쳐지고 아니면 접힌다. 주 버튼이 가리키는 섹션은 **자동으로 펼쳐지고 포커스가 간다**.
- **국소 판단은 콘텐츠 옆에**: 후보별 [합격]/[불합격], 체크리스트 항목, 페이지 미리보기. 결정 바와 **같은 버튼을 두 곳에 두지 않는다**(기존 폼의 동일 버튼은 제거하거나 결정 바가 그 폼의 submit 을 호출한다).

**밈 레인(소재 기반·카드 기반 공통)**: 글 초안(`text_requested`→`text_running`→`draft`; 글 요청은 결재 안에서만) → 차단 사유(`drinks_meme_blockers`: 안전·길이·근거) → [승인] → 렌더 → 분기:
- `publish_waiting` → 발행안 → 승인 요청 → 승인 → 예약 → 게시(웹 레인).
- `manual_audio`(박자 밈) → **수동 레인**: [앱에서 붙이기 안내] → 운영자가 앱에서 게시 → [게시했음 + URL](`meme_draft_action(manual_posted)`) → `posted_manual`. 성과 수집 대상 여부는 §12 결정 2 에 따른다.
- `stopped`(근거 철회·지문 변경) → 사유 + [제작안 다시 열기] → 재승인.

### 6-4. 발행 `/drinks/publish` — 큐·계정
발행안 폼은 작업공간으로 간다. 남는 것: 이번 주 예약 달력(07:00~23:30 칸), 요청 탭(확인 필요·작성·승인 대기·예약·게시 중·게시됨·취소), 계정 상태·발행 스위치, 수동 게시된 밈 목록(URL). 각 행은 소재 작업공간 링크.

### 6-5. 자료·설정 `/drinks/data`
기능 그대로, 탭으로 묶는다. 트렌드 수집 상태(정상 관측일·관찰 계정·음원·토큰·Apify 월 상태)는 여기와 소재 화면 밈 카드 탭 상단 둘 다에 보인다(같은 컴포넌트).

## 7. 다음 행동 결정 — 네 계층

순수 함수 `web/lib/drinks/work/decision.ts`. 입력은 §9-1 `drink_work_items` 한 행(+ 설명형이면 `drinks_explainer_status`). 출력은 `{ target, lane, version, blocks[], primary, warnings[] }`. `decision.test.ts` 가 모든 줄과 형식 분기를 고정한다.

### 7-1. 1계층 — 대상·형식·버전 식별
- 작업 단위 = (소재 또는 카드 밈) × 형식. 한 소재에 형식이 둘이면 작업 단위 둘(§9-1).
- "현재 버전" = 제작안은 `drink_deliverables.current_revision_id`, 설명형은 `drink_explainer_episodes`(plan_revision 당 1), 제작 작업은 가장 최근 `created_at`, 게시 요청은 끝나지 않은 것(`published`·`canceled` 아님) 중 최근 1 → 없으면 가장 최근 끝난 것.
- 식별 실패(형식 의도 없음·제작안 형식 불일치·소유자 없음) → `primary = needs_review("확인 필요: 사유")`. **초안 생성으로 떨어지지 않는다.**

### 7-2. 2계층 — 차단 조건 (주 버튼보다 먼저, **그 작업 단위에만** 적용)

## 9. 데이터·권한·버전·승인 계약

### 9-1. 조회 뷰 `drink_work_items` (0072, 뷰)
- **행 단위 = 작업 단위** = (소재 × 형식 의도) **또는** (카드 소유 밈 제작안). 소재 1행이 아니다 — 한 소재에 형식이 둘이면 2행. 카드 밈은 `topic_id null, card_id, meme_draft_id` 행으로 들어와 **누락되지 않는다**.
- **JOIN 증식 방지**: 제작안·제작 작업·게시 요청·설명형 에피소드·밈 제작안은 각각 **"현재 1건"을 LATERAL 서브쿼리로 고른다**(§7-1 규칙). 과거 버전·실패 이력은 뷰에 넣지 않고 작업공간 이력 패널이 따로 읽는다. 행 수 = 작업 단위 수를 시험이 단언한다.
- 재제작·재게시: "현재" 선정 규칙이 새 것을 가리키고, 이전 것은 이력으로. 뷰에 `prior_failed_count` 정도만 둔다.
- 권한: `security_invoker`, anon/authenticated 접근 없음, service_role 만(0050 방향). 라우트는 service key 로 읽는다.
- 되돌리기: `drop view`. **단, §9-3 의 쓰기 RPC 가 0072 에 함께 들어가면 "뷰만이라 쉽게 되돌린다"고 말할 수 없다** — RPC 는 별 파일(0073)로 나눌지 §12 결정 4 와 함께 정한다.

### 9-2. 추천 형식 저장 — 이번 범위에서 **보류**(권고)
- 선택 시 추천값 스냅샷은 이미 저장된다(`drink_topic_picks.recommended_format/reason`). "저장하지 않으면 측정 불가"는 틀렸다 — 선택 대비 추천 정확도는 지금도 잴 수 있다.
- 후보 단계 영속화는 계산 시각·규칙 버전·근거 수 변경 시 갱신·수집기 수정이 필요하다. 단순 칸 2개가 아니다. 필터·집계가 꼭 필요해질 때(§12 결정 5) 따로 한다.
- 이번엔 화면 계산(`formatRecommend`) 그대로, "모름"과 "근거 0" 을 가른다.

### 9-3. 밈 연결 — 카드 ↔ 소재
현행: 밈 제작안은 카드 또는 소재 중 하나를 소유. 카드 밈은 `ig_card_use_refine`(정밀화 포함) 또는 `ig_card_decide(use)` 로 시작하고, 소재 밈은 `pick_topic(format=meme)` 로 시작한다(개발 요청 없음). 두 경로의 산출물·게시(`create_meme_publication`, 0068)·성과는 같다.

| 안 | 내용 | 장점 | 단점 | 권고 |
|---|---|---|---|---|
| **A. 연결 없이 뷰로 합친다** | 카드 밈을 작업 단위로 뷰에 넣고, 작업공간이 `card_id` 소유 밈도 연다(`/drinks/work/meme/[draftId]` 또는 `?card=`) | 데이터 변경 0, 기존 정밀화·Apify 통제 그대로, 기존 데이터 보존 | 카드 밈은 "소재"가 아니라 소재 화면 내 소재 탭에서 **밈 제작안**으로 보인다(형식 칩으로 구분) | **기본안** |
| B. [쓰자] 때 소재를 만들어 연결 | `drinks_ig_card_use_as_topic`: `ig_card_decide(use)` + `pick_topic(format=meme, candidate 없음)` + 제작안 `topic_id` 로 생성 | 작업 단위가 전부 소재 | 새 쓰기 RPC, 카드↔소재 중복 클릭·기존 제작안 재사용·출처(IG 미디어·분석 결과) 보존 계약 필요, 정밀화와 분리 필요(`use_refine` 는 그대로 두고 연결만) | 2차 |
| C. 기존 카드 밈 소유자를 소재로 일괄 변경 | 데이터 마이그레이션 | 단일 모델 | 이력·게시 기록·`drink_meme_owner_ck` 위반 위험 | **제외** |

- 어느 안이든 **밈을 일반 소재의 `selected` 로 강제하지 않는다**(설명형·카드의 편성 계약과 다르다).
- `ig_card_use_refine` 의 Apify 비용 통제(클릭 1회=실행 1회, 실행·월 상한, 영상 삭제)는 그대로이며 자동 실행으로 바뀌지 않는다.

### 9-4. 버전·승인 계약(화면이 지킬 것)
- 모든 쓰기에 `expected_version` / `expected_digest` 를 **화면에 보인 값**으로 보낸다. 불일치는 "새로 불러오기"로 끝나고 자동 재시도하지 않는다.
- 결정 함수는 서버가 거부할 버튼을 만들지 않는다(차단 계층이 먼저). 그래도 서버가 거부하면 그 사유를 그대로 보인다.
- 금액이 걸린 버튼([결재 열기]·[구매 요청]·[쓰자(정밀화)])은 상한·잔액·승인자 말을 한 번 더 보여 주는 확인 단계를 갖는다.
