## 1. 목적과 구현 위치

기존 논문·리포트 운영 대시보드에 **주류 공장**을 추가한다. 사케·전통주·위스키 애호가를 대상으로 소재를 수집·선정하고, 하나의 검증된 기획에서 영상과 카드뉴스를 각각 제작·검수·예약 발행한다.

기획은 이 대화에서 정리할 수 있지만 실제 개발·테스트·PR은 VIDEO-ARTICLE 프로젝트에서 수행한다. DrinkNote 앱에는 이 기능을 구현하지 않는다. 기존 논문·리포트 자료를 주류 저장 구조로 일괄 이관하지 않는다.

이 문서에 있는 테이블·경로·상태 이름은 **신규 구현 계약안**이다. 이미 존재하는 기능으로 해석하지 않는다. 기존 동작의 근거는 §3, 외부 자료의 확인 범위는 §16에 기록한다.

### 1.2 이번 명세의 완료 조건

1. 재사용·어댑터 필요·신규 범위가 파일 근거와 함께 나뉜다.
2. 원자료→후보→검증→선정→두 형식 제작→발행의 추적 관계가 정의된다.
3. 정상·실패·재시도·수정·승인 무효화·발행 결과 불명의 상태 전이가 정의된다.
4. 화면에서 운영자가 다음 행동과 차단 이유를 알 수 있다.
5. 자동 수집 실패와 정상 0건을 구별하고, 근거 없는 인기 소재가 제작으로 직행하지 않는다.
6. 실제 구현 위치, 단계별 범위, 미검증·결정 유보 항목이 명확하다.

## 2. 서로 섞지 않을 네 가지 축

| 축 | 값 | 규칙 |
|---|---|---|
| 공장 `factory` | 기존 paper/finance + 신규 drinks | 수집·근거·선정은 분야별 처리 |
| 결과물 `format` | video / carousel | 카드뉴스는 영상 스타일이 아닌 독립 결과물 |
| 표현 설정 `visual_profile` | 기존 photo 연결 / 주류용 추가 프로필 | 이름만 추가해 렌더 가능하다고 처리하지 않음. 지원하지 않는 조합은 발주 차단 |
| 발행 대상 | platform + social_account_id + post_type | 공장·주종·언어에서 계정을 암묵 선택하지 않음 |

`drink_categories`는 sake/traditional/whisky의 복수 태그다. 전통주의 세부 분류와 제품·양조장명은 별도 메타데이터이며 공장을 추가하지 않는다. 술째리고 브랜드 규칙은 제작 버전에 고정되는 `brand_profile_version`으로 표현한다.

영상과 카드뉴스는 공통 근거·핵심 질문을 공유하지만 대본·페이지 구성·승인·비용·발행 일정을 각각 갖는다. 두 형식을 반드시 동시에 만들거나 발행할 필요가 없다.

## 4. 목표 흐름과 소유 관계

```text
수집원 등록 → 수집 실행 → 원문 스냅샷/실패 기록
                            ↓
                  소재 후보 + 출처/질문 연결
                            ↓
                 경량 채점 → 조사 후보 선정
                            ↓
             추가 근거 확보 → 주장 확인 → 편성 승인
                            ↓
             승인된 근거·공통 기획 버전(동결)
                      ┌─────┴─────┐
                   video        carousel
                영상 제작안      페이지 제작안
                   ↓               ↓
                 렌더링         페이지 렌더링
                   ↓               ↓
                 개별 검수·승인된 파일 묶음
                            ↓
               계정·캡션·일정을 지정한 발행 승인
                            ↓
               예약 → 발행 → 결과 확인 → 성과
```

‘수집한 문서’와 ‘제작할 주제’를 분리한다. 하나의 문서가 여러 소재에 쓰일 수 있고, 한 소재에 여러 문서·질문이 연결될 수 있다. 원자료를 수정하거나 다른 출처를 덧붙여 기존 승인 버전을 덮어쓰지 않는다.

## 5. 소재 수집: 세 개의 공급 경로

### 5.1 무엇을 어디서 얻을지

| 경로 | 입력 | 결과 | 운영 방식 |
|---|---|---|---|
| 상시 지식 | 제조·원료·향·보관·라벨·문화에 대한 공식/전문 자료 | 시간이 지나도 쓸 수 있는 질문형 소재 | 최초 기반 목록 구축 후 주 1회 보충. 새 게시물이 없어도 재사용 가능한 근거에서 새 질문 발굴 |
| 시의성 | 제조사·수입사·기관의 신제품·행사·공지 | 유효 기간이 있는 소재 | 승인한 수집원에서 일 1회 변경 탐색. 날짜와 적용 지역 확인 |
| 독자 수요 | 운영자가 등록한 댓글·질문·현장 경험·검색 질문 | 애호가가 궁금해하는 후보 | 질문을 묶어 빈도를 기록. 질문·인기 신호는 근거로 쓰지 않음 |

초기에는 Instagram 전체 크롤링, 인기 계정 영상 다운로드, 유료 검색/분석 서비스, DM 자동 수집을 필수 의존성으로 두지 않는다. 질문은 운영자 입력·URL 등록으로 시작한다. 향후 자사 계정 댓글 연동은 권한·데이터 최소화 검토 후 추가한다.

| 분야 | 확인한 출발점 | 활용 | 커넥터 상태 |
|---|---|---|---|
| 사케 | NRIB의 용어·보관·입문·연구 안내, 일본 국세청 제조/표시 자료 | 원리·용어·범위 확인 | 공개 페이지 확인. 자동 수집·파싱·재사용 권리는 미검증 |
| 전통주 | 더술닷컴의 우리술 자료·책자·제품/양조장 안내 | 초기 소재 지도·출처 탐색 | 검색 결과·안내 확인. 개별 자료 최신성·파싱·권리는 미검증 |

공식 출처도 광고성 효능·우월성·주관적인 맛 표현까지 검증된 일반 사실로 취급하지 않는다. 예를 들어 ‘숙취가 적다’는 판매 설명은 그대로 근거 승인하지 않는다. 제조사 시음 표현은 ‘제조사 설명’으로 귀속하거나, 독립 근거를 확보하지 못하면 제외한다.

### 5.3 수집원 등록 계약

`drink_sources`에 출처명·canonical URL·publisher·source_type·language·대상 주종·수집 방식·주기·파서 버전·최대 요청 수·이용 조건 확인 상태를 둔다.

수집 방식은 manual_url / feed / approved_page다. 실제 피드 존재를 확인하기 전에는 feed로 등록하지 않는다. 상태는 proposed → validated → active, 실패 누적 시 paused, 더 이상 쓰지 않으면 retired다. active 전에는 성공 수집·원문 품질·요청 제한·저장 범위를 운영자가 확인한다.

초기 제안값: active 수집원 12개 이하, 자동 실행 일 1회, 실행당 문서 메타데이터 100건·본문 신규 확보 20건·LLM 조사 후보 12건 이하. 실제 비용 상한은 기존 모델 단가를 확인해 후속 구현 설정에 넣는다. 초과분은 다음 실행으로 넘기고 무제한 재시도하지 않는다. 이번 문서 작성 중에는 수집기나 유료 호출을 실행하지 않는다.

### 5.4 중복·워터마크·실패

1. URL은 추적 파라미터만 정규화하고 의미 있는 제품/페이지 식별자는 보존한다.
2. 본문 해시가 같으면 스냅샷을 재생성하지 않는다. 같은 URL의 본문이 바뀌면 새 스냅샷을 만든다.
3. 소재는 주종+핵심 질문+대상 제품/공정+각도 기반 중복키로 1차 묶는다. 유사도는 병합 제안에만 사용하며 서로 다른 제품·빈티지·시장을 자동 합치지 않는다.
4. 여러 매체가 같은 보도자료를 전재하면 `origin_group`으로 묶어 독립 출처 수를 부풀리지 않는다.
5. 성공한 수집원만 해당 구간 워터마크를 전진시킨다. 페이지 일부 실패는 partial로 기록하고 재수집 구간을 남긴다.
6. 정상 0건 / 일부 성공 / 인증·차단 / 네트워크 / 파싱 실패를 구별한다. 검색 결과 요약만 얻은 항목은 metadata_only다.
7. HTML/PDF/이미지 라벨의 텍스트를 얻지 못하면 실패나 부분 확보로 남긴다. OCR·번역 결과를 원문으로 대체하지 않는다.

## 6. 소재 선정: 인기 순위와 제작 적합성을 분리

### 6.1 2단계 선별

**A. 경량 후보 평가:** 제목·질문·원자료 개요로 조사할 가치가 있는지 평가한다. 점수는 provisional이며 근거 검증 완료와 무관하다. 조사 후보는 최대 12개/회로 제한한다.

**B. 제작 편성 평가:** 선택된 후보에 대해서만 원문을 확보하고 핵심 주장의 근거를 확인한다. 제작 가능한 형태인지 판단한 뒤 운영자가 주간 편성을 확정한다. 후보 점수가 높아도 검증이 막히면 조사 대기로 남긴다.

### 6.2 제작 편성 전 필수 조건

- 사케·전통주·위스키 애호가의 구체적인 질문 하나와 사용 가치가 있다.
- 핵심 사실 주장에 접근 가능한 출처·스냅샷·원문 위치가 연결된다.
- 원문 발췌의 존재 확인과 ‘이 발췌가 주장을 뒷받침하는지’의 범위 검토가 모두 끝난다. 둘을 같은 verified 플래그로 합치지 않는다.
- 제품 설명·시음 평가·공정 일반론·추정을 구분하고, 가격/재고/행사 정보에 확인일·시장·유효 기한이 있다.
- 결정적 출처 충돌이 없거나 콘텐츠가 그 불확실성 자체를 정확히 설명한다. 미해결 충돌을 확정 결론으로 내보내지 않는다.
- 최소 하나의 형식에서 설명 가능하다. 영상 적합성이 낮아도 카드뉴스 적합성이 있으면 선정 가능하다.
- 필요한 이미지·인용·음원은 사용 가능한 범위가 확인됐거나 직접 제작으로 대체 가능하다.

제품별 규격은 해당 제조사의 1차 자료 하나로 확인 가능할 수 있다. 일반적인 원리·비교·효능으로 확대할 때는 주장을 실제로 뒷받침하는 전문/독립 근거가 필요하다. ‘출처 2개’라는 숫자만으로 통과시키지 않는다.

### 6.3 설명 가능한 점수

각 축은 0~4점이며 코드가 가중 합을 계산한다. LLM은 항목별 점수 제안과 근거만 제공한다. 사람이 수정하면 이전 값·이유를 남긴다.

| 축 | 비중 | 0점 / 4점 기준 |
|---|---:|---|
| 애호가 관련성 | 25 | 분야와 동떨어짐 / 실제 선택·이해·경험에 직접 연결 |
| 저장할 효용 | 25 | 감상만 남음 / 반복해서 사용할 판단 기준 제공 |
| 발견·궁금증 | 20 | 질문과 발견 없음 / 익숙한 대상에 구체적인 새 관점 |
| 형식 적합성 | 20 | 두 형식 모두 설명 불가 / 한 형식 이상에서 명확한 설명 구조 |
| 지금 다룰 이유 | 10 | 현재 편성과 연결 약함 / 시기·질문 수요·연재 공백에 적합 |

`score = Σ(weight × item_score / 4)`; 0~100점. 형식 적합성은 video/carousel 각 점수를 기록하고 최댓값을 사용한다. 상시 지식은 발행일이 오래됐다는 이유만으로 시의성 0점을 주지 않는다.

제안 기준은 65점 이상+필수 조건 충족을 편성 후보로 표시한다. 65점은 검증 전 기준값이며, 자동 발주/발행 문턱이 아니다. 같은 점수에서는 근거 준비·최근 중복·편성 균형·예상 제작비를 별도 열로 보여주고 운영자가 결정한다. 순위와 거절 사유를 다시 설명할 수 있도록 rubric_version을 저장한다.

### 6.4 주간 편성과 소재 부족 대응

- 초기 운영 가설: 주 3개 소재, 원칙적으로 세 주종을 고르게 다루되 제작 적합성을 우선한다. 각 소재는 video/carousel/both 중 선택한다.
- 상시 지식 60% / 시의성 20% / 독자 질문 20%는 4주 누적의 소프트 가이드다. 소량 편성에 강제 할당하지 않는다.
- 편성함에 발행 가능한 소재 6개(주 3개 기준 2주분)를 확보하는 것을 목표로 한다. 실제 확보량은 미검증이다.
- 부족하면 상시 지식 대기열에서 보충하고 조사 범위를 좁힌다. 근거 기준을 낮추거나 발행량을 채우기 위해 자동 생성하지 않는다.
- 최초 도입 시 수동 질문 30개(주종별 10개)를 입력하는 부트스트랩을 권장한다. 이는 후속 구현/운영 작업이며 이번에는 만들지 않는다.
- 거절 이유(중복/근거 부족/독자 불일치/화면화 어려움/시기 만료/비용)를 보관한다. 근거 추가·각도 변경 시 재평가 가능하다.
- 신규 계정의 성과 0·외부 계정의 비공개 저장/팔로우 지표를 인기 근거로 쓰지 않는다.

### 6.5 근거 신선도와 반영

기본 재확인 제안값: 가격·재고는 발행 전 24시간 이내, 행사 일정은 72시간 이내 및 행사 종료 전, 제품 규격은 30일 이내. 상시 원리 자료는 발행 전 접근 가능성·정정 여부를 확인한다. 의미 있는 변경을 찾지 못했다는 것과 내용이 참이라는 것은 구분한다.

기한이 지나면 `freshness_blocked`로 예약 실행을 막고 원문 재확인을 요청한다. 새 스냅샷이 기존 주장과 다르면 근거·기획 새 버전과 관련 결과물 재검수가 필요하다. 값이 같고 원문 동일성이 확인되면 확인 이력을 추가해 신선도만 갱신할 수 있다. 운영값은 주제별로 조정 가능하며 조정 이유를 기록한다.

ID는 UUID, 시각은 UTC 저장·Asia/Seoul 표시가 기본이다. 원자료 발행시각이 없으면 null로 남기며 수집일로 대체하지 않는다. current_*는 화면 편의를 위한 포인터이며 승인된 옛 버전의 참조를 바꾸지 않는다.

research 결과는 새로운 draft 상태의 topic_review로 저장한다. plan 작업은 선택한 형식의 새 draft content_revision을 만든다. render 작업만 승인된 제작안을 읽어 파일을 만든다. 늦게 끝난 작업은 최신 포인터를 무조건 덮어쓰지 않고 입력 해시·기준 버전과 비교해 별도 후보 결과로 보존한다. `production_jobs`는 이 세 단계의 논리 실행 기록이며 물리 이름은 변경 가능하다.

핵심 주장에 대한 자동 의미평가 결과는 support 제안으로만 저장한다. ready로 전환하기 전 운영자가 핵심 주장의 support_review를 확인한다. selected는 점수 기준과 승인 review가 모두 필요하며, 기준점 미달을 예외 편성하려면 사유를 기록한다. 근거 미확인·권리 미확보 같은 필수 조건은 점수 예외로 우회하지 않는다.

### 7.2 근거 문서 계약

`evidence_pack.claims[]`는 claim_id, text, claim_type(product_fact/process/comparison/opinion), attribution, scope(product/region/lot/time), source_refs[], quote_check, support_review, limitations, valid_until을 가진다.

`source_refs[]`는 snapshot_id, section/page 또는 text_offset, original_quote, translation?을 가진다. quote_check는 matched/unmatched/not_checked, support_review는 supported/conflicting/insufficient/not_reviewed다. 자동 문자열 일치는 사실 검증 완료가 아니다. 핵심 사실이 모두 supported여야 편성 승인 가능하다. 취향 평가는 주관적 평가로 명시하고 사실 주장처럼 검증 상태를 부여하지 않는다.

`brief`는 audience_question, core_takeaway, selected_claim_ids, exclusions, useful_action, proposed_formats, followup_question을 가진다. 수집원 신뢰도·출처 수·본문 길이만으로 supported를 자동 부여하지 않는다.

### 7.3 형식별 제작안 계약

- video: scenes[]의 narration, visual_role, explanation, claim_ids, source_refs, timing, continuity, overlays. 기존 엔진이 실제로 받는 필드로 변환하는 어댑터가 필요하다.
- carousel: pages[]의 position, role(cover/explain/compare/checklist/source), heading, body, graphic_spec, claim_ids, source_refs, template_version. 첫 범위는 정적 이미지 카드뉴스이며 동영상 혼합 캐러셀은 제외한다.
- 공통: locale, aspect_ratio, brand_profile_version, schema_version, content_revision, asset_manifest. 유료 모델·크기·티어·스타일·이전 연결 프레임이 실행/비용/캐시에 동일하게 반영돼야 한다.
- 같은 소재에서 승인 근거 A로 영상, B로 카드를 만들 수는 있으나 화면에 불일치를 표시한다. 최신 근거에서 철회된 주장에 의존하는 예약은 차단한다.

## 8. 상태 전이

### 8.1 소재와 편성

```text
inbox → triaged → researching → ready → selected
  └──────────→ on_hold / rejected / duplicate
```

| 전이 | 실행자·조건 | 실패/되돌리기 |
|---|---|---|
| inbox→triaged | 경량 분류·provisional 점수 완료 | 실패는 inbox 유지+오류; 0점으로 정상 처리 금지 |
| triaged→researching | 운영자가 조사 후보 선택 | 자동 선정은 기본 비활성 |
| researching→ready | 현재 review의 필수 근거·공통 기획 검사 통과 | 부족/충돌 시 researching+block_reasons |
| ready→selected | 운영자가 형식·편성 주차와 approved 상태인 review 버전을 확정. current_review_id·입력 해시·승인 무효화 여부를 서버가 재검사 | 한 트랜잭션으로 선정 버전·형식·이력 기록. 제작 발주는 별도 명시 행동 |
| *→on_hold/rejected | 운영자 사유 기록 | on_hold는 재검토일; rejected는 명시 재개 가능 |
| *→duplicate | 운영자가 canonical_topic_id 지정 | 이미 발행/예약된 소재 자동 병합 금지 |
| selected→researching | 승인 근거에 중대한 오류·변경 발견 | 관련 미발행 요청 pause, 생성 작업 보호, 기존 발행 이력 보존 |

주제 상태에 ‘영상 완료’나 ‘전체 발행 완료’를 저장하지 않는다. 선택한 형식별 현황으로 화면에서 계산한다.

### 8.2 검토 버전·제작안

topic_review 및 형식별 plan의 승인 상태는 draft → in_review → approved 또는 changes_requested다. 승인 본문은 불변이며 수정은 draft 상태의 새 버전을 만든다. 이전 승인에는 revoked_at/reason을 붙일 수 있고 삭제하지 않는다.

신규 근거 추가가 기존 주장을 바꾸지 않으면 새 버전을 자동 승인하지도, 기존 버전을 자동 폐기하지도 않는다. 검토자가 영향 범위를 결정한다. 오류·권리 철회처럼 기존 내용이 유효하지 않다는 판단이 나면 해당 버전은 revoked, 관련 예약은 paused가 된다.

승인이 철회되면 해당 버전과 그 파생 결과물을 서버에서 즉시 차단한다. queued 조사 후속/제작 작업은 canceled로 하고, running 작업은 가능한 범위에서 중단한다. 이미 진행 중인 외부 생성이 끝나면 파일·비용·결과는 보존하되 output_review는 blocked로 저장하며 새 제작안이나 파일 승인으로 우회할 수 없다. 최신의 유효한 근거 버전을 입력으로 새 revision을 만든 뒤 다시 검토해야 한다. 철회와 완료 저장이 경합해도 승인·발행 시 현재 철회 상태를 다시 검사한다.

### 8.3 제작 작업과 결과 검수

```text
queued → running → succeeded / failed / canceled
파일 검수: pending → approved / changes_requested / blocked
```

- succeeded는 파일 생성 성공일 뿐 게시 승인 아님. 경고가 있으면 pending에서 표시하고 검토자가 판단한다.
- 최종 파일 검수 상태는 output_reviews에 저장한다. 발행안 작성·승인 시 revision과 manifest가 일치하는 유효한 approved 검수 기록이 필수다. 같은 revision을 여러 번 렌더했다면 발행할 manifest를 명시 선택한다.
- 실패 재시도는 같은 revision에 새 job을 만들며 자동 시도는 기본 최대 2회다. 원인·비용 상한을 넘으면 수동 조치.
- 워커 lease 만료 시 외부 생성 operation_id부터 확인한다. 회수된 lease의 옛 attempt_token은 완료 저장을 할 수 없다.
- 재렌더로 파일이 바뀌면 새 manifest를 만들고 결과 검수와 연결된 발행 승인을 다시 받는다. 승인 manifest 파일을 덮어쓰지 않는다.
- queued 취소는 원자적으로 가능. running 취소는 best effort이고 이미 발생한 비용·파일은 기록한다. 취소된 작업의 늦은 결과를 자동 승인하지 않는다.

### 8.4 발행 요청

```text
draft → awaiting_approval → approved → scheduled → publishing → published
                                  └→ canceled       ├→ failed
                                                    └→ unknown
scheduled/approved → paused → awaiting_approval 또는 scheduled
```

| 상태 | 의미 / 허용 행동 |
|---|---|
| draft | 계정·캡션·결과물·시각 작성. 자유 수정 가능 |
| awaiting_approval | 정확한 파일 묶음·계정·캡션·일정을 사람에게 제시 |
| approved | 승인 digest와 현재 payload가 일치. 즉시 발행도 워커 요청을 거침 |
| scheduled | publish_at 도래 시 워커가 재검증 후 원자적으로 점유 |
| publishing | 업로드/처리 확인/최종 publish/확인 단계를 attempt에 기록 |
| published | 외부 게시물 ID 및 계정 일치 확인. URL 확인 지연 시 별도 reconcile_state 표시 |
| failed | 공급자가 실패를 확정했고 미게시임을 확인한 상태. 원인 수정 후 재시도 가능 |
| unknown | publish 타임아웃·워커 종료 등으로 게시 여부 불명. 자동 재발행 금지, 기존 컨테이너/게시물 조회로 대조 |
| paused | 근거 만료·승인 무효·계정 연결 문제·운영자 중지. 사유 해소 후 승인 digest가 같으면 scheduled 복귀; payload 변경이면 재승인 |
| canceled | 외부 publish 시작 전 취소가 확정되었거나, 조회 대조로 미게시가 확정된 경우만. 게시 여부 불명 상태의 취소 요청은 unknown을 유지하고 cancel_requested를 기록 |

계정·캡션·파일·커버·예약시각 변경은 새 승인 digest를 요구한다. approved/scheduled payload를 제자리 수정하지 않고 기존 요청 취소+새 요청으로 대체한다. 중복 제약은 취소·확정 실패 요청을 제외한다. 동일 게시물 재게시 기능은 초기 범위에서 제외한다.

예약 워커는 publish_at≤now와 승인 유효성·근거 신선도·미취소·파일·계정 상태를 확인하고 짧은 트랜잭션으로 점유한다. 기본 허용 지연은 2시간이며 초과 시 자동 늦은 게시를 하지 않고 paused로 보낸다. publishing에 들어간 뒤 취소/승인 철회가 경합하면 최종 외부 publish 직전에도 확인하며, 이미 진행된 외부 호출은 되돌릴 수 없음을 기록한다.

외부 API와 로컬 DB 사이 exactly-once는 보장하지 않는다. 고유키·점유·조회 대조로 중복을 줄이고 판단 불가는 unknown으로 남긴다.

unknown은 취소 요청이 있어도 중복 제약과 파일 보관 보호를 유지한다. 이미 게시된 것이 확인되면 published로 정정하고 취소가 적용되지 않았음을 표시한다. 확정 미게시이면 canceled로 종료할 수 있다. 운영자가 ‘확인 필요’를 취소로 바꿔 새 요청을 만들게 하는 우회는 두지 않는다.

## 9. 대시보드 화면 명세

기존 논문·리포트 경로는 유지한다. 주류 공장만 다음 메뉴를 가진다. 설정은 보조 메뉴로 둔다.

### 9.1 선별 `/drinks`

- 상단: 조치 필요(수집 실패/조사 막힘/발행 가능 소재 부족), 수집 마지막 시각, 편성 준비 소재 수.
- 탭: 전체 후보 / 조사 중 / 편성 가능 / 편성함 / 보류·제외.
- 필터: 사케·전통주·위스키, 공급 경로, 근거 준비, 형식 적합성, 수집일/자료 발행일.
- 후보 카드: 질문, 독자 효용, 출처 종류·원출처 묶음, provisional/final 점수, video/carousel 적합성, 중복 경고, 근거 부족 이유, 유효 기한, 다음 버튼.
- 행동: URL·질문 직접 등록 → 조사 후보로 선택 → 근거 검토 → 편성. ‘편성’이 유료 제작을 암묵 실행하지 않는다.
- 편성함: 주차별 선택한 형식과 조사/제작 준비 상태. 3소재를 골라도 두 형식을 모두 만들었다고 계산하지 않음.

### 9.2 작업함 `/drinks/review`, 상세 `/drinks/review/[topicId]?tab=`

목록은 소재 단위이며 ‘다음 행동’ 순으로 정렬한다. 상세 탭은 근거 / 공통 기획 / 영상 / 카드뉴스 / 이력이다.

- 근거: 원문/번역, claim별 발췌·범위·충돌·유효 기한, 근거 승인 버튼과 차단 이유.
- 공통 기획: 질문·결론·제외 범위·효용·제작 형식, 현재 승인 review 버전.
- 영상/카드뉴스: 제작안 버전, 근거 버전 차이, 표현 설정, 비용 추정, 형식별 승인·발주.
- 주 버튼은 상태에서 계산하는 하나로 제한: 조사하기 / 근거 검토 / 기획 승인 / 제작안 작성 / 제작안 검수 / 제작 요청.
- API가 승인 시 조건을 재검증한다. UI 버튼 숨김만으로 권한·예산·무효 버전을 보호하지 않는다.

### 9.3 제작·발행 `/drinks/production`

- 탭: 조치 필요 / 제작 중 / 검수 대기 / 발행 대기·예약 / 발행 완료 / 보관.
- 같은 소재 아래 영상·카드를 묶고 개별 상태·비용·revision을 노출한다.
- 영상: 재생·커버·자막·QA. 카드뉴스: 전체 페이지 스트립·확대·순서·누락 검사.
- 행동: 검수 승인 / 변경 요청 / 같은 제작안 재렌더 / 새 제작안 / 파일 다운로드 / 발행안 작성 / 예약 취소.
- 발행 승인 모달: 계정명+외부 ID, 실제 파일 순서·커버·캡션, 현지시각+시간대, 공개 게시임을 표시.
- 예약 달력과 목록은 같은 publication_requests를 읽는다. 화면의 예약 카드가 별도 실행 주체가 아니다.
- unknown은 실패 탭에 숨기지 않고 ‘게시 여부 확인 필요’로 표시하고 재발행 버튼을 차단한다.

### 9.4 성과 `/drinks/analytics`

- 기간·주종·형식·계정·시리즈별 필터. 소재→결과물→외부 게시물로 내려갈 수 있다.
- 실제 수집된 지표만 표시. 게시 후 24h/72h/7d의 같은 경과시간 비교를 목표로 하되 누락된 과거 시점을 추정해 채우지 않음.
- 저장/공유/도달, 영상 시청 지표의 정의·분모·지원 여부를 표시. 영상 길이 대비 평균 시청시간을 완주율로 부르지 않음.
- 초기에 연결 전이면 ‘미연결/미수집’을 표시. 가짜 성과 수치 금지.

### 9.5 설정 `/drinks/settings`

수집원·실행 주기·상한·소재 점수 기준·신선도·브랜드/표현 프로필·계정 연결·기본 시간대·발행 스위치를 관리한다. 인증정보 원문은 보여주지 않는다. ‘수집 켜짐’, ‘유료 제작 허용’, ‘Instagram 발행 허용’은 각각 별도이며 초기 모두 비활성으로 시작한다.

## 10. 서버·워커 경계

- Next.js: 권한 확인, 입력 검증, 버전·승인 기록, 작업 큐 적재, 상태 조회.
- Python 워커: 수집·조사·기획 생성·형식별 제작·발행·성과 수집. 오래 걸리는 작업을 웹 요청이나 Edge 백그라운드 수명에 의존시키지 않음.
- 수집 단계의 네트워크 파싱과 유료 LLM 조사를 분리하고 각각 상한·실행 기록을 둔다.
- 기존 engine/db·Supabase 접근은 검증한 헬퍼만 공유. paper/report 암묵 분기를 통과해 잘못된 테이블에 기록하지 않음.
- 렌더 연결은 신규 주류 어댑터가 기존 영상 입력 계약을 충족하는지 확인한 후 활성화. carousel은 별도 실행기.
- 조회는 응답의 completeness(normal/partial/failed/not_run)를 전달한다. 여러 요청 일부 실패를 전체 정상 0건으로 집계하지 않음.
- 외부에서 읽어온 문서·댓글은 데이터다. 실행 명령·시스템 지시로 사용하지 않으며 외부 URL 다운로드는 허용된 주소·형식·크기만 받는다. 수동 URL도 내부망 주소 접근을 허용하지 않는다.

## 11. Instagram 연동 준비 계약

기본 공급자는 Meta 공식 API다. Instagram Login/Facebook Login 선택은 계정·음악·분석 요구를 확인해 결정한다. 서로 다른 로그인 방식의 권한명·Page 요구를 섞지 않는다. 계정 연결 전부터 특정 권한이 확보됐다고 가정하지 않는다.

- 실제 계정 ID와 표시명을 연결 때 확인하고 발행 때 재대조한다. 기본 계정 자동 폴백 금지. 기존 계정 재인증은 동일 외부 ID일 때만 credential_ref를 갱신한다. 다른 외부 ID가 반환되면 기존 연결 갱신을 거부하고 새 계정 레코드로 등록해야 한다. 요청 승인 digest와 attempt에 고정한 외부 ID가 실제 인증 계정과 다르면 게시를 중단한다.
- 플랫폼별 기능(릴스/정적 카드뉴스/커버/음원/AI 표시/분석)을 capabilities로 기록한다. 지원하지 않는 옵션은 발행 전에 명시 차단한다.
- video는 실제 영상 파일을, carousel은 승인한 순서의 정적 이미지 묶음을 전달한다. 이미지 개수·크기·코덱·음원 등의 제한은 구현 시 API 버전 문서와 실제 계정으로 확인해 버전 있는 검증 규칙으로 저장한다.
- 공급자가 파일을 가져가는 동안 접근 가능한 URL을 제공하되, 인증 토큰을 URL/로그/공개 데이터에 넣지 않는다. 다운로드 완료 전에 URL이 만료되면 파일 준비 실패로 처리한다.
- carousel 자식 컨테이너가 모두 준비되기 전 부모 publish를 하지 않는다. 부분 업로드 실패에 대한 개별 상태를 남긴다.
- 토큰 만료·권한 철회는 계정을 reauth_required로 하고 요청을 paused로 보낸다. 다른 계정으로 대신 게시하지 않는다.
- 초기에는 무인 자동 콘텐츠 승인·DM·광고 집행·게시물 자동 삭제를 구현하지 않는다. 승인 후 예약 자동 실행이 목표다.
- Metricool 등 대안은 후속 선택 가능하지만 실제 예약 실행 주체는 하나다. 양쪽에서 동시에 발행하지 않는다.

## 12. 파일 보관·권한·비용

### 12.1 보관

현재 `engine/publish.py`는 YouTube 성공 뒤 `storage_gc.purge_after_upload`를 호출한다. 신규 예약 파일과 공유 에셋은 이 경로와 주기 정리 양쪽에서 보호해야 한다. 기존 파일명의 mp4 판별만으로 카드 이미지를 캐시로 분류하면 안 된다.

파일은 referenced-by 관계로 보관한다. approved/scheduled/publishing/unknown/paused 발행이 참조하는 final/cover/pages, 활성 제작 입력, 운영자 보관 파일은 삭제 대상에서 제외한다. paused가 오래되면 보관 비용을 알리고 명시 취소/보관 선택을 받는다. 자동으로 예약을 지우거나 파일을 없애지 않는다.

공유 파일은 참조가 모두 해제되고 보관 기한이 끝난 뒤에만 회수 가능하다. 발행 요청+파일 참조 생성과 GC 점유는 DB 잠금/참조 재검사로 경합을 막는다. 이미 deleting/deleted인 파일을 발행 승인할 수 없으며 게시물을 완성 파일 백업으로 가정하지 않는다.

후속 구현에서는 GC 드라이런으로 다른 플랫폼 예약·카드뉴스·공유 에셋 보존을 검증한 뒤 연결한다. 이 문서는 삭제 실행을 승인하지 않는다.

### 12.2 권한

기존 운영자 게이트를 유지한다. 신규 테이블에 기존 초기 마이그레이션의 anon 전체 쓰기 정책을 복사하지 않는다. 현재 저장소 `0049_public_repo_lockdown.sql` 방향을 따른다. 신규 데이터는 기본 서버 경유 읽기/쓰기, 공개 직접 접근 차단 및 RLS를 원칙으로 하며 실제 운영 정책은 마이그레이션 단계에서 확인한다.

계정 토큰은 서버 비밀 저장소에 두고 DB에는 credential_ref만 둔다. 운영자 키·service key·refresh token은 브라우저·Git·명세·실행 로그에 남기지 않는다. 이번 조사에서는 .env나 토큰을 열지 않았다.

### 12.3 비용

추정 비용은 조사 / 기획 / 이미지 / 영상 / 카드 렌더 / 발행 도구로 구분하고, 실행 비용은 공급자·모델·시도·revision/job에 귀속한다. 공통 에셋 비용은 한 번 기록하고 형식별 사용 참조를 남겨 이중 합산을 피한다.

소재·작업·일간 상한을 두되 구체 금액은 후속 구현 시 현행 단가와 운영자 예산으로 확정한다. 금액이 미설정이면 유료 제작은 비활성이다. 모델의 ‘잘 만들었다’는 자기보고로 비용·캐시·검수 상태를 확정하지 않는다.

## 17. VIDEO-ARTICLE 구현 인계 기준

이 명세를 VIDEO-ARTICLE 프로젝트의 다음 구현 작업 입력으로 사용한다. 이번 대화에서 구현 작업을 다른 채팅에 자동 발송하거나 시작하지 않는다.

구현자는 현재 origin/main과 모든 관련 worktree/미커밋 변경을 확인한 뒤 격리된 작업 환경을 사용한다. 제품 코드는 그 저장소에서만 수정하며 이 문서를 DrinkNote 코드로 옮기지 않는다. 논문·리포트 데이터 일괄 이관·스타일 전역 변경·기존 요청/업로드 테이블 이름 교체는 범위 밖이다.

첫 개발 범위는 §13-A를 기본으로 별도 확정한다. 테이블 DDL·RLS·기존 영상 입력 어댑터·UI 액션 계약을 제시하고 적절한 검증을 통과한 뒤 후속 단계로 간다. 머지·배포·운영 DB 적용·유료 생성·실제 게시·삭제는 각각 해당 작업에서 승인 범위를 확인한다.
