## 1. 홈 기본 배치일 — "최신" → **"가장 오래된 미확인"** (8/19 결정 취소)

`web/app/page.tsx`, `web/app/finance/page.tsx`

2026-08-19 에 기본을 최신 배치로 바꿨다. 이유는 "확인 처리를 며칠 건너뛰면 홈이 계속
과거를 보여준다"였다(실제로 리포트 홈이 12일 전 화면으로 열렸다).

**되돌리는 이유:** 선별은 밀린 날을 **오래된 것부터 순서대로** 지워 나가는 작업이다.
최신부터 열리면 매번 "내가 어디까지 봤더라"를 손으로 찾아 거슬러 올라가야 한다.
8/19 결정이 풀려다 한 문제(과거에 갇힘)는 그 뒤 들어온 도구로 이미 해결된다 —
[✓ 확인하고 다음 날짜로 →] 로 한 번에 닫고 넘어가고, 며칠치를 통째로 넘길 때는
[밀린 N일 한번에 확인], 오늘 것만 보려면 [오늘로].

```
batchDate = ?date= 지정값 ?? 가장 오래된 미확인 ?? 최신
```

**되돌리려면:** 두 페이지의 `firstUnreviewed ?? dates[0]` 를 `dates[0]` 으로.

## 2. 배치일 글자 크기 14px → **26px**

`web/app/globals.css` `.batch-bar-date`

홈이 **과거 날짜로 열리기** 때문에 필요한 짝 변경이다. 며칠 것을 보고 있는지 눈에 안 띄면
오늘 것인 줄 알고 선별한다. 목록 맨 아래 바에도 18px 로 다시 적는다.

## 3. 홈 [다음 작업] 카드에서 렌더 큐 작업을 감춤

`web/lib/work/nextAction.ts` — `HOME_SKIP = ["retry_render", "check_render"]`,
`nextStep(counts, hrefs, skip)` 3번째 인자.

우선순위 규칙(§5-3)상 렌더 실패는 **항상 맨 위**다. 실패 잡이 며칠 쌓여 있으면 홈을 열 때마다
"렌더 실패 2건 — 원인을 확인하고 재렌더하세요"가 선별 작업을 가린다. 홈은 선별 화면이므로
렌더 큐는 요약 타일 [렌더·업로드 필요] 와 ⑥ 화면에 맡긴다.

- **카운트는 건드리지 않았다.** `summarize()` 의 `renderNeeded` 는 그대로다 — 타일 숫자는 안 변한다.
- 홈이 아닌 화면에서 `nextStep()` 을 부르면 예전 우선순위 그대로다(기본 인자 `skip = []`).
- **되돌리려면:** 두 홈 페이지의 `nextStep(counts, HREFS, HOME_SKIP)` 에서 세 번째 인자를 지운다.

> 실패 렌더는 **감춘 것이지 없앤 것이 아니다.** [렌더·업로드 필요] 타일과 ⑥ 화면에서 계속 보인다.

## 4. "확인 완료"가 그 날의 미결정 후보를 닫는다

`web/app/page.tsx`, `web/app/finance/page.tsx` — `candidateDecisions: isReviewed ? [] : …`

예전에는 낙점하지 않고 남긴 후보가 계속 "후보 미결정"으로 남았다. 탈락 버튼을 한 편씩
눌러야만 숫자가 줄었다. 실제 작업은 "그날 목록을 눈으로 다 보고 쓸 만한 것만 낙점"이므로,
[확인]이 그 날을 닫는 신호다.

- **DB 는 건드리지 않는다.** `decisions` 에 자동 탈락을 쓰지 않는다 — 카운트에서만 뺀다.
  그래서 [✓ 확인 완료 · 되돌리기]를 누르면 숫자가 그대로 돌아온다.
- 후보 카드는 계속 보인다(다시 낙점할 수 있다).
- 영향 범위는 **홈 요약 타일 [후보 미결정]** 과 [다음 작업] 카드뿐이다.
  `검수 필요`(=낙점됐는데 초안·승인이 남은 편)는 날짜와 무관하므로 바뀌지 않는다.

## 5. 목록 맨 아래 배치일 바 + [↑ 맨 위로]

`web/components/BatchDateFooter.tsx`, 공용 로직 `web/lib/useBatchReview.ts`

후보 20편을 훑고 나면 손이 화면 맨 아래에 있는데 확인·다음날 버튼은 맨 위에만 있었다.
목록이 끝나는 자리에 같은 동작을 다시 놓는다:
`[← 이전 날짜] [✓ 확인하고 다음 날짜로 →] [다음 날짜 →]` / 그 아래 `[↑ 맨 위로]`(`#batch-top` 앵커).

상단 바(`BatchDateBar`)와 **같은 훅**을 쓴다 — API 경로·이동 규칙이 두 벌로 갈라지지 않게.

## 6. ④ — [승인하고 ⑤ 지시서 만들기] 에 버전 체크박스 (두 공장)

`web/components/ReportReviewClient.tsx`, `web/app/api/report-directive-generate/route.ts`

예전에는 이 버튼이 **말없이 `version_type: "comic"` 하나만** 발주했다. 화면에 선택지가 없어서
운영자는 "3가지 버전이 다 만들어지는 건가?"를 알 수 없었다.

- ④ 에 체크박스 3개(만화식·설명판형·실사형). **기본은 만화식 1건 = 예전 동작**이라 비용이 저절로 늘지 않는다.
- 버튼 라벨에 건수를 박는다: `승인하고 ⑤ 지시서 만들기 (N건) →`. 0건이면 비활성.
- 라우트가 `version_types: string[]` 를 받는다(단수 `version_type` 은 호환 별칭으로 유지 —
  `ReportDirectiveClient` 가 아직 단수로 부른다). 버전별로 중복 요청을 접고 결과를 배열로 돌려준다.
- 이미 승인(발행)된 대본에는 그 버튼이 없으므로 체크박스도 감춘다 — 그 경우 ⑤ 화면의 버전 탭에서 고른다.

### 6-1. 논문 ④ 도 같은 구조로 (`web/components/ReviewClient.tsx`)

논문 ④ 에는 [승인] 하나뿐이라, 승인하고 → 배너 링크로 ⑤ 로 가서 → 거기서 버전을 고르고 →
생성을 또 눌러야 했다. 리포트와 같게 맞춘다:

- ④ 에 체크박스 3개(만화식·웹툰·실사형), 기본 **만화식 1건**.
- 버튼 두 개: `[승인만]`(예전 동작 — 승인만 하고 이 화면에 남는다) / `[승인하고 ⑤ 지시서 만들기 (N건) →]`.
- 발주는 기존 `/api/directive-generate` 의 `version_types` 를 그대로 쓴다(라우트 변경 없음).
- 승인 확인 모달 문구를 "지시서는 만들지 않습니다 — ⑤ 에서 따로 발주"로 고쳤다(이제 [승인만] 전용이다).

### 6-2. 논문 ⑤ `VersionOrderBar` 기본 체크 — 전 버전 → **만화식 하나**

예전 기본은 제공 버전 **전부** 체크였다(나란히 비교가 목적). 버전이 2개에서 3개로 늘면서,
아무것도 손대지 않고 [선택한 버전 만들기]를 누르면 지시서 3벌이 생성되고 이미 초안이 있던
버전은 곧바로 승인 → 렌더(=돈)까지 갔다. 운영자 요청("내가 체크해서 진행하게")에 맞춰
기본을 만화식 하나로 줄인다 — 비교하려면 체크를 늘리면 된다(안내 문구도 그렇게 고쳤다).

**되돌리려면:** `useState(() => new Set([DEFAULT_VERSION_KEY]))` 를
`useState(() => new Set(slots.map((s) => s.key)))` 로.
