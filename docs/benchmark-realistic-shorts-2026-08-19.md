## 제목 문법 (인기 40편)

**신비한 건축사전** — 반전 평서문 + 숫자 + 한국 지명.
- 한국 지명·역사 23/40 ("서울 한복판", "경복궁", "한강", "강화도", "남한산성")
- 숫자 포함 18/40 ("철문 78개", "쓰레기 9200만 톤", "풍차 1만 개", "125년")
- 반전어 15/40 ("사실은", "일부러", "…없이", "거꾸로", "안 무너진")
- "~습니다" 평서문 종결 12/40, "…이유" 11/40
- 예: *"서울 한복판 억새밭, 사실은 쓰레기 9200만 톤 위에 떠 있습니다"*(453만),
  *"한강이 강이 아니라 호수인 이유"*(494만), *"경복궁 마당은 평평해 보이지만 사실 평평하지 않습니다"*(365만)

**이런거지** — "원리/구조" 명사형 + "천재적인" + "진화".
- 원리/구조 16/40, 천재적인 12/40, 진화 10/40
- 예: *"물속 다리 기둥을 세운 천재적인 해결법, 코퍼댐 공법의 진화"*(1,350만),
  *"대문 잠금 장치의 천재적인 진화"*(1,136만)

## 제작법 (튜토리얼이 공개한 것)

1. **기획**: 잘 된 영상 URL 을 Gemini 에 넣어 "왜 잘 됐나"를 분석시킨다. 핵심은 **예측 오류** —
   "한강은 강이지"라는 상식을 "사실 호수"로 뒤집는다. 구조: 문제 제기 → 왜? → 예측을 깨는
   원인 → 해결 메커니즘 → 결론. 마술처럼 한쪽을 보게 하고 다른 쪽에서 답이 나온다.
2. **대본**: LLM 이 초안 → 사람이 "인간미 있게" 고침 → **팩트체크를 LLM 에 다시 시킨다**
   ("숫자 하나 틀리면 댓글에서 바로 잡힌다"). 우리 Fact Sheet 불변식과 같은 문제의식.
3. **영상**: **이미지 단계 없이 영상 프롬프트로 바로** 생성(Google Flow / Veo 계열 "옴니플래시",
   9:16, 8초). 10~12컷. 8초를 뽑아 **좋은 3초만 쓴다**. 한 컷에 2~3샷을 넣는 "멀티샷"으로
   같은 크레딧에 화면을 3배로. 카메라: 8초에 비트 2개, 횡이동 + 마지막 급속 푸시인, 붉은 계측선.
   **연속성은 추구하지 않는다** — "영상 내 일관성이 유지되지 않는 것을 체감했다"고 명시.
   텍스트 깨짐도 "잡지 않는다"("잡을 시간에 다음 편을 만드는 게 이득").
   비용: 편당 약 3,500~4,200원(크레딧 환산).
4. **목소리**: 타입캐스트(필제 등 — "잘 되는 채널 목소리가 거의 다 여기 있다").
5. **편집**: 캡컷/프리미어. 규칙 둘 — **말이 끝나는 지점에서 장면 전환**, **자막 필수**(무음 시청).
6. **운영**: "핵심은 업로드 주기". 반복 작업은 에이전트 스킬로 자동화하라고 권한다 — 우리
   파이프라인이 정확히 그것이다.

## 우리가 따라가지 않기로 한 것 (의도적)
- **가짜 숫자 방치**: 벤치 채널은 건축 상식이라 숫자 오류가 "댓글에서 잡히는" 수준이지만,
  우리는 증권사 리포트 수치다. 화면 숫자 = Fact Sheet 숫자여야 한다(컴플라이언스).
- **연속성 포기**: 같은 편 안에서 피사체가 바뀌는 것을 그들은 감수한다. 우리는 개선 3번(앞 컷
  이미지를 참조로 전달)을 하기로 했고, 실사형에서 그 효과가 가장 크다.

## 뒤늦은 반영 (2026-09-04) — 이 문서의 제작법이 계약으로 간 것은 47일 뒤였다

§46-3 이 공개한 카메라 문법("8초에 비트 2개, **횡이동 + 마지막 급속 푸시인**")은
위 표에 **반영 항목으로 적히지 않았다.** 컷 길이·숫자 금지·훅 문형은 갔는데 그것만 빠졌다.

그 사이 두 번 더 같은 신호가 왔는데 둘 다 흘려보냈다:
- **G2 달 클립 실측(8/31)**: 좋았던 8초 팔의 비트가 `DOLLY_OUT → TRACK → DOLLY_IN` 에
  마지막이 `IMPACT` 였고, 화면에 실제로 나타난 구간도 그 `TRACK` 이었다.
  그런데 `docs/실측_품질/G2/결과.md` 는 **결함만** 정리했다("세계를 버린다", "글자가 박혔다").
  잘된 쪽 기록은 "배선이 끝까지 작동한다" 한 줄뿐이고, **"이런 비트가 좋은 비트다"로는
  가지 않았다.**
- **TC-1 구현(9/3)**: `min_beats`·`camera_plan`·`state_change` 를 **필드 존재**로만 검사하게
  만들었다. `HOLD`("카메라가 가만히 있다")도 "카메라 계획 있음"으로 통과했다.

결과: 9/3 첫 실사형 렌더의 invest 컷 둘이 `APPEAR + HOLD` ×2 로 **계약을 100% 만족하면서
아무것도 움직이지 않았다.** 운영자 지적("역동적으로 움직이면서 원리를 설명해야 한다")이
정확히 이 지점이었다.

**교훈: 좋은 샘플에서 결함만 뽑고 성공 조건을 안 뽑으면, 계약은 최저선으로 내려앉는다.**
막을 것 목록과 **요구할 것 목록**은 다른 문서다.

지금 계약(`engine/temporal_plan.evaluate`, invest 한정):
- 카메라 중 최소 하나는 `HOLD` 가 아니어야 한다 (`temporal_camera_never_moves`)
- 비트마다 카메라가 달라야 한다 — 멀티샷 (`temporal_camera_monotone`)
- 변이 중 최소 하나는 실제 변형이어야 한다 (`temporal_no_transforming_mutation`)
  — `config.TRANSFORMING_MUTATIONS`, `APPEAR`·`HIGHLIGHT`·`DIM` 은 제외
- 달 클립의 비트를 프롬프트에 **실측 예시로** 박았다(`TEMPORAL_CONTRACT_GUIDANCE`).

`standard`·`economy` 는 종전 그대로다 — 여기까지 조이면 대부분이 강등된다.
