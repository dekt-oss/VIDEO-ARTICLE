## 사용자가 확정한 핵심

1. ‘오늘’은 **오늘 할 일**로 바꿉니다. 현재 승인·검수·예약·문제 확인 작업과 주간 진행을 보여 줍니다.
2. **소재 고르기 → 만들 형식 복수 선택 → 형식별 대본·영상화 기획 → 각자 제작·게시**입니다.
3. 릴스·밈·카드뉴스는 단일 선택이 아닙니다. 소재 하나에서 1~3개를 함께 고릅니다.
4. 소재·근거는 공유할 수 있지만, 형식별 기획·버전·승인·제작·게시 상태는 독립적입니다. 릴스만 승인하거나 카드만 먼저 게시할 수 있어야 합니다.
5. 작업공간 상단에 선택한 형식과 각각의 진행 상태를 보여 줍니다. 형식을 바꾸어도 진행·입력이 사라지면 안 됩니다.
6. 릴스는 설명형 영상의 대본·장면 구성, 밈은 짧은 글·반전·박자, 카드뉴스는 표지·페이지별 기획입니다.
7. 기본 카드뉴스는 넘겨 보는 카드 게시물입니다. 기존 카드 릴스를 별도 게시 옵션으로 제공하는 안은 목업 제안이므로 실제 지원과 도입 여부를 확인하세요. 이 옵션 때문에 기본 복수 선택 작업을 중단하지 마세요.

## 반드시 유지할 규칙

- 내용 승인 ≠ 결재 ≠ 제작 시작 ≠ 공개 게시 승인 ≠ 예약. 한 번의 클릭으로 묵시적으로 합치지 마세요.
- 설명형 후보 합격/불합격, 선택 이유, 조립, 과정 3항목, 품질 6항목, 산출물 승인을 유지하세요. 실제 항목은 `web/lib/drinks/explainerQueue.ts`에서 확인하세요.
- 설명형 ‘AI 생성 영상’ 문구, 카드 릴스 필수 음원, 예약 시간 07:00~23:30, 버전·승인 지문·근거 유효성 검증을 유지하세요.
- 박자 밈은 앱에서 음원을 붙여 게시한 뒤 URL을 기록합니다. 웹에서 자동 게시하지 않습니다.
- 밈의 카드 기반/소재 기반 출발과 기존 이력을 보존하세요. Apify 정밀 분석·비용 통제를 우회하지 마세요.
- 생성 비용은 형식별·선택 합계로 표시하고, 공통 근거 재사용이 자동으로 무료라는 가정을 하지 마세요.

## 먼저 확인할 기술 간극

실제 root·remote·HEAD·dirty, PR #142 이후 수정과 충돌 파일을 확인하세요. 이전 리뷰 당시 로컬 HEAD는 48d5f1c였고 PR 최신은 a760a5bd였으므로 현재 상태로 재검증해야 합니다.

기존 형식 의도가 단일값일 수 있습니다. 체크박스만 복수로 바꾸거나 `pick_topic`을 여러 번 호출해 덮어쓰지 마세요. 형식별 작업 식별·멱등성·부분 실패·비용·기존 데이터 호환을 확인한 뒤 최소 변경안을 정하세요. 공동 근거 변경이 각 계획에 미치는 영향도 명시하세요.

간극을 파일:줄 근거로 짧게 보고하고, 이미 합의한 범위는 로컬에서 계속 구현하세요. 화면 의미 변경, 승인/결재 완화, 데이터 삭제·소유권 일괄 전환 같은 추가 결정은 임의로 하지 말고 영향과 대안을 제시하세요.

## 구현·검증 순서

1. 실제 코드와 기획/목업을 대조하고 필요한 최소 작업 계획을 정리.
2. 소재 복수 선택과 형식별 작업·상태 보존부터 구현.
3. 기존 레인·검수·게시 기능을 같은 작업공간으로 연결. 목적지가 준비된 뒤 메뉴·옛 주소 전환.
4. 작업명세서의 검증 사례를 실제 action/payload·버전·DB 전이 기준으로 확인. 가짜 공급자·로컬 DB만 사용.
5. 390px·1280px 화면과 주요 사용자 경로를 직접 확인. 신규 migration이 테스트 로더에 포함되는지도 검증.
6. 최종 결과 → 수행 작업 → 변경 파일 → 리뷰/조치 → 실행 검증 → 미검증/위험 순서로 보고하고 운영 적용 전에 멈춤.
