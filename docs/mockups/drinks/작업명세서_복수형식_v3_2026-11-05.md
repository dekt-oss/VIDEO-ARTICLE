## 2. 구현 전 확인해야 할 간극

이전 리뷰에서 `drink_topic_picks`의 형식 의도가 단일값으로 관찰됐다. **복수 선택을 프런트 체크박스만 바꾸거나 pick_topic을 세 번 호출해 해결한다고 가정하지 말 것.** 최신 HEAD에서 실제 계약을 다시 확인한다.

- 한 소재 아래 형식별 선택·계획·버전·승인·작업을 어떻게 식별하는가?
- 두 번째 선택이 첫 번째 선택·승인·예산을 덮어쓰지 않는가?
- 같은 소재의 공통 근거 재사용 범위와 각 형식의 주장 검증은 무엇인가?
- 선택 3건 중 1건이 실패하면 성공·대기·실패를 형식별로 어떻게 표시·재시도하는가?
- 다시 누르기·중복 요청이 중복 생성·중복 청구를 일으키지 않는가?
- 공통 근거가 변경될 때 어떤 형식의 어떤 버전이 무효화되는가?
- 기존 단일 형식 소재와 카드 기반 밈의 제작·게시 이력을 어떻게 계속 보여 주는가?
- 카드뉴스 캐러셀과 카드 릴스를 현재 API·엔진이 각각 지원하는가? 부가 옵션 제공 여부는 사장님 확인 항목이다.

위 질문에 파일:줄 근거와 최소 변경안을 제시한다. 미확인 운영 상태는 추정하지 않는다. 상세 DB 설계는 이 문서에 임의 확정하지 않는다.

## 3. 구현 순서

1. **현황 확인:** root/remote/HEAD/dirty, PR #142 및 이후 변경, 실제 상태·승인·형식 계약 확인. 기존 동시 작업 보존.
2. **간극 보고:** 복수 선택에 필요한 변경과 기존 기능 재사용 범위, 영향을 받는 파일, 테스트 계획을 정리. 화면 합의와 다른 결정만 질문.
3. **로컬 구현:** 기존 결재·권한을 유지하며 소재 선택→복수 형식 기획→각 레인의 현재 행동을 연결. 테스트용 데이터·가짜 공급자만 사용.
4. **형식별 회귀:** 설명형 검수, 카드 출력·음원, 밈 수동 경로, 게시 승인·예약의 독립성을 검증.
5. **전환:** 목적지 기능이 준비된 뒤 기존 링크를 전환한다. planId→topicId·형식·과거 버전을 보존한다.
6. **인계:** 구현 결과·테스트·미검증·운영 적용이 필요한 일을 보고. 배포·운영 적용은 별도 승인 전 실행하지 않는다.

## 4. 필수 검증 사례

- 복수 선택의 7개 조합과 선택 0개 차단. 추천 형식을 바꾸는 사례.
- 동일 소재 릴스+카드 선택 → 두 기획 존재 → 릴스만 승인 → 카드 미승인 유지 → 카드만 먼저 게시.
- 세 형식 중 하나 실패 → 나머지 상태 보존 → 실패한 형식만 재시도, 중복 작업 없음.
- 레인 전환·새로고침·다른 탭 변경 시 최신 버전·미저장 내용 충돌을 명확히 표시.
- 공통 근거 변경 → 영향받는 계획의 기존 승인으로 제작·게시 불가.
- 후보 자동·사람 검수 합격 + 선택 이유 없이는 확정 불가. 과정 3항목·품질 6항목·산출물 승인 유지.
- 카드 캐러셀과 카드 릴스 구분. 카드 릴스 음원 누락, 설명형 AI 문구 누락, 07:00 이전/23:30 이후 차단. 경계 시각 허용.
- 게시 draft→submit→approve→schedule 및 버전·digest 검증. 버튼 이름만 비교하지 않음.
- 밈 두 출발점, 앱 게시 URL 기록, 웹 자동 게시 미노출, 기존 Apify 비용 한도 유지.
- 조회 실패/미실행/부분 조회/정상 0건 구분. 전체 후보 페이지네이션과 전역 필터 확인.
- DB 테스트가 신규 migration을 실제 로드하는지 확인. 기존 005x/006x 제한 로더의 누락 주의.

## 5. 금지·승인 경계

실제 유료 LLM·영상·이미지·Apify 호출, 운영 DB 접속·변경, migration 운영 적용, 공개 게시, 크론 활성화, 커밋·푸시·PR·머지·배포는 별도 승인 없이는 하지 않는다. 비밀값 출력과 `.env`의 시험 로드를 금지한다.

현재 목업의 버튼은 전부 가짜다. 모형 영상, 체크된 검수, 고정 달력을 실제 품질·게시·운영 증거로 사용하지 않는다. 논문·리포트 공장의 공통 컴포넌트 추출이나 관련 없는 리팩터링은 범위 밖이다.
