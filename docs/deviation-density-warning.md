# 편차 기록 — "읽기 부담" 경고를 씬마다에서 편당 1건으로 (2026-08-19)

## 무엇을 바꿨나
`engine/report_evidence.validate_text_density` 가 씬마다 내던 경고
`narration_too_long_for_cut`(= "그 컷 길이 안에 다 읽을 수 없는 나레이션입니다")을 **없애고**,
편당 1건의 `duration_estimate_off`(= "계획한 길이와 나레이션 길이가 다릅니다 — 영상은
나레이션 길이로 나갑니다")로 바꿨다.

작업지시서 v3 §6(텍스트 밀도)의 **목적**은 유지한다: 화면이 소화 가능한가. 한 씬에 소리 내
읽는 숫자가 너무 많은지 보는 `too_many_numbers_in_scene` 은 그대로다.

## 왜
1. **검사 대상이 렌더에 존재하지 않았다.** 조립은 초안이 적어 둔 `duration_sec` 를 쓰지 않고
   **나레이션 실측 길이**로 컷을 만든다(`engine/assemble.py:119` — "duration 은 나레이션
   실측(ffprobe)"). 즉 "나레이션이 duration_sec 안에 안 읽힌다"는 조건은 완성 영상에서
   성립할 수 없다.
2. **그래서 사실상 항상 켜져 있었다.** 최근 리포트 초안 12편을 실측하니 **12편 전부**에서
   경고가 났고, 씬 평균 6.6개 중 5.75개가 빨간 줄을 받았다. 같은 편의 완성 영상은
   43~59초로 정상 재생됐다(계획은 25~30초).
3. 항상 켜진 경고는 신호가 아니라 소음이다. 같은 패널에 있는 진짜 경고(근거 수치 부족,
   Fact Sheet 에 없는 근거 참조)까지 같이 무시하게 된다 — 운영자가 ④ 에서 멈추는 이유 중
   하나였다.

## 대신 무엇을 보는가
`STORY_SPEAK_CHARS_PER_SEC`(기본 7.6자/초)로 계산한 **발화 기준 예상 길이**와 초안이 계획한
총 길이를 비교해, `STORY_DURATION_TOLERANCE`(기본 0.25 = 25%)를 넘게 어긋나면 한 줄로 알린다:

> 계획한 길이와 나레이션 길이가 다릅니다 — 영상은 나레이션 길이로 나갑니다. · 계획 25초 → 예상 43초

7.6자/초는 추정이 아니라 **실측**이다: 완료된 렌더 잡의 QA `cut_map`(컷별 실제 길이)과 그
컷의 나레이션 글자 수를 맞춰 68컷을 계산한 중앙값(평균 7.56, 범위 5.9~8.7, KO/edge-tts).
재현:

```bash
python -m scripts.repro_phase0_board   # (참고) 보드 재현 스크립트
```

실제 계산은 `report_render_jobs.qa.cut_map` 과 `report_directives.cuts[].narration_ko` 를
맞춰 보면 된다.

## 트레이드오프
- 잃는 것: 씬 단위 지목. 어느 씬이 특히 긴지는 더 이상 표시하지 않는다. 다만 그 정보는
  렌더 결과와 무관했으므로 실질 손실은 작다.
- 얻는 것: ④ 화면의 경고가 다시 "볼 만한 것"이 된다. 그리고 **계획과 실제 길이의 괴리**라는,
  지금까지 아무도 보지 못하던 진짜 사실이 화면에 나온다(계획 25초인데 영상은 47초).

## 되돌리는 법
`STORY_DURATION_TOLERANCE` 를 아주 크게 두면(예: 99) 이 경고는 사실상 꺼진다.
씬 단위 경고를 되살리려면 `validate_text_density` 안에서 예전 비교
(`len(narration)/STORY_READ_CHARS_PER_SEC > duration_sec`)를 복원하면 된다 —
다만 위 1·2의 이유로 권하지 않는다.
