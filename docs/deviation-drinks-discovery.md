# 주류 공장 B 보완 — 커뮤니티·SNS 소재 발견 (2026-10-22)

기반: B단계(`docs/deviation-drinks-phase-b.md`, PR #122). 마이그레이션 `0052_drinks_discovery.sql`(0051 위, 어디에도 미적용).

## 무엇을 만들었나

사실 근거와 **다른 표**에 "소재 발견 자료"를 둔다 — 사람들이 무엇을 궁금해하는지의 신호이지 근거가 아니다.

| 표 | 내용 |
|---|---|
| `drink_discovery_items` | 원문 URL·플랫폼·채널/커뮤니티·제목·확보한 요약(600자)·발견 시각·게시 시각(알 때만)·확보 범위·수집 상태(수집/수동)·권리 확인 상태·질문 문장(원문)·신호 |
| `drink_discovery_observations` | 공개 지표 관측(append-only). **제공된 지표만** — 미제공은 키가 없다(0 으로 채우지 않음) |
| `drink_discovery_candidates` | 규칙(discovery-v1)으로 묶은 후보 카드. 임시 점수·점수 이유·기준 버전 |
| `drink_candidate_items` | 자료 하나는 후보 하나에만(같은 자료로 여러 후보를 부풀리지 않음) |

화면 `/drinks/discover`: 채널 연결 상태 · 발견 수집원 · 후보 카드(열린/올림/기각/합쳐짐) · 아직 안 묶인 자료 · 수동 등록 · 발견 채널 등록.

## 후보 카드 — 규칙(LLM 0회)

- 신호: 질문·논쟁·오해·선택 고민·보관·신제품·행사(한·일·영 낱말 규칙). 질문 문장은 **원문 그대로**(번역·요약 안 함), 주소 조각·두세 단어 조각은 버린다.
- 묶기: 흔한 낱말·주종 이름을 뺀 낱말 Jaccard ≥ 0.34 + 겹친 낱말 2개 이상, 또는 같은 본문(전재). 판정이 아니라 제안 — 합치기·기각은 운영자.
- 관심 신호: **독립 출처 수**(같은 원출처 묶음·같은 본문 전재·같은 채널은 하나로) + 플랫폼별 지표 최댓값. **플랫폼끼리 더하지 않는다.**
- 카드: 핵심 질문(원문) / 독자 효용 / 발견 경로 / 관심 신호 / 첫 장면 제안("[규칙 제안]", 연출 장면 표기) / 영상·카드 적합성 / 추가 확인할 사실 / 중복 후보 소재.
- 임시 점수 discovery-v1 = 질문 신호 25 + 독립 출처(최대 4곳) 40 + 신호 종류(최대 3) 15 + 형식 적합 20. 이유 문장을 같이 저장한다. **승인·편성과 무관.**

## 후보 → 소재

운영자가 한국어 제목·질문을 **새로 쓴다**(남의 글을 옮기지 않고 술째리고의 질문·설명 각도로). 발견 자료는 URL만(metadata_only)
**질문·인기 신호(discovery)** 로 붙는다. A단계 규칙상 metadata_only·discovery 는 근거가 될 수 없다 — 근거로 쓰려 하면 저장이 거부된다(테스트).
근거는 공식·전문 원자료를 따로 등록해 발췌 대조·지지 검토를 탄다.

## 질문 신호를 소재와 전략까지(2026-10-28)

근거: `docs/리뷰_주류소재수집_2026-10-28.md` §4-2·§4-4·§5·§6. 전부 0원이고 LLM 호출이 없다.

**무엇을 바꿨나(세 가지)**
1. **한국어 질문 인식** — 네이버 검색 요약은 물음표가 잘려서 질문이 비던 문제. `인가요·일까요·할까요·나요·까요·건가요·는지·궁금` 등(`config.DRINKS_QUESTION_ENDINGS_KO`)으로 끝나는 한글 6자 이상 문장도 질문으로 친다. 물음표 규칙은 그대로.
2. **소급 일수 + 질문 일괄 등록** — 발견 수집원마다 `lookback_days`(1~3650)를 줄 수 있고 없으면 전역 365일(Stack Exchange 는 최근 1년이 0건이라 필요). `scripts/drinks_bootstrap_topics.py` 가 CSV 의 질문을 대시보드 [직접 등록]과 같은 DB 함수로 등록한다(기본 미리보기, `--apply` 로 실제 등록, 같은 질문은 한 번만).
3. **질문 신호가 소재·전략까지** — 마이그레이션 `0058_drinks_topic_signals.sql`: 소재에 `question_kind`(보관·오해·선택·논쟁·페어링·방법·일반)·`discovery_platforms`·`interest` 를 더하고, 후보를 소재로 올릴 때 복사한다. 전략 묶음에 "질문 유형"이 늘고 편성 순서 가점에도 붙는다. 문턱(묶음 3편·전체 6편·±0.2·±0.5)은 그대로.

**운영 DB 적용은 운영자 승인 뒤**다. 순서: ① 0058 적용 → ② 웹 배포(질문 유형 선택칸·태그). 거꾸로면 화면이 보낸 `question_kind` 를 옛 함수가 조용히 무시한다(오류는 없지만 저장 안 됨). 전략 제안(`python -m engine.drinks_strategy`)도 0058 뒤에 돌린다. 되돌리기는 0058 머리말에 있다.

**운영자가 손으로 할 일**
1. GitHub 저장소 시크릿 `NAVER_CLIENT_ID`·`NAVER_CLIENT_SECRET` 등록(술째리고 API HUB 키).
2. `/drinks/discover` 에서 네이버 수집원 등록(검색어 예: 사케 보관, 위스키 입문 추천, 막걸리 유통기한) → [검증 실행] → 이용 조건 확인 → 활성.
3. 상시 지식 질문 30개를 `docs/drinks-bootstrap/questions_template.csv` 형식으로 쓴 뒤 `python -m scripts.drinks_bootstrap_topics 파일.csv`(미리보기) → `--apply`(`SUPABASE_URL`·`SUPABASE_SERVICE_KEY` 필요).

**확인한 것** 파이썬 전체 3168 통과, 웹 node 테스트 260 통과(PGlite 실제 Postgres 문법으로 복사·가점·검증), `tsc`·`lint` 통과.

**(미검증)** ① 실제 네이버 응답에서 끝말 규칙이 질문을 얼마나 잡는지(테스트는 모양을 흉내 낸 문장 5개). ② 전략 효과 — 게시 6편이 쌓이기 전에는 "표본 부족"만 나오고, 질문 유형 가점은 그 뒤에야 의미가 있다. ③ 운영 DB 에 0058 을 올린 결과.
