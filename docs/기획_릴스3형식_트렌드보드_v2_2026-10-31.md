## 2. 세 형식 공통 원칙

### 2-1. 화면 규칙 (v1 유지)
- 시청 유지: 첫 1.5초 안에 가장 강한 장면 + 상단 훅 자막.
- 무음 시청: 자막 없이 이해 안 되는 장면 0개.
- 원본성: 남의 영상·소리를 잘라 붙이지 않는다. 밈은 형식만 빌린다.
- 공유: 마지막에 "보낼 이유" 한 줄.
- 순위 신호(시청 유지·공유·도달 대비 좋아요·원본성)는 업계 글 기준이다. **1차 출처 미확인**이라 화면 규칙의 참고로만 쓰고 합격 기준으로 쓰지 않는다.

### 2-2. 형식별 길이·자막 규칙 (최종 영상 기준, 1.2배속 후)

| 형식 | 길이 | 화면 바뀜 | 자막 |
|---|---|---|---|
| 설명형 | **40~55초(목표 45~50초)** | 편집 컷 2~4초(한 컷 최대 4.5초) | 상단 훅(첫 컷만, 위 20~25% 높이) + 하단 뜻 단위 말 자막 + 핵심 낱말 강조색 |
| 카드뉴스 릴스 | 15~30초 | 페이지당 2.5~4초 | 첫 페이지 큰 훅 제목, 하단 말 자막 없음(나레이션 없음이 기본) |
| 밈형 | 6~15초 | 밈 틀이 정함 | POV 상단 / 가운데 큰 글자 / 전·후 좌우 중 틀이 정함 |

**설명형 길이 정정 (2026-10-31, 운영자 지적: 30초로는 설명이 안 되고, 옛 공장을 보면 최소 40~50초는 돼야 한다)**
- 처음 v2 의 "20~35초"는 근거가 없었다. 소재 개발 엔진 0단계에서 제가 정한 대본 범위(`DRINKS_DEVELOP_SECONDS` = 배속 전 30~40초, `config.py:4625`)를 그대로 옮긴 것이고, 운영자가 정한 값이 아니다.
- [기존 실측] 옛 공장(논문·리포트) 완성 렌더 47편의 최종 길이: 최소 32.9초 · **중앙값 50.4초** · 최대 85.8초(`render_jobs.qa.signals.duration_sec`, 2026-10-31 조회).
- [기존 실측] 유튜브에 올린 23편은 전부 40초 이상이었다. 길이 구간별 평균 시청 비율: 40~54초 29% · 55~69초 41% · 70초 이상 49%(`youtube_analytics` 최신 스냅샷). ★ 조회수가 편당 수십 회로 작고 플랫폼이 유튜브 쇼츠라, "길수록 낫다"는 증거가 아니라 **"40초 이상이 불리하다는 증거는 없다"** 정도로만 쓴다.
- [기존 운영자 결정] V2 엔진 때 "완성도와 이해를 위해서라면 100~120초까지도 갈 수 있다. 억지로 늘릴 필요는 없다"(`config.py` `V2_TARGET_MIN_SEC=45`).
- 그래서 설명형은 **40~55초, 목표 45~50초**로 한다. 단 **근거가 모자라면 늘리지 않는다** — 원문 근거 없이 채운 문장은 금지다(대본에 처방을 지어내지 않기). 근거가 40초 분량에 못 미치면 그 소재는 보류한다.
- 말 속도 기준: [신규 실측] 위스키 초안 4판은 최종 영상 기준 **초당 5.9음절**이다(158음절 ÷ 26.7초). 운영자 승인값과 같다. 48초면 약 280음절, 지금 대본의 **1.8배**다.
- [신규 실측 2026-11-01, Apify 1단계] 인스타 설명형 계정 16곳에서 계정마다 최근 릴스 30개 중 조회수 상위 10개와 가운데값 아래 5개를 골라 재생 길이를 받았다(202개 중 171개 성공, 비용 최대 $0.53).
  - 과학·설명 7개 계정의 **인기 상위 69편: 가운데값 69초**(아래 4분의 1 46초 · 위 4분의 1 91초). 같은 계정의 하위 33편은 가운데값 36초.
  - 같은 계정 안에서 상위 릴스가 하위보다 길었던 계정이 7곳 중 5곳이다(17~53초 더 김). 예외 둘 중 하나가 **3D 해부 도해로 우리 기전 장면과 가장 비슷한 zackdfilms** 인데, 상위·하위 모두 28~52초(가운데값 32초)다.
  - 16개 계정 전체에서 조회수 상위 30편의 가운데값은 **46초**다.
  - 해석: 40~55초(목표 45~50초)는 인기 설명형 릴스 분포의 가운데에 든다. 근거가 충분하면 60초를 넘겨도 불리하다는 증거는 없다. 다만 **우리와 형식이 가장 비슷한 계정은 30~40초대로 잘 된다** — 근거가 40초에 못 미치는 소재를 "보류"하는 규칙은 다시 볼 여지가 있다(운영자 판단 사항).
  - ★ 조회수는 인기의 대리 지표일 뿐 시청 유지율이 아니다. 경쟁 계정의 유지율은 어떤 경로로도 볼 수 없다.
  - ★ **술 계정 릴스는 연령 제한으로 길이를 못 받았다**(masterofmalt 0/9 · dailyshot 0/15). 위 숫자에는 술 설명형이 거의 없다. 상세: `docs/검토_Apify도입_2026-11-01.md`.

### 2-3. 안전 영역 — 숫자를 정하는 것과 실제 앱에서 확인하는 것을 나눈다
- **설계값(가설):** 1080×1920 기준 아래 340px, 오른쪽 120px 를 비운다. 훅 자막은 위 20~25% 높이에 둔다. **[미검증]** — 업계 관행값이다.
- **자동 검사(0원):** 렌더가 자막·카드의 실제 그림 위치(ASS 위치 → 픽셀 상자)를 계산해, 설계값 안전 영역을 벗어나면 막는다.
- **실제 앱 확인(0원, 운영자 손 작업, 1회):** 안전 영역 안내선을 그린 시험 영상(게시 안 함)을 휴대폰으로 보낸다. 인스타 앱의 릴스 만들기 화면에 올려 **게시하지 않고** 미리보기에서 버튼·캡션에 가려지는지 본다. 스크린샷 3장(맨 위·가운데·맨 아래)을 남기고 설계값을 확정한다. 앱 버전과 날짜도 함께 적는다.

### 2-4. 제작 합격과 성과 평가는 다른 것이다
- **제작 합격**(게시 전): 자동 검사(§3-8) + 사람 검수(§3-8). 통과해야 게시 대기열에 들어간다.
- **성과 평가**(게시 후 7일): 조회·평균 시청 시간·공유·저장(인사이트 권한으로 읽기). 같은 형식끼리 비교하는 **참고 지표**다.
- 성과가 나쁘다고 제작 합격을 거꾸로 취소하지 않는다. 성과는 다음 편의 설계 변경 근거로만 쓴다.
- 성과 기준 숫자는 우리 계정 표본이 10편 쌓이기 전에는 정하지 않는다.

### 3-3. 생성 자산·후보·시도 데이터 계약 (항목 3)

자산은 **슬롯 → 후보 → 시도** 3단으로 나눈다. 편집 컷은 별도 표다(§3-6).

| 이름 | 키 | 필수 필드 | 비고 |
|---|---|---|---|
| 자산 슬롯 `slot` | `slot_id` = `{plan_id}:A{n}` | `role`(reality/mechanism), `spec_hash`(모델·문장·시작 그림 해시·길이·해상도), `min_src_ms`(편집 컷들이 이 자산에서 쓰는 가장 늦은 끝 지점 + 여유 200ms), `candidates_planned`(1 또는 2), `boundary_in`/`boundary_out`(§3-5), `status` | 장면당 하나 |
| 후보 `candidate` | `candidate_id` = `{slot_id}#c{k}` (k=1,2) | `seed`(공급자가 받으면), `status`, `cost_usd`(시도 합계), `auto_verdict`, `human_verdict`, `asset_id`(받은 파일) | 후보마다 **별도 item_key** — 0054 의 "항목당 3회" 상한이 후보마다 따로 걸린다 |
| 시도 `attempt` | `attempt_id` = `{candidate_id}#a{m}` | `idempotency_key` = sha256(`attempt_id` + `spec_hash`), `provider_request_id`, `hold_id`, `state`, `billed_units`, `actual_usd`, `error_code` | 공급자 호출 **전에** 행을 만든다 |
| 선택 `selection` | `slot_id` | `selected_candidate_id`, `selected_by`, `selected_at`, `reason` | 사람만 고른다. 자동 점수는 정렬용 참고값이다. |

**재사용 규칙**
- `buy()` 의 `prompt_hash` 재사용을 설명형에서는 이렇게 바꾼다.
  - 다시 쓰는 것은 "**이 슬롯에서 이미 선택된 자산**"뿐이다. 재렌더·언어 추가가 여기에 해당한다.
  - 새 후보를 채우는 데에는 캐시를 쓰지 않는다.
  - 캐시 키에 `candidate_id` 를 넣어, 후보 1·2가 같은 파일로 합쳐지지 않게 한다.

**요청 멱등성**
- 시도 행은 `requested` 로 만든 **뒤에** 공급자를 부른다.
- 같은 `idempotency_key` 로 두 번 부르지 않는다.
- 호출을 보낸 뒤 응답 없이 워커가 죽으면 그 시도는 `unknown_billed` 가 된다.
  - 자동으로 다시 부르지 않는다.
  - 공급자에 요청 ID 로 조회할 수 있으면 조회로 정정한다(②의 작업 이름).
  - 조회가 안 되면(①은 동기 호출이라 조회할 ID 가 없을 수 있다 [미검증]) 운영자가 보고 `billed`(청구된 것으로 처리) 또는 `void`(없던 일로 처리)로 닫는다.
  - 닫기 전에는 같은 후보로 새 시도를 만들 수 없다.

**시도 상태:** `requested → generating → received → probed(ffprobe 실측) → stored`. 실패 쪽은 셋이다.
- `failed_unbilled`: 생성 전에 거절됨. 같은 후보로 재시도할 수 있다.
- `failed_billed`: 만들어졌는데 받기·검사에서 실패. 비용을 기록하고, 재시도는 새 결재 금액 안에서만 한다.
- `unknown_billed`: 위 설명대로 처리한다.

**재시도 상한:** 후보당 2회, 슬롯당 합계 4회. 0054 의 항목당 3회보다 좁게 잡는다.

**후보 판정**
- **자동:** 길이 ≥ `min_src_ms`, 9:16, 정지 구간(§3-8 문턱), 검은 화면, 글자 나타남 의심(Jev 신호 — 참고만).
- **사람:** 시각 주장(§3-4) 위반 여부, 연속성(§3-5), 사진 느낌.
- 후보는 자동 통과 **그리고** 사람 통과일 때만 선택할 수 있다.
- **두 후보 모두 불합격이면 슬롯은 `no_pass` 가 되고, 편은 `blocked_no_pass` 로 멈춘다.** 선택지는 둘뿐이다. 둘 다 운영자가 고르고, 자동 진행은 없다.
  - 새 결재로 다시 찍기
  - 장면 계획 변경
- "그나마 나은 쪽"을 채택하지 않는다.

### 3-5. 연속성 — 계획된 시작 그림이 아니라 실제 클립으로 본다 (항목 9)

경계마다 종류를 지시서에 적는다.

| 경계 종류 | 뜻 | 자동 검사(0원) | 사람 검사 |
|---|---|---|---|
| `match` | 같은 세계가 이어진다(같은 잔·테이블) | 앞 클립 **실제 사용 구간 끝 프레임** ↔ 뒤 클립 **실제 사용 구간 첫 프레임**의 색 분포 거리, 밝기 차 | 같은 물건·같은 조명인가 |
| `cut_to_mechanism` | 실사 → 도해(단면) 의도적 전환 | 재질·색 분포만(무광 CG 화풍 공유 확인) | 같은 잔의 속으로 들어간 것으로 읽히나 |
| `flash_forward` | 훅 — 뒤에 나올 장면을 먼저 보여 줌 | 검사 없음(의도적 단절) | 뒤에서 같은 장면이 다시 나오나 |
| `loop` | 마지막 컷 끝 → 첫 컷 시작 | 마지막 프레임 ↔ 첫 프레임 색 분포·구도(잔이 화면 가운데 크게) | 다시 볼 때 자연스러운가 |

- `match` 경계의 뒤 장면 시작 그림은, 앞 장면에서 **선택된 클립의 실제 마지막 프레임**을 참고 그림으로 넣어 만든다(기존 `build_last_frame_command`).
- 그래서 `match` 로 이어진 장면은 **순서대로** 산다. 앞 슬롯이 선택돼야 뒤 슬롯 시작 그림을 주문할 수 있다.
- 자동 검사 문턱값은 첫 편에서 숫자를 기록만 하고(차단 아님), 운영자 판정과 맞춰 본 뒤 정한다. 사람 검사는 처음부터 필수다.

### 3-8. 검사 — 기계 검사와 사람 검수를 나눈다

**A. 최종 영상 자동 검사(렌더 끝, 0원, 실패하면 게시 대기열에 못 들어감)**
1. 규격: 1080×1920, 23~60fps, H.264/HEVC, AAC 48kHz 이하, 300MB 이하, 3초 이상.
2. 길이: 최종 40~55초(§2-2). 밖이면 차단한다.
3. 렌더 기록(manifest): 모든 편집 컷이 `kind=clip` + `asset_id` + 원본 구간을 가졌는가. 홀드·왕복·켄번스·스틸 항목이 0개인가. 사진 대체 기록(`VIDEO_FALLBACKS`)이 비었는가.
4. 정지: 최종 영상 freezedetect(노이즈 −55dB). **설명형은 정지 0.8초 이상이면 차단한다.**
   - 기존 3.0초·경고 설정은 설명형에 쓰지 않는다.
   - 0.8초는 첫 값이다. 클립 자체가 거의 정지한 장면(병이 놓여 있기만 함)은 사람 검수에서 다시 판정한다.
5. 검은 화면 0.3초 이상 0개, 소리 크기(loudnorm 목표 ±2 LU).
6. 자막 상자가 §2-3 안전 영역 안에 있는가. 상단 훅 자막이 0~1.5초에 있는가.

**B. 사람 검수 — 두 장으로 나눈다**
- **과정 검수**(돈 쓰기 전과 산 직후): 장면별 지시서 ↔ 시각 주장표(§3-4) ↔ 산 클립이 맞는가. 후보 선택 이유. 비용 합계 ↔ 결재 금액.
- **품질 검수**(최종 영상): 아래 6가지를 운영자가 판정하고 결과를 기록한다. 하나라도 불합격이면 게시하지 않는다.
  1. 첫 1.5초에 멈추게 하는가
  2. 사진처럼 보이는 장면 0개
  3. `match` 경계가 이어지는가
  4. 도해가 '왜'를 소리 없이 보여 주는가
  5. 가짜 글자·깨짐 0개
  6. 루프가 자연스러운가
- 자동 검사 통과는 품질 합격이 아니다. **G3 원칙대로 사람 판정 전에는 "돌아간다"고만 말한다.**

## 5. 밈형

- 입력: 밈 보드에서 [쓰자] 한 카드. 카드가 **정밀 틀**(§6-5 승격 조건 충족)이어야 밈형으로 넘어간다.
- 틀 구성: 비트 수, 비트별 길이, 자막 자리, 화면 종류, 음원 정보(`audio_id` 또는 없음), **동기화 등급**.
- **동기화 등급**
  - `sync_required`: 음원의 특정 박자·가사 지점에 반전이 맞아야 성립한다.
  - `sync_free`: 분위기용 배경 음악이라 어느 지점에서 시작해도 된다.
- `sync_required` 처리: Audio API 에 시작 위치 지정이 없으므로(§7) 자동 게시하지 않는다. 다음 둘 중 하나로 간다.
  - **수동 앱 부착**: 엔진이 음원 없는 영상 + "이 음원을 X초 지점부터" 안내를 만들어 주고, 운영자가 인스타 앱에서 붙여 게시한다. 게시 기록은 운영자가 링크로 등록한다.
  - **제작 보류**: 안내만 남긴다.
- 화면: 우리가 만든다.
  - 글자만 + 배경(0원).
  - 짧은 반응 장면: 클립 4초, ① 기준 약 $0.41 + 그림 $0.039. 사진+움직임은 여기서도 금지.
- 글: 정보 주장이 들어가면 근거 규칙을 그대로 탄다. 농담은 음주 조장·미성년·과음 미화 검사를 받는다.
- **틀 엔진 검증은 가짜 데이터로 한다(0원, 2주 관측과 무관).**
  - 손으로 만든 밈 카드 픽스처 6장으로 틀 → 글 → 렌더 → 자동 검사를 끝까지 돌린다.
  - 6장의 구성: `sync_free` 4장 / `sync_required` 1장 / 정보 주장 포함 1장(2026-11-02 운영자 확정, 종전 3 / 2 / 1).
  - `sync_required` 는 자동 게시가 막히는지까지 본다.
- 트렌드 보드 2주 관측은 **문턱값을 정하는 데만** 쓴다. 밈형 개발을 기다리게 하지 않는다.
- [신규 실측 2026-11-02, Apify 시험 2] 해외 밈 계정 4곳(9gag·pubity·memezar·daquan)의 인기 릴스 24편을 봤다. 상세: `docs/검토_Apify도입_2026-11-01.md` §6.
  - 길이 가운데값 **13초**(중간 절반 10~36초).
  - **24편 중 22편이 원본 소리**다. 인기 음원을 붙인 것은 2편뿐이다. → 밈형은 `sync_free`/음원 없음이 기본일 가능성이 높다. 이 실측을 근거로 운영자가 픽스처 구성을 `sync_required` 1장으로 바꿨다(2026-11-02).
  - 장면 전환이 없는 한 장면 클립이 19편이다. 화면 틀은 셋이었다.
    - 검은 바탕 위쪽 글 + 가운데 가로 클립: 12편. memezar 는 핵심 낱말을 빨간색으로 칠한다.
    - 세로 꽉 찬 영상 + 크고 굵은 제목 글(핵심 낱말 노란색): 7편.
    - 글 없는 세로 원본 영상: 5편.
  - 한계: 해외 계정만 봤다. 한국 밈 계정은 공식 API 로 찾지 못했다(이름 추측 17개 중 16개 없음, 1개는 2022년 뒤 게시 없음).

- **나이 구간:** 릴스마다 관측 시점의 "올린 뒤 경과 시간"을 저장한다. 0~24시간 / 24~72시간 / 3~7일 / 7일 이상 중 어디인지 기록한다.
- **기준선:** 같은 계정, 같은 나이 구간의 조회수 중앙값.
  - 그 구간에 조회수가 있는 릴스가 8개 미만이면 `insufficient_sample` 로 표시하고, 뜨는 릴스 판정을 하지 않는다.
- **뜨는 릴스:** 같은 나이 구간 기준선의 3배 이상(첫 값 — 2주 뒤 분포를 보고 정한다).
- **누락:** `view_count` 가 없으면 판정에서 빼고, 빠진 수를 실행 기록에 남긴다. 0으로 채우지 않는다.
- **중복:** 미디어 ID로 하나로 합친다(T2 와 T3 에서 같은 릴스가 오면 한 행). 같은 날 같은 릴스를 두 번 관측하면 마지막 값만 쓴다.
- **관찰 계정 추가 효과:** 새로 추가된 계정의 첫 관측일 릴스는 `backfill` 로 표시한다. "새 예시"·"오르는 중" 신호에 넣지 않는다. 그날 카드 신호가 계정 추가 때문에 오르는 것을 막는다.

### 6-4. 인기 음원 순서 표현 (항목 7)

- `ig_audio` 가 돌려준 순서는 "**인스타가 우리 계정에 준 추천 순서**"라고 부른다. 인스타 전체 인기 순위라고 부르지 않는다.
  - 문서: "트렌딩 오디오를 돌려준다", "앱에서 보이는 것과 다를 수 있다".
- 화면 표기: "목록 n번째(우리 계정 기준, 오늘)".
- "오르는 음원" = 목록에 처음 들어옴, 또는 3일 연속 목록에 남음.
  - 자리 바뀜만으로는 판정하지 않는다. 순서가 날마다 안정적인지 아무도 확인하지 않았기 때문이다.
  - 14일 관측 뒤, 같은 음원의 자리 변동 폭을 보고 다시 정한다.

### 6-5. 형식 뽑기 — 표지 기반 분석 제한 (항목 5)

필드마다 값과 함께 **근거와 확신도**를 저장한다.
- 근거 종류: `video` / `cover` / `caption` / `api_metrics` / `operator`
- 확신도: `high` / `low`

| 필드 | 영상을 본 경우 | 표지·캡션만 있는 경우 |
|---|---|---|
| 구조(POV / 전후 / 반전 / 리스트 / 반응) | 채움 | **추정**으로 채움(근거 `cover`/`caption`, 확신도 low) |
| 표지·첫 화면 글자 | 채움 | 표지에 글자가 보이면 채움(근거 `cover`) |
| 캡션 훅 문장 | 채움 | 채움(근거 `caption`) |
| 음원 종류(노래/원본 소리) | API 값 | API 값(`media_audio_type`) |
| 비트 수 · 컷 길이 · 반전 시점 · 첫 1.5초 내용 · 음악 동기화 | 채움 | **null** — 모델에게 묻지도 않는다 |

**정밀 틀 승격 조건:** 아래 둘 중 하나일 때만 밈형(§5)으로 넘어간다. 아니면 카드는 "참고 카드"로 남는다.
- 비트 수·컷 길이·반전 시점이 `video` 근거로 채워짐
- 운영자가 원본 릴스를 보고 그 칸들을 직접 확인·입력함

**평가(개발 P1 끝, 0원 + 분석비)**
- 영상 파일이 있는 릴스 20개를 고른다.
- 일부러 표지·캡션만 줘서 분석하고, 같은 릴스의 영상 분석 결과와 비교한다.
  1. **근거 없는 필드 생성률** = null 이어야 할 필드에 값이 들어온 비율. 목표 0%. 0이 아니면 코드가 강제로 지운다. 모델을 믿지 않는다.
  2. 추정 필드(구조)의 일치율 — 참고값으로만 쓴다.

### 6-6. 밈 카드 병합·분리와 수명 (항목 7)

- 병합 키 우선순위:
  1. `audio_id`
  2. 챌린지 이름(원본 소리 제목)
  3. 구조 + 훅 문장 유사도
- **음원 이름은 키로 쓰지 않는다.** "original audio"·"오리지널 사운드" 같은 이름이 서로 다른 음원에 겹친다.
- Business Discovery 의 미디어에는 `audio_id` 가 없다(`media_audio_type` 만 온다 [문서]). → 관찰 계정 릴스를 음원 카드에 붙이는 것은 **운영자 확인** 또는 **영상 분석에서 같은 음원으로 판정 + 운영자 확인**일 때만 한다. 자동으로 붙이지 않는다.
- 분리 규칙:
  - 같은 `audio_id` 라도 구조가 다르면 다른 카드다. 같은 음원을 쓴다는 연결 표시만 단다.
  - 같은 이름이라도 `audio_id` 가 다르면 다른 카드다.
- 수명:
  - 새로 뜸 → 오르는 중 → 정점 → 식음.
  - "식음" = **정상 관측일** 7일 동안 새 예시가 없음. `failed` / `not_run` / `partial`(80% 미만)인 날은 세지 않는다.
  - 정상 관측일이 3일 이상 끊기면 모든 카드의 상태 변화를 멈추고, 화면에 "관측 중단 — 상태 고정"을 띄운다.
  - 자동 보관도 그동안 멈춘다.

### 6-7. 분석 예산과 파일 수명 (항목 8)

| 항목 | 값 |
|---|---|
| 분석 모델 | config 상수 하나(기본 `gemini-2.5-flash`, 주류 근거 추출과 같은 모델). 단가는 개발 착수일에 가격 페이지로 다시 확인한다. **[미검증]** |
| 건수 상한 | 영상 분석 하루 20건, 표지 분석 하루 60건 |
| 금액 상한 | 하루 $0.30, 한 달 $6.00. 별도 계수기로 센다 — 건수 상한과 독립. 먼저 닿는 쪽에서 멈춘다. |
| 입력 제한 | 영상 60초 이하·20MB 이하만 영상 분석(바이트로 직접 보냄). 넘으면 표지 분석으로 내린다. 저해상도 분석 옵션을 쓴다. |
| 출력 상한 | 분석 1건 출력 1,500토큰, JSON 만 |
| 재시도 | 파싱 실패 1회 재시도(프로젝트 규칙). 429·5xx 는 그날 재시도하지 않고 다음 날로 넘긴다. 재시도 비용도 금액 계수기에 넣는다. |
| 재분석 방지 | 키 = `media_id` + `analysis_version`. 이미 있으면 다시 부르지 않는다. 판정 기준을 바꿔 `analysis_version` 을 올릴 때만, 운영자 버튼으로 다시 돌린다. |
| 아이디어 생성 | 카드가 처음 생길 때 1회. 하루 10장 상한. 같은 카드는 다시 만들지 않는다. 금액 계수기에 포함. |
| 비용 기록 | 호출 전에 예상액으로 잡고 호출 뒤 실제 토큰으로 정산한다. 상한을 넘을 호출은 시작하지 않는다. |

**파일 수명**
- **로컬:** 실행마다 새 임시 폴더에 받는다. 분석이 끝나면 `finally` 에서 지운다. 삭제가 실패하면 로그를 남기고, 다음 실행 시작 때 24시간 넘은 임시 파일을 먼저 지운다. GitHub Actions 러너는 실행이 끝나면 사라진다.
- **원격:** 영상을 공급자 파일 저장소에 올리지 않는 것이 기본이다(20MB 이하 바이트 직접 전송).
  - 올려야 하는 경우가 생기면 분석 직후 삭제 API 를 부른다.
  - 실패하면 `remote_file_deletions` 에 파일 이름을 남기고, 매일 재시도한다.
  - 공급자 자동 만료 기간에 기대지 않는다.
- **우리 저장소(Supabase Storage)에는 남의 영상 파일을 절대 넣지 않는다.** 남기는 것은 링크·수치·형식 설명·표지 주소(만료되는 URL)뿐이다.

## 7. 음원 — 기능 구분과 게시 계약 (항목 6)

### 7-1. 무엇을 미리 들을 수 있나

| 구분 | 가능 여부 |
|---|---|
| **음원만 미리듣기** | 된다 [문서]. 응답에 `download_url`(약 1.5일 뒤 만료)과 `on_platform_audio_preview_link`(없을 수 있음)가 있다. 화면에서 이 링크로 듣는다. |
| **완성 릴스 + 음원 합성 미리보기** | 안 된다 [문서] — "음원을 붙인 릴스의 미리보기는 지원하지 않는다. 설정대로 게시된다." 우리 쪽에서 `download_url` 음원을 받아 섞어 보는 "근사 미리보기"는 기술적으로 가능하다. 다만 인스타 실제 결과와 같다는 보장이 없고, 음원 파일을 저장하는 것이 약관상 허용되는지 **[미검증]**이다. → 기본은 하지 않는다. |

### 7-2. 검증 항목 (게시 전에 확인할 것)

| 항목 | 문서상 | 확인 방법 |
|---|---|---|
| 시작 위치 지정 | **파라미터 없음**(audio_id·audio_volume·video_volume 뿐) | 문서 기준 "지원 안 함"으로 설계한다. 첫 시험 게시에서 음원이 어디서 시작하는지 귀로 기록한다. |
| 타이밍 제어 | 없음 | 위와 같음 |
| 계정별 사용 가능 | "제3자 사용 허가된 음원만 돌려준다, 앱과 다를 수 있다" | 게시 직전 `GET /{audio_id}?user_id=우리계정` 으로 다시 조회한다. 실패하면 게시하지 않는다. 우리 앱(개발 모드)·우리 계정에서 부착 게시가 되는지는 시험 게시로만 확인된다. **[미검증]** |
| 게시 토큰 종류 | 문서끼리 다르다: 게시 문서는 "페이지 토큰", Audio API 문서는 "사용자 토큰" | 시험 게시 때 사용자 토큰 → 실패하면 페이지 토큰 순서로 확인한다. **[미검증]** |
| 게시 후 음원이 실제로 붙었나 | API 로 읽을 칸이 확인 안 됨 | 운영자가 앱에서 눈으로 확인하고 기록한다. |

### 7-3. 음원 설정 전달 계약 — 화면 → 승인 → 게시 요청 → 공급자

게시 요청에 `audio` 묶음을 추가한다(마이그레이션은 개발 단계에서, 운영 적용은 §10 결재 대상).

```
audio = {
  mode: "ig_audio" | "licensed_mix" | "none",
  audio_id, audio_type, title_snapshot, artist_snapshot,   # 고를 때 화면에 보인 그대로
  audio_volume (1~100), video_volume (1~100),
  sync_grade: "sync_free" | "sync_required",
  selected_by, selected_at,
  verified_available_at                                     # 7-2 재조회 시각
}
approval_hash = sha256(영상 파일 해시 + 캡션 + audio 묶음)
```

1. **화면:** 운영자가 음원을 고르면 `audio` 묶음이 게시 요청에 저장된다. 형식이 카드뉴스 릴스·밈형이면 `mode="none"` 은 고를 수 없다(음원 필수).
2. **승인:** 승인은 `approval_hash` 와 함께 저장된다.
3. **승인 뒤 변경:** 음원·볼륨을 바꾸면 해시가 달라진다. → 승인이 `needs_reconfirm` 으로 돌아간다. 다시 승인해야 게시된다.
4. **게시 워커:** 저장된 `audio` 를 그대로 `audio_configuration={"audio_id","audio_volume","video_volume"}` 로 보낸다. 값을 고치거나 기본값으로 채우지 않는다. 음원을 붙이는 게시는 **facebook_login 연결로만** 보낸다.
5. **공급자:** 컨테이너 상태가 `FINISHED` 일 때만 게시를 호출한다(문서: 1분 간격, 최대 5분).

**실패 처리**

| 언제 | 어떻게 |
|---|---|
| 게시 직전 재조회 실패 / 컨테이너 생성 오류 / 컨테이너 상태 `ERROR`·`EXPIRED` | 요청 상태 `audio_failed`. **음원 없이 게시하는 자동 대체는 없다.** 운영자가 고른다: 다른 음원 → 재승인, 수동 앱 부착, 보류. |
| `sync_required` | 자동 게시 대상이 아니다(§5). |

**기존 흐름 보존**
- 게시 호출 **뒤**의 모든 실패는 지금처럼 `unknown` 이다. 다시 게시하지 않고 조회로 대조한다(`drinks_publish.py:10-14`). 음원 기능은 이 규칙을 바꾸지 않는다.
- 컨테이너 생성 단계(게시 호출 전)의 실패만 재시도할 수 있다. 다만 계정당 하루 400개 컨테이너 한도가 있다 [문서].

### 7-4. 볼륨 기본값 (v1 유지, 첫 시험 게시에서 귀로 판정)
- 나레이션 있음: 음원 15~25 / 영상 100.
- 나레이션 없음: 음원 80~100 / 영상 0~30.

## 8. 토큰 — 검증 전에는 단정하지 않는다 (항목 10)

v1 의 "앱 비밀키를 넣으면 매주 자동 연장" 문장은 **지운다.** 문서가 보장하지 않는다.

| 사실 [문서] | 내용 |
|---|---|
| 장기 사용자 토큰 | 약 60일. 짧은 토큰을 앱 비밀키로 교환해 만든다. |
| 장기 토큰을 다시 교환해 늘릴 수 있나 | **문서에 없다.** |
| 만료되면 | "로그인 흐름을 다시 거쳐야 한다". |
| 장기 페이지 토큰 | 장기 사용자 토큰에서 얻으면 만료일이 없다(특정 조건에서만 무효화). 단, 게시에 페이지 토큰이 맞는지는 §7-2 [미검증]. |

**현재 값 [기존 실측]:** 사용자 토큰(EA…), 만료 2026-12-29 14:52 UTC, 데이터 접근 만료 2027-01-28.

**검증 절차**
| 단계 | 돈·위험 | 내용 |
|---|---|---|
| V-T1 | 0원, 읽기만 | `debug_token` 으로 `expires_at`·`data_access_expires_at` 를 매일 수집 기록에 남긴다. |
| V-T2 | 운영자 결재 필요: `META_APP_SECRET` 저장 + 토큰 교체 | 지금 장기 토큰으로 교환을 1회 시도하고, 새 토큰의 `expires_at` 를 V-T1 값과 비교한다. 늘어났으면 "재교환 가능"으로 기록한다(그래도 주기는 실측으로 정한다). 그대로거나 오류면 "자동 연장 불가"로 확정한다. 새 토큰을 받으면 운영자가 비밀값을 교체한다. |
