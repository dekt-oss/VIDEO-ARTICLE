# 0. 결론

## 0-1. 한 줄 결론

현재 시스템은 **자동화 엔진과 기능 범위는 충분히 성숙했지만, UI가 파이프라인의 데이터 구조를 그대로 노출하여 사용자의 “결정 흐름”이 분산된 상태**다.

따라서 개선의 핵심은 화면을 화려하게 만드는 것이 아니라 다음 4가지다.

1. **익명 쓰기·삭제 권한 차단**
2. **홈을 통계 화면이 아니라 ‘오늘의 다음 작업’ 화면으로 변경**
3. **④ 초안 검수와 ⑤ 지시서를 단계형 작업공간으로 분리**
4. **⑥ 렌더를 상태 목록이 아니라 ‘조치 필요 큐’로 재구성**

## 0-2. 쉽게 말하면

지금은 작업에 필요한 모든 기능이 있지만, 버튼과 정보가 여러 화면·여러 위치에 흩어져 있다.  
개선 후에는 시스템이 사용자에게 다음처럼 말해야 한다.

> “현재 처리할 일은 이것입니다.  
> 여기만 확인하고 이 버튼을 누르면 다음 단계로 넘어갑니다.  
> 오래 걸리는 작업은 화면을 닫아도 계속되며, 문제가 생기면 원인과 해결 버튼만 먼저 보여줍니다.”

## 0-3. 최종 권고 구조

상단의 실제 사용 메뉴를 다음 3개로 단순화한다.

- **오늘의 작업**
- **보관함**
- **데이터**

논문/리포트 공장 전환은 유지하되, 색상 외에 공장명·아이콘·페이지 제목을 항상 같이 표시한다.

기존 라우트는 당장 삭제하지 않는다.  
1차에서는 기존 URL을 유지하면서 새 작업 큐와 단계형 상세 화면으로 연결하고, 안정화 후 중복 목록 화면을 통합한다.

- 모바일 전용 앱 수준의 별도 인터페이스

## 1-3. 개선 판단 기준

모든 개선안은 아래 기준으로 평가한다.

| 기준 | 가중치 | 질문 |
|---|---:|---|
| 작업시간 절감 | 35% | 매일 반복되는 클릭·스크롤·재확인을 줄이는가 |
| 오류·오조작 방지 | 30% | 저장 유실, 잘못된 승인, 삭제, 중복 실행을 줄이는가 |

점수는 각 항목 1~5점으로 계산한다.

- **P0:** 즉시 처리. 보안·데이터 유실·오조작 위험
- **P1:** 핵심 작업시간 단축
- **P2:** 구조·일관성·접근성 강화
- **P3:** 선택적 편의·시각 개선

# 2. 핵심 진단

## 2-1. 가장 큰 문제는 화면 수가 아니라 “행동 상태의 분산”이다

현재 동일 논문이 다음 위치에 반복 노출된다.

- 홈 후보
- ④ 초안 검수 목록
- ④ 검수 상세
- ⑤ 영상 지시서 목록
- ⑤ 지시서 상세
- ⑥ 렌더 결과
- 아카이브

각 화면은 데이터 상태를 잘 보여주지만, 사용자가 궁금한 것은 상태 전체가 아니라 다음 두 가지다.

1. 지금 무엇을 처리해야 하는가
2. 이 작업을 끝내려면 무엇을 눌러야 하는가

따라서 “화면별 목록” 중심에서 **작업 항목 중심 상태 머신**으로 전환해야 한다.

## 2-2. 30분 목표를 가장 많이 깎는 구간

### 1위: ④ 검수 상세의 긴 스크롤과 중복 결정

한 페이지에 다음 작업이 모두 존재한다.

- Fact Sheet 확인
- 빨간 깃발 확인
- 장면별 근거 확인
- 장면 편집 저장
- 대본 편집
- 대본 승인
- 지시서 생성
- 컷 편집 저장
- 렌더 언어 선택
- 지시서 승인

문제는 정보량 자체가 아니라, **현재 단계와 다음 버튼이 화면 밖으로 사라지는 것**이다.

### 2위: 렌더 결과의 조치 우선순위 부재

완료·실패·진행중·업로드됨·보관됨이 날짜순으로 섞여 있다.  
실패 로그는 운영자용 요약 없이 원시 로그가 그대로 노출된다.

사용자는 날짜보다 다음 순서로 보고 싶다.

1. 실패하여 재처리가 필요한 것
2. 완료되어 확인·업로드가 필요한 것
3. 진행 중인 것
4. 이미 처리된 것

### 3위: 홈 상단의 컨트롤 과다

후보 카드에 도달하기 전에 다음이 먼저 나온다.

- 제목과 날짜
- 파이프라인
- 요약 타일 5개
- 확인 바
- 날짜 이동
- 정렬
- 결정 필터
- NEW 필터

운영자의 주요 행동은 후보 낙점인데, 이를 위한 카드가 첫 화면 아래로 밀린다.

## 2-3. 가장 큰 운영 위험

현재 공개 URL을 아는 사용자가 익명 상태로 낙점·승인·삭제 계열 조작을 할 수 있다.

이는 UI 문제가 아니라 운영 불변식 위반이다.

> 시스템이 1인용이어도 “사용자가 1명”인 것과 “누구나 사용자”인 것은 다르다.

# 4. 목표 정보구조

## 4-1. 제안 네비게이션

### 공통 상단바

```text
[🎬 논문 공장 ▾]   [오늘의 작업] [보관함] [데이터]
```

리포트 공장일 때:

```text
[📈 리포트 공장 ▾] [오늘의 작업] [보관함] [데이터]
```

### 원칙

- 공장 선택은 현재처럼 항상 보이게 유지
- 공장 선택 영역에 공장명 전체를 표시
- 주 메뉴는 최대 3개
- ④·⑤·⑥은 상단 메뉴가 아니라 “오늘의 작업” 내부 단계 필터로 표시
- 휴지통은 보관함 내부 보조 링크
- 측정·성과·원자료·채점은 데이터 내부 탭

## 4-2. 목표 라우트

### 실제 노출 라우트

| 라우트 | 역할 |
|---|---|
| `/` | 논문 공장 오늘의 작업 |
| `/work/[paperId]` | 논문 단위 단계형 작업공간 |
| `/archive` | 의도적으로 보관하거나 발행한 결과 |
| `/data` | 원자료·채점·측정·성과 통합 탭 |
| `/finance` | 리포트 공장 오늘의 작업 |
| `/finance/work/[reportId]` | 리포트 단위 단계형 작업공간 |
| `/finance/archive` | 리포트 보관·발행 결과 |
| `/finance/data` | 리포트 원자료·채점 |

### 기존 라우트 처리

1차에서는 기존 라우트를 유지한다.

- `/review`
- `/directive`
- `/render`
- `/papers`
- `/scored`
- `/measure`
- `/analytics`
- `/analytics/report`

이후 새 화면이 안정화되면 다음 중 하나를 적용한다.

- 새 통합 화면으로 redirect
- 통합 화면의 특정 탭으로 연결
- 관리자성 보조 URL로 유지하되 상단 메뉴에서 제거

# 5. 공통 작업 상태 모델

## 5-1. 단일 상태 모델

각 콘텐츠는 UI에서 다음 상태 중 하나로 해석한다.

```text
candidate_undecided
candidate_shortlisted
candidate_picked
draft_missing
draft_generating
draft_review_required
draft_blocked
draft_approved
directive_missing
directive_generating
directive_review_required
directive_blocked
directive_approved
render_queued
render_running
render_failed
render_review_required
upload_pending
uploaded_private
published
archived
```

DB 구조를 즉시 변경할 필요는 없다.  
현재 여러 테이블의 상태를 서버에서 위 상태로 변환하는 **작업 ViewModel**을 만든다.

## 5-2. 작업 ViewModel 예시

```ts
interface WorkItem {
  id: string;
  factory: "paper" | "finance";
  title: string;
  stage: 3 | 4 | 5 | 6;
  state: WorkState;
  nextAction:
    | "decide"
    | "generate_draft"
    | "review_draft"
    | "generate_directive"
    | "review_directive"
    | "check_render"
    | "retry_render"
    | "upload"
    | "none";
  blockingCount: number;
  warningCount: number;
  updatedAt: string;
}
```

## 5-3. 다음 행동 결정 규칙

```text
렌더 실패가 있으면                → 렌더 재시도
렌더 완료·미확인이 있으면         → 결과 확인
지시서 초안·미승인이 있으면       → 지시서 검수
대본 초안·미승인이 있으면         → 대본 검수
낙점됐지만 초안이 없으면          → 초안 생성
미결정 후보가 있으면               → 후보 결정
모두 처리됐으면                    → 오늘 작업 완료
```

이 규칙은 홈의 “다음 작업” 카드와 작업 큐 정렬에 공통 사용한다.

# 6. 화면별 개선 명세

# 6-1. 홈: 오늘의 작업

## 목표

접속 후 3초 안에 다음을 알 수 있어야 한다.

- 오늘 할 일이 있는가
- 가장 먼저 처리할 것은 무엇인가
- 몇 건 남았는가

## 현재 문제

- 요약 타일 5개가 모두 같은 시각적 강도를 가짐
- 발행 수처럼 즉시 행동과 무관한 숫자도 상단에 배치
- 날짜 네비게이션과 필터가 후보보다 먼저 노출
- “미확인 배치일”과 “후보 미결정”이 다른 개념인데 섞여 있음
- 후보 상태가 카드 테두리·투명도에 과도하게 의존

## 목표 배치

```text
[페이지 제목: 논문 공장 · 오늘의 작업]

┌ 다음 작업 ───────────────────────────────┐
│ 미결정 후보 20편                         │
│ 오래된 미확인 배치: 2026-07-15           │
│                          [후보 검토 시작] │
└──────────────────────────────────────────┘

[후보 20] [검수 필요 3] [렌더·업로드 필요 2]

[후보 카드 목록]

[고급 필터 ▾]
[배치 날짜 이동 ▾]
```

## 변경 규칙

1. 기존 요약 타일 5개를 3개 작업 지표로 축소
   - 후보 미결정
   - 검수 필요
   - 렌더·업로드 필요
2. `발행` 누계는 홈에서 제거하고 보관함/성과로 이동
3. 날짜 네비게이션을 “배치 날짜” 접이식 보조 영역으로 이동
4. 정렬 기본값은 유지하되 컨트롤을 한 줄로 축소
5. 후보 카드에 상태 라벨을 항상 표시
   - `미정`
   - `낙점`
   - `후보`
   - `탈락`
6. 탈락 카드의 투명도는 50%보다 높게 유지
   - 텍스트 가독성 유지
   - 상태 라벨과 아이콘으로 구분
7. 결정 후 카드 위치가 갑자기 이동하지 않게 한다
8. 오류는 토스트로 통일
9. 처리 중인 카드만 로컬 busy 상태 표시
10. `낙점`을 주요 버튼, `후보`를 보조 버튼, `탈락`을 더보기 또는 낮은 강조로 배치

## 후보 카드 정보 계층

항상 노출:

- 한국어 제목
- 한 줄 요약

# 6-2. ④·⑤ 단계형 작업공간

## 핵심 결정

④ 초안 검수와 ⑤ 영상 지시서는 **같은 콘텐츠 맥락은 유지하되, 동시에 한 화면에 길게 렌더하지 않는다.**

권고 방식:

- 동일 작업 URL
- 단계별 탭/stepper
- 현재 단계만 본문에 렌더
- 승인 후 다음 단계로 자동 전환 가능
- 사용자가 이전 단계로 돌아가 근거를 재확인할 수 있음

## 목표 상단

```text
[← 작업 목록]  제목

④ 초안 검수  ✓ 완료
⑤ 영상 지시서  검수 필요
⑥ 렌더 결과    대기

차단 0 · 경고 2 · 마지막 저장 14:32
```

## 단계 전환 규칙

- 현재 단계에 미저장 편집이 있으면 이동 전 확인
- 차단 오류가 있으면 승인 비활성
- 경고만 있으면 승인 가능하되 확인 모달에 경고 수 표시
- 승인 성공 시 다음 단계 이동 CTA 표시
- 이전 단계는 읽기 전용으로 재확인 가능
- 렌더 시작 후 승인된 지시서는 잠금 유지

## 데스크톱 레이아웃

1100px 이상에서 2열 사용:

```text
┌ 본문 760~820px ─────────────┬ 결정 레일 280~320px ┐
│ Fact Sheet / 장면 / 컷       │ 상태                │
│ 대본·프롬프트 편집            │ 차단·경고 요약       │
│                              │ 저장 상태            │
│                              │ 승인/다음 단계       │
└──────────────────────────────┴─────────────────────┘
```

모바일에서는 1열로 전환하고 하단 sticky 액션을 사용한다.

# 6-3. ④ 초안 검수 단계

## 정보 우선순위

### 상단 고정 요약

- 자기검증 통과 여부
- 근거 없음 씬 수
- 편집 미저장 여부
- 원문 링크
- 주요 승인 버튼

### 기본 펼침

- 빨간 깃발이 있는 씬
- 전체 대본
- 검증 요약

### 기본 접힘

- Fact Sheet 전체
- 근거가 모두 있는 일반 씬
- 영문 나레이션
- 이미지·영상 프롬프트 전문
- 원문 초록 전문

단, 근거 정보 자체를 제거하지 않는다.

## 씬 카드 요약 헤더

```text
#3  핵심 수치 설명 · 6초
✓ 근거 2개 · ⚠ 경고 0
[펼치기]
```

빨간 깃발 씬:

```text
#4  결론 일반화 · 7초
⛔ 근거 없음 1개
[확인 필요]
```

## 편집 모드

- 기본은 검토 모드
- `편집 시작`을 누르면 textarea 활성화
- 편집 모드 진입 시 상단에 저장 상태 표시
- 대본과 장면 편집을 동일한 “현재 초안 변경사항”으로 묶음
- 최소 구현은 통합 저장 버튼
- 권장 구현은 800~1200ms debounce autosave
- 승인은 저장과 다른 행위로 유지

## 승인 규칙

승인 버튼 활성 조건:

- 생성 중 아님
- 저장 중 아님
- 차단 오류 0
- 최신 편집 저장 완료

승인 모달:

```text
대본을 승인하고 ⑤ 영상 지시서 단계로 이동합니다.

검증 결과
- 차단: 0
- 경고: 2
- 근거 없는 씬: 0

[취소] [승인하고 다음 단계]
```

## 페이지 이탈 방지

다음 두 가지 모두 구현한다.

1. `beforeunload`
2. 앱 내부 링크 전환 가드

메시지는 브라우저 기본 경고를 사용해도 된다.  
별도 커스텀 모달은 내부 단계 이동에만 사용한다.

## 수정 대상

- `web/app/review/[paperId]/page.tsx`
- `web/components/ReviewClient.tsx`
- 신규 `web/components/StageStepper.tsx`
- 신규 `web/components/DecisionRail.tsx`

- 근거 없는 씬은 페이지 진입 시 접혀 있지 않음
- 일반 씬은 요약 헤더로 빠르게 훑을 수 있음

# 6-5. ⑥ 렌더 결과

## 핵심 변경

날짜순 목록을 기본 구조로 사용하지 않는다.

기본 탭:

1. **조치 필요**
2. **진행 중**
3. **완료**
4. **보관**

### 조치 필요 포함 항목

- 렌더 실패
- QA hard fail
- 렌더 완료됐지만 확인하지 않은 결과
- 확인 완료됐지만 업로드가 필요한 결과
- 유튜브 업로드 실패

## 카드의 주요 행동

상태별 주요 버튼은 하나만 강조한다.

| 상태 | 주요 버튼 |
|---|---|
| 실패 | 원인 확인·재시도 |
| QA 실패 | 영상 확인 |
| 완료·미확인 | 영상 검수 |
| 검수 완료·미업로드 | 유튜브 업로드 |
| 업로드 실패 | 업로드 재시도 |
| 진행 중 | 버튼 없음 |
| 처리 완료 | 세부 보기 |

보조 행동은 `⋯` 메뉴 또는 낮은 강조 버튼으로 이동한다.

- 다른 언어 생성
- 보관
- 반려
- 휴지통

## 진행 중 표현

반드시 표시:

- 현재 단계
- 경과 시간
- 화면을 떠나도 계속된다는 안내
- 마지막 상태 확인 시각
- 자동 갱신 여부

예시:

```text
조립 중 · 08:42 경과
10초마다 자동 확인 · 이 화면을 닫아도 렌더는 계속됩니다.
```

정확한 예상 완료 시간은 측정 전 표시하지 않는다.  
우선 렌더 시작·종료 시간을 기록한 뒤 최근 N건의 중앙값을 사용할 수 있다.

## 자동 갱신

- 진행 중 job이 있을 때만 10초 간격 polling
- `document.visibilityState === "hidden"`이면 30~60초로 완화
- 모든 job이 종료되면 polling 중단
- 갱신은 `router.refresh()` 사용
- 열린 그룹·스크롤 위치 보존
- `window.location.reload()` 사용 금지

## 실패 메시지

원시 로그를 바로 노출하지 않는다.

```text
렌더 실패
원인: 입력 영상 파일을 읽지 못했습니다.
권장 조치: 해당 컷 에셋을 다시 생성한 뒤 재렌더하세요.

[재시도] [기술 로그 보기]
```

`기술 로그 보기`를 펼쳤을 때만 전체 `ffmpeg` 로그를 표시한다.

## 오류 분류 예시

| 패턴 | 사용자 메시지 |
|---|---|
| `moov atom not found` | 영상 파일이 불완전하거나 손상됨 |
| `Invalid data found` | 입력 에셋을 읽지 못함 |
| `예산 초과` | 설정된 렌더 비용 상한 초과 |
| 업로드 401/토큰 | 유튜브 인증 갱신 필요 |
| 알 수 없음 | 기술 로그를 확인하고 재시도 |

## 렌더 검수 모달/상세

영상 검수 시 다음을 한 영역에 표시한다.

- 영상 플레이어
- 언어·버전·길이·비용
- QA 결과
- 업로드 제목·설명
- 주요 승인/업로드 버튼

복사 버튼 4개를 첫 계층에 모두 둘 필요는 없다.

- 한국어 job이면 한국어 제목·설명 우선
- 영어 job이면 영어 제목·설명 우선
- 다른 언어는 보조 영역

## 수정 대상

- `web/components/RenderList.tsx`
- `web/app/render/page.tsx`
- `web/lib/useGeneration.ts` 또는 신규 `useAsyncJobPolling.ts`
- 신규 `web/lib/renderError.ts`
- 신규 `web/components/AsyncJobStatus.tsx`
- 신규 `web/components/ErrorDisclosure.tsx`
- 신규 `web/components/RenderReviewPanel.tsx`

## 완료 조건

- 실패 항목이 기본 화면 최상단에 표시
- 원시 로그는 기본 접힘
- 진행 job은 수동 새로고침 없이 상태 갱신
- 완료/반려/업로드/보관 후 전체 reload 없음
- 열린 상세 상태와 스크롤 위치 유지
- 각 job에서 강조된 주요 행동은 1개
- 삭제는 항상 확인 모달 사용

## 7-3. 버튼 계층

- Primary: 현재 단계 완료 또는 다음 단계
- Secondary: 저장, 원문 보기, 복사
- Tertiary: 필터, 펼치기, 보조 이동
- Danger: 삭제·재생성·반려

한 영역에 Primary 버튼은 원칙적으로 1개만 둔다.

## 7-4. 상태 표현

색상만 사용하지 않는다.

모든 상태는 다음 3개를 조합한다.

- 텍스트
- 아이콘
- 색상

예시:

- `✓ 완료`
- `⏳ 진행 중`
- `⚠ 확인 필요`
- `⛔ 차단`
- `🗑 휴지통`

## 7-5. 모바일

최소 터치 영역 44×44px을 목표로 한다.

- 상단바는 2줄 이내
- sticky 상단바가 화면 높이의 과도한 비율을 차지하지 않음
- 작업 단계는 짧은 라벨 사용
- 긴 테이블은 문서 전체가 아니라 테이블 컨테이너 내부에서 처리
- action bar는 safe-area를 고려

# 8. 피드백·저장·비동기 작업 규칙

## 8-1. 피드백 통일

금지:

- 브라우저 `alert`
- 브라우저 `confirm`
- 성공 후 `window.location.reload()`

허용:

- `Toast`
- `ConfirmModal`
- `router.refresh()`
- 로컬 optimistic update
- 상태별 인라인 배너

현재 `addLanguage`의 `window.confirm`도 `ConfirmModal`로 교체한다.

## 8-2. 토스트 규칙

| 상황 | 방식 |
|---|---|
| 저장 성공 | 2초 성공 토스트 |
| 복사 성공 | 버튼 내부 `복사됨 ✓` 또는 짧은 토스트 |
| 네트워크 실패 | 오류 토스트 + 재시도 가능 |
| 오래 걸리는 작업 시작 | 인라인 상태 + 시작 토스트 |
| 차단 오류 | 토스트만 쓰지 말고 본문 배너 표시 |

## 8-3. 저장 상태

모든 편집 화면 상단 또는 우측 레일에 표시한다.

- 저장됨
- 저장 중
- 저장 실패
- 저장되지 않은 변경사항
- 마지막 저장 시각

## 8-4. 중복 실행 방지

- 동일 콘텐츠·동일 작업의 active job이 있으면 생성 버튼 비활성
- 서버에서도 idempotency 또는 unique 조건 확인
- 버튼 busy 상태만으로 중복 방지를 끝내지 않음
- 오류 후 재시도는 명시적 action으로 처리

## 8-5. polling 공통화

현재 초안·지시서용 `useGeneration`과 렌더 갱신을 다음 공통 훅으로 통합한다.

```ts
useAsyncJob({
  kickoff,
  status,
  interval,
  timeout,
  backgroundInterval,
  onDone,
  onError,
});
```

기능:

- 시작
- 중복 실행 방지
- 단계 라벨
- 경과 시간
- visibility 기반 polling
- 완료 후 `router.refresh()`
- 타임아웃이 작업 실패를 의미하지 않는다는 안내
- 언마운트 정리

# 11. 접근성 최소선

## A11Y-01. 키보드

- 모든 버튼·링크 Tab 접근 가능
- Enter/Space 동작 확인
- 모달 열릴 때 포커스 이동
- 모달 닫힐 때 원래 버튼으로 포커스 복귀
- Esc로 모달 닫기
- 비활성 요소는 실제 `disabled` 사용

## A11Y-02. 탭

현재 `role="tablist"`만 있고 자식에 완전한 tab semantics가 없는 구조를 정리한다.

선택지:

1. 단순 필터이면 `role="tablist"`를 제거하고 일반 버튼 그룹 사용
2. 실제 탭이면:
   - `role="tab"`
   - `aria-selected`
   - `aria-controls`
   - `role="tabpanel"`

후보 정렬·필터는 실제 문서 탭이 아니므로 일반 버튼 그룹이 더 적절하다.

## A11Y-03. 포커스 표시

```css
:focus-visible {
  outline: 2px solid var(--accent);
  outline-offset: 2px;
}
```

## A11Y-04. 색상 외 상태

- 낙점·탈락을 테두리와 투명도만으로 구분하지 않음
- 배지 텍스트·아이콘 추가
- 실패·경고·완료 배너에 텍스트 라벨 포함

## A11Y-05. 라이브 상태

토스트와 생성 진행 상태에 적절한 live region을 적용한다.

- 성공 토스트: `aria-live="polite"`
- 차단 오류: `role="alert"`
- 진행 상태: 과도하게 매초 읽히지 않도록 경과 초 전체를 live region에서 제외

# 17. 개발 AI 전달용 통합 작업 지시

아래 내용은 Claude Code 또는 Codex에 그대로 전달할 수 있다.

```text
프로젝트: dekt-oss/VIDEO-ARTICLE
기준 커밋: ba779712cc3d8940c814c0cb4ab0b254f91e9495
목표: video-article 대시보드를 1인 운영자의 결정 중심 작업 콘솔로 개선한다.

최우선 불변식:
1. Fact Sheet·빨간 깃발·근거 있음/없음 표시는 축소·삭제하지 않는다.
2. 논문 1편 낙점부터 지시서 승인까지 사람 작업 30분 이내가 목표다.
3. Next.js 14 App Router, Supabase, 큐 기반 비동기 구조를 유지한다.
4. 한국어 UI와 ①~⑥ 파이프라인 번호를 유지한다.
5. 기존 migration을 수정하지 말고 신규 migration을 추가한다.
6. 논문·리포트 공장 양쪽의 UX가 어긋나지 않게 한다.
7. UI 라이브러리를 새로 도입하지 않는다.

작업 순서:

Phase 0
A. 인증·RLS 복구

- mutation API 전부 서버 세션 검증

D. 렌더 오류
- renderError parser 작성
- 사용자용 원인·권장조치 표시
- 원시 로그는 details로 접기
- 실패 상태의 주요 버튼을 재시도로 변경

Phase 1
E. 홈
- 5개 summary tile을 후보/검수/렌더·업로드 필요 3개로 축소
- NextActionCard 추가
- 후보 카드를 날짜·고급필터보다 위에 배치
- 날짜/필터는 접이식 보조 영역
- 후보 카드에 항상 텍스트 상태 라벨 표시

F. 작업 ViewModel
- 여러 DB 상태를 WorkItem(stage/state/nextAction/blockingCount/warningCount)으로 변환
- 조치 필요 우선 정렬
- 논문·리포트 adapter 분리

G. 단계형 상세
- ④ 초안 검수, ⑤ 지시서, ⑥ 렌더 stepper
- 현재 단계만 본문에 렌더
- 데스크톱 DecisionRail, 모바일 하단 action bar
- 경고 항목 자동 펼침
- 승인 후 다음 단계 이동

Phase 2
```
